# Flutter: денежные операции — только бэкенд

**Статус:** обязательно к следующему релизу. Документ **отменяет** legacy-режим из [cash-and-cashflows.md](./cash-and-cashflows.md) (§1.3, §4, §6, флаг `BE_CASHFLOWS`) и раздел 13.4 из [add-product.md](./add-product.md).
**Дата:** 2026-10-02

---

## 0. Коротко

1. Движения кассы (приход/расход) создаёт **только бэкенд** — внутри того же запроса, что и бизнес-операция (продажа, создание товара, приход, оплата долга, возврат).
2. Flutter **никогда** не делает `POST /construction/cashflows/` после бизнес-операции. Ни сразу, ни «если не получилось», ни «на всякий случай».
3. Флаг `BE_CASHFLOWS`, функцию `postCashflowIfNeeded`, выбор «первой кассы» (`GET /construction/cashboxes/` → `[0]`) и поле `status` в авто-операциях — **удалить из кода**, а не выключить.
4. Единственное исключение — экран «Касса» → «Добавить приход/расход», когда пользователь сам вводит сумму и сам выбирает кассу (§5).

---

## 1. Почему: инцидент на проде 2026-10-02

Приложение после каждой операции отправляет второй запрос в кассу — по инструкции из старого раздела [add-product.md §13.4](./add-product.md#134-денежный-поток). Бэкенд к этому моменту уже создал свою запись. Итог — каждая операция в кассе учитывается **дважды**.

Пример из nginx-лога (UTC), user-agent `Dart/3.12 (dart:io)`:

```
15:23:48 POST /api/main/pos/sales/{id}/checkout/   ← бэк создал 2 записи pos_sale (Наличные 20000, Мбанк 20500)
15:23:49 POST /api/construction/cashflows/         ← приложение: «Продажа (наличные)» 20000
15:23:49 POST /api/construction/cashflows/         ← приложение: «Продажа (онлайн)» 20500
```

Что в итоге в кассе:

| Операция                   | Бэкенд создал                               | Приложение добавило                                      | Ошибка                                   |
| -------------------------- | ------------------------------------------- | -------------------------------------------------------- | ---------------------------------------- |
| Продажа (смешанная оплата) | `pos_sale` × 2, со сменой и способом оплаты | «Продажа (наличные)», «Продажа (онлайн)», `shift = null` | Приход ×2                                |
| Продажа **в долг**         | ничего (денег нет)                          | «Продажа (наличные)» на всю сумму                        | **Фантомный приход** — денег в кассе нет |
| Создание товара            | `warehouse_purchase` «Закупка товара: X»    | «X» на ту же сумму                                       | Расход ×2                                |

Масштаб: с 2026-09-25 — **~6 600 лишних записей** во многих компаниях. Веб-клиент `market.nurcrm.kg` дублей не создаёт — он уже работает по этому документу.

## 2. Что удалить в приложении

Запросы, после которых приложение сейчас шлёт `POST /construction/cashflows/` (по логу за один день):

| После какого запроса                                        | Кол-во за день | Что сделать                                            |
| ----------------------------------------------------------- | -------------- | ------------------------------------------------------ |
| `PATCH /main/products/{id}/`                                | 252            | Удалить POST кассы. См. §4.1 — пополнение остатка      |
| `POST /main/pos/sales/{id}/checkout/`                       | 222            | Удалить POST кассы                                     |
| `POST /main/products/create-manual/` (+ загрузка `images/`) | 275            | Удалить POST кассы. Сумму передать в сам create (§3.1) |
| `POST /main/clients/{id}/deals/`                            | 68             | Удалить POST кассы. См. §4.2                           |

Чек-лист удаления:

- [ ] Все вызовы `POST /construction/cashflows/` вне экрана ручной кассы.
- [ ] `postCashflowIfNeeded` (Dart) и всё, что его вызывает.
- [ ] Флаг `BE_CASHFLOWS` / `CashflowConfig.isBackendCashflowsEnabled` и ветки `else` под ним.
- [ ] Получение «первой кассы» для авто-операций (`cashBoxes.first`, `cashBoxes[0]`).
- [ ] Расчёт `status: approved/pending` по тарифу «Старт» — статус ставит бэкенд.
- [ ] Тосты «касса не записалась, добавьте вручную» для авто-операций.

> Поиск по коду: `construction/cashflows`, `source_cashbox_flow_id`, `source_business_operation_id`. В бизнес-флоу этих строк остаться не должно — только в экране ручной кассы и в чтении ленты (`GET`).

## 3. Что слать вместо этого

Во все операции ниже бэкенд сам выбирает кассу, создаёт движение, ставит статус (`approved`/`pending` по настройкам компании) и привязывает его к смене. Flutter передаёт только **параметры операции**.

Общие поля маршрутизации (все опциональны):

| Поле           | Когда слать                                                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `shift_id`     | POS-операции, если у кассира открыта смена                                                                                                     |
| `branch_id`    | Если пользователь работает в филиале                                                                                                           |
| `cashbox_role` | Только если известно точно: `pos_main` / `pos_branch` для продаж и оплаты долга, `expense_variable` для закупок. Не прислали — бэк выберет сам |
| `cashbox_id`   | **Только** если пользователь явно выбрал кассу в UI. Никогда не подставлять первую из списка                                                   |

### 3.1 Создание товара

```http
POST /main/products/create-manual/
POST /main/products/create-by-barcode/
```

Добавить в тело создания товара:

| Поле              | Значение                                                                                                                                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payment_type`    | `"cash"` — оплачено сразу, `"debt"` — в долг, `"prepayment"` — предоплата                                                                                                                                             |
| `cashflow_amount` | **Только для предоплаты** — сумма предоплаты (`"500.00"`). Для `"cash"` не слать: бэк сам посчитает `purchase_price × quantity`. Для `"debt"` **не слать никогда** — если прислать, бэк создаст расход даже при долге |
| `cashbox_role`    | `"expense_variable"` (можно не слать — это значение по умолчанию)                                                                                                                                                     |
| `cashbox_id`      | Только при явном выборе кассы пользователем                                                                                                                                                                           |

Бэк создаёт расход `source_kind = "warehouse_purchase"`, название «Закупка товара: {name}». Если сумма 0 или `payment_type = "debt"` (без `cashflow_amount`), расход не создаётся.

Сделка/долг с поставщиком (`POST /main/clients/{id}/deals/`, `POST /main/debts/`) — как и раньше, отдельным запросом. Касса после неё — **не трогать**.

### 3.2 Продажа (checkout)

```http
POST /main/pos/sales/{sale_id}/checkout/
```

Тело — как в [cash-and-cashflows.md §9.1](./cash-and-cashflows.md#91-checkout): `payment_method` или `payments[]` для смешанной оплаты, `cash_received`, `client_id`, `prepayment_method`, `shift_id`, `branch_id`, `cashbox_role`.

Бэк создаёт:

| Оплата                   | Записи в кассе                              |
| ------------------------ | ------------------------------------------- |
| Одним способом           | 1 × `pos_sale` на сумму чека                |
| Смешанная (`payments[]`) | По одной `pos_sale` на каждый способ        |
| В долг без предоплаты    | **Ничего**                                  |
| В долг с предоплатой     | `pos_prepayment` только на сумму предоплаты |

Ответ содержит `cashflows[]`, `resolved_cashbox_id`, `resolved_cashbox_name` — их можно показать в тосте («Учтено в кассе «…»»). Ничего больше делать не нужно.

### 3.3 Оплата долга клиента

Любой из эндпоинтов (см. [debt-payments.md](./debt-payments.md)):

```http
POST /main/clients/{client_id}/deals/{deal_id}/pay/
POST /main/clients/{client_id}/deals/pay-any/
POST /main/debts/{id}/pay/
POST /main/pos/sales/{sale_id}/pay-debt/
```

Слать `amount`, `payment_method`, `shift_id` (если смена открыта). Бэк создаёт `debt_repayment` (или `supplier_debt_payment` для долга перед поставщиком).

### 3.4 Приход от поставщика

```http
POST /main/suppliers/{supplier_id}/receipt/
```

Слать `items[]`, `payment_type`. Бэк создаёт `procurement_receipt` и возвращает `cashflows[]`.

### 3.5 Возвраты

| Операция              | Эндпоинт                                      | Что создаёт бэк                                                                                                  |
| --------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Возврат чека клиентом | `POST /main/pos/sales/{sale_id}/return/`      | `pos_sale_return` (расход), см. [sale-returns-and-cashflow-requests.md](./sale-returns-and-cashflow-requests.md) |
| Возврат поставщику    | `POST /main/suppliers/{supplier_id}/returns/` | `supplier_return`                                                                                                |

## 4. Операции, где бэк кассу **не** трогает

Для этих операций движения кассы не будет ни от бэка, ни от приложения. Это осознанно — **не компенсировать ручным POST**.

### 4.1 Пополнение остатка через `PATCH /main/products/{id}/`

`PATCH` товара — это редактирование карточки, а не закупка. Бэк расход не создаёт.

Как на вебе:

- **Поставщик выбран** → оприходовать через `POST /main/suppliers/{supplier_id}/receipt/` с `items: [{ product, qty, purchase_price }]` и `payment_type`. Расход создаст бэк (§3.4). Затем, если нужно, `PATCH` только розничной цены.
- **Поставщик не выбран** → `PATCH { quantity, purchase_price, price }` без движения кассы. Это быстрая корректировка остатка.

Если нужен расход без поставщика — это задача бэку (отдельный эндпоинт), а не приложению.

### 4.2 Создание сделки `POST /main/clients/{id}/deals/`

Создание сделки/долга кассу не меняет. Деньги попадают в кассу только при **оплате** (§3.3) или через предоплату внутри создания товара (§3.1) или checkout (§3.2).

## 5. Ручная касса — единственный разрешённый POST

Экран «Касса» → «Добавить приход/расход». Пользователь сам вводит название, сумму и выбирает кассу.

```http
POST /construction/cashflows/
```

```json
{
  "cashbox": "<uuid, выбранный пользователем>",
  "type": "income",
  "name": "Внесение размена",
  "amount": "5000.00"
}
```

Правила:

- Только по явному нажатию пользователя на этом экране.
- `cashbox` — обязательно из выбора пользователя.
- **Не** слать `source_cashbox_flow_id` и `source_business_operation_id`. Ручная операция ни к чему не привязана.
- **Не** слать `status` — его ставит бэк.

---

## 6. Чтение кассы

Без изменений:

```http
GET /construction/cashflows/?cashbox={id}&status=approved&page=1&page_size=100
```

Записи от бэка отличаются полем `source_kind` (`pos_sale`, `warehouse_purchase`, `debt_repayment`, …) и `source_id` (id продажи/товара/платежа). Записи с `source_kind = null` и заполненным `source_cashbox_flow_id` — это старые дубли из приложения. Их почистят на бэке отдельно, клиенту ничего делать не нужно.

Для каждой строки: выполнить операцию в приложении → открыть `GET /construction/cashflows/?cashbox=…` → проверить.

| #   | Сценарий                                          | Ожидаемо в кассе                                             |
| --- | ------------------------------------------------- | ------------------------------------------------------------ |
| 1   | Продажа наличными 1000                            | 1 запись, `source_kind = pos_sale`, `shift` заполнен         |

| 6   | Создание товара в долг                            | 0 записей                                                    |

## 8. Старые версии приложения

Пользователи, которые не обновятся, продолжат создавать дубли. Нужно:

1. Поднять минимальную версию приложения (force update) после релиза.
2. Бэку — отдельная задача: отклонять `POST /construction/cashflows/` с `source_cashbox_flow_id`, если на этот id уже есть авто-запись (`pos_sale`, `warehouse_purchase` и т.д.).
