# Flutter: массовое сканирование на склад (mass-scan)

Документ для мобильного клиента NurCRM Market. Описывает экран **«Массовое сканирование»** так, как он работает на вебе после исправления (сентябрь 2026). Цель — повторить API, классификацию, валидацию и порядок запросов 1:1.

**Веб-экран:** `/crm/sklad/mass-scan` (кнопка «Массовое сканирование» на `/crm/sklad`)
**Веб-код:** `src/features/mass-incoming/`

- `model/useMassIncoming.ts` — состояние, очередь сканов, проведение
- `api/massIncomingApi.ts` — все запросы
- `lib/classifyBarcode.ts` — классификация штрихкода, ключи строк
- `ui/MassIncomingView.tsx` — разметка

Связанные доки: [auth-and-api-basics.md](./auth-and-api-basics.md), [products-catalog.md](./products-catalog.md), [add-product.md](./add-product.md), [../backend/alternate-barcodes.md](../backend/alternate-barcodes.md).

## 0. Какие баги исправлены (и чего не повторять во Flutter)

| # | Симптом | Причина | Как правильно |
|---|---------|---------|---------------|
| 1 | «Не найден склад компании. Дождитесь загрузки или обновите страницу» даже когда все товары есть в CRM | Склад брался из `GET /warehouse/crud/warehouses/`. Это модуль «Склад» другого сектора, у маркет-компаний он пустой | Склад маркета — `GET /main/warehouses/`. Если его нет, проводить приход через карточки `/main/products/` (§5.3b). **Отсутствие склада больше не блокирует приход** |
| 2 | Товары из «Есть в базе CRM» не приходуются | `global-barcode` возвращает **глобальный** товар NurCRM (`GlobalProduct`). Его `id` не является карточкой компании | Сначала создать карточку компании `POST /main/products/create-by-barcode/`, затем приходовать по новому `id` (§5.1) |
| 3 | Нельзя указать цену для товаров «Есть в базе NurCRM» | Цены в UI не было | В списке IN_CATALOG есть колонка «Цена продажи». Для товаров из глобальной базы она **обязательна** (§4) |
| 4 | Неизвестный штрихкод нельзя внести в базу | `create-by-barcode` работает только с глобальной базой и для неизвестного кода отвечает ошибкой. Ошибка выводилась под модалкой, поэтому её не было видно | Неизвестный код создаётся через `POST /main/products/create-manual/`, ошибка показывается **внутри** модалки (§3.4) |
| 5 | При быстром сканировании часть товаров пропадала | Пока шла проверка одного кода, следующие сканы отбрасывались (`busy`) | Очередь сканов: коды обрабатываются по одному, ни один не теряется (§3.1) |

## 1. Общие правила API

Базовый префикс: `{host}/api`, авторизация `Authorization: Bearer <accessToken>` (см. [auth-and-api-basics.md](./auth-and-api-basics.md)).

- `quantity` и `price` отправляются **строками** с точкой (`"10"`, `"120.50"`). При вводе с клавиатуры принимать и `,`.
- `404` / `405` / `501` на новых эндпоинтах означают «не поддерживается», и клиент переходит на fallback. Любой другой код ошибки показывается пользователю.
- Ошибки: `{ "detail": "…" }`, `{ "message": "…" }` или объект полей `{ "name": ["…"] }`. Тот же парсер, что в остальных экранах.

### Эндпоинты экрана

| Метод | Путь | Назначение |
|-------|------|-----------|
| `GET` | `/main/warehouses/` | Склад маркета (берём первый). Пустой список — режим без склада |
| `GET` | `/warehouse/{warehouse_id}/barcode-check/{code}/` | Серверная классификация (если склад есть) |
| `GET` | `/main/products/warehouse-barcode/{code}/` | Карточка компании по основному штрихкоду |
| `GET` | `/main/products/list/?search={code}&page=1&page_size=50` | Поиск по `alternate_barcodes` |
| `GET` | `/main/products/global-barcode/{code}/` | Глобальная база NurCRM (`GlobalProduct`) |
| `POST` | `/main/products/create-by-barcode/` | Карточка компании из глобальной базы |
| `POST` | `/main/products/create-manual/` | Карточка компании для неизвестного кода |
| `PATCH` | `/main/products/{id}/` | Смена цены; приход без склада |
| `GET` | `/main/products/{id}/` | Свежий остаток перед приходом без склада |
| `POST` | `/warehouse/{warehouse_id}/mass-incoming/` | Атомарный приход (если склад принят сервером) |

`{code}` всегда URL-encoded (`Uri.encodeComponent`).

## 2. Модель данных

### 2.1 Статусы и источники

```dart
enum MassStatus { inStock, inCatalog, unknown } // IN_STOCK / IN_CATALOG / UNKNOWN

/// Откуда товар строки.
enum MassSource {
  company, // карточка компании (/main/products/) — можно приходовать
  global,  // только глобальная база NurCRM — сначала создать карточку
  none,    // нигде не найден
}
```

Три списка на экране:

| Список (ru / ky) | `status` | Возможные `source` |
|------------------|----------|--------------------|
| «Есть на складе» / «Складда бар» | `IN_STOCK` | `company` |
| «Есть в базе CRM» / «CRM базасында бар» | `IN_CATALOG` | `global` (подпись «из базы NurCRM»), `company` (создана карточка на этом экране или сервер вернул IN_CATALOG) |
| «Неизвестный штрихкод» / «Белгисиз штрихкод» | `UNKNOWN` | `none` |

### 2.2 Строка

```dart
class MassRow {
  final String key;          // см. 2.3
  final String barcode;
  MassStatus status;
  MassSource source;
  String name;
  num quantity;              // по умолчанию 1, повторный скан +1
  num? stockQty;             // текущий остаток (только company)
  String? productId;         // id карточки компании; null для global/none
  String? unit;
  String price;              // цена продажи, которую ввёл пользователь
  String initialPrice;       // цена карточки на момент скана ("" для global/none)
}
```

### 2.3 Ключ строки (важно для объединения сканов)

```dart
String rowKey(MassSource source, String barcode, String? productId) =>
    source == MassSource.company && productId != null
        ? 'p:$productId'
        : '${source.name}:$barcode';
```

- Одна карточка компании = одна строка, даже если её отсканировали по разным (альтернативным) штрихкодам.
- Повторный скан с тем же ключом увеличивает `quantity` на 1 и **не меняет** статус строки. Если сначала создали карточку для UNKNOWN (строка перешла в IN_CATALOG с ключом `p:{id}`), следующий скан этого кода вернёт `company`, найдёт ту же строку и увеличит количество.
- Если после создания карточки ключ совпал с уже существующей строкой, строки сливаются, количества складываются.

### 2.4 Нормализация товара из любого ответа

Ответы бывают как `{ ...product }`, так и `{ product: { ... } }`:

```dart
Map<String, dynamic>? unwrap(dynamic raw) {
  if (raw is! Map) return null;
  final p = raw['product'] is Map ? raw['product'] : raw;
  return Map<String, dynamic>.from(p);
}

// id:        p['id'] ?? p['uuid'] ?? p['product_id']
// name:      p['name'] ?? p['title'] ?? 'Товар'
// stock_qty: p['stock_qty'] ?? p['quantity'] ?? p['stock'] ?? 0
// price:     p['price'] → строка ('' если нет/не число)
// unit:      p['unit'] ?? 'шт'
```

## 3. Сканирование

### 3.1 Очередь (обязательно)

Сканер шлёт коды быстрее, чем отвечает сеть. **Нельзя** игнорировать скан, пока идёт проверка предыдущего: именно так терялись товары. Используйте последовательную очередь:

```dart
Future<void> _queue = Future.value();
int pending = 0; // показывать «Проверка штрихкодов: N»

void onScan(String raw) {
  final code = raw.trim();
  if (code.isEmpty) return;
  // Антидубль: один физический скан может прийти дважды
  // (поле ввода + глобальный слушатель сканера).
  final now = DateTime.now();
  if (code == _lastCode && now.difference(_lastAt).inMilliseconds < 300) return;
  _lastCode = code; _lastAt = now;

  setState(() => pending++);
  _queue = _queue
      .then((_) => _processScan(code))
      .whenComplete(() => setState(() => pending--));
}
```

- Пока `pending > 0`, кнопка «Провести приход» **неактивна**.
- Во время проведения и при открытой модалке «Создать карточку» сканы от аппаратного сканера игнорируются.
- Звуки: `success` для IN_STOCK/IN_CATALOG, `unknown` для UNKNOWN, неоднозначного кода и ошибки.

### 3.2 Определение режима (один раз при открытии экрана)

```dart
// warehouseId = первый элемент GET /main/warehouses/ (массив или {results: []}).
// Ошибка или пустой список → warehouseId = '' (режим без склада).
serverMode = warehouseId.isNotEmpty;
```

Сканы, пришедшие до ответа, ждут этот запрос (`await modeReady`).

### 3.3 Классификация одного кода

```text
если serverMode:
    GET /warehouse/{warehouseId}/barcode-check/{code}/
      404/405/501  → serverMode = false, перейти к fallback (для всех следующих сканов тоже)
      200:
        ambiguous == true                   → ошибка «Найдено несколько товаров…»
        status IN_STOCK|IN_CATALOG + product.id → source = company, status как в ответе
        status UNKNOWN                      → проверить глобальную базу (шаг 3 fallback)
      409 + matches[]                      → ошибка «Найдено несколько товаров…»
      другое                                → ошибка «{code}: <текст ошибки>»

fallback (через /main/products/, склад не нужен):
  1. GET /main/products/warehouse-barcode/{code}/
       200 с id → IN_STOCK, source = company
       409 + matches / ambiguous → ошибка неоднозначности
       404 / «не найден» → шаг 2
       прочее → ошибка
  2. GET /main/products/list/?search={code}&page=1&page_size=50
       найти товар, у которого barcode == code ИЛИ code ∈ alternate_barcodes
       нашли → IN_STOCK, source = company
       ошибка запроса → считать «не нашли»
  3. GET /main/products/global-barcode/{code}/
       200 → IN_CATALOG, source = global (productId = null!)
       404 / «не найден» → шаг 4
  4. → UNKNOWN, source = none
```

> **Критично:** `id` из `global-barcode` — это `GlobalProduct`, а не товар компании. Не кладите его в `productId` и не отправляйте в приход.

«Не найден» = HTTP 404 **или** текст `detail`/`message`, содержащий «не найден» / «not found».

### 3.4 Создание карточки для UNKNOWN

Кнопка «Создать карточку» в строке списка UNKNOWN открывает модалку:

| Поле | Обязательно | Валидация |
|------|-------------|-----------|
| Штрихкод | — | read-only, из строки |
| Название | да | `trim()` не пустой, иначе «Укажите название товара» |
| Цена (необязательно) | нет | если заполнено: число ≥ 0, иначе «Некорректная цена» |

```http
POST /main/products/create-manual/
{ "barcode": "4601234567890", "name": "Чай", "price": "120", "quantity": 0 }
```

- `quantity: 0` **обязательно**: количество придёт приходом, иначе остаток задвоится.
- Ответ: товар (`id` в корне или в `product`). Если `id` нет, считать это ошибкой.
- Успех: строка переходит в IN_CATALOG с `source = company`, `productId = id`, `key = 'p:{id}'`, `stockQty = 0`, `price = initialPrice = введённая цена`. Количество строки сохраняется (если код сканировали несколько раз до создания).
- Ошибка показывается **внутри модалки**. Модалка не закрывается, кнопки на время запроса заблокированы.
- Отправка по Enter/«Готово» на клавиатуре = «Сохранить».

## 4. Цена

| Список | Колонка «Цена продажи» | Правило |
|--------|------------------------|---------|
| IN_STOCK | нет | цену не трогаем |
| IN_CATALOG, `source = global` | да, **обязательна** | placeholder «Цена *». Пусто при проведении → подсветить поле красным + ошибка «Укажите цену продажи для товаров из базы NurCRM». Предзаполнить `price` из `global-barcode`, если он есть |
| IN_CATALOG, `source = company` | да, необязательна | предзаполнена ценой карточки. Изменилась → `PATCH` перед приходом (§5.2) |

Любая непустая цена должна быть числом ≥ 0, иначе «{Название}: Некорректная цена». Клавиатура: `TextInputType.numberWithOptions(decimal: true)`, `,` → `.`.

## 5. «Провести приход»

Кнопка активна, если в IN_STOCK + IN_CATALOG есть строки и `pending == 0`. Строки UNKNOWN в приход **не идут** и остаются на экране. Строки с `quantity <= 0` пропускаются.

Порядок:

```text
0. Валидация (§4). Дождаться очереди сканов и определения режима.
0.5. Попробовать единый батч-запрос (§5.0). Успех → готово, шаги 1-4 не нужны.
     404/405/501 → эндпоинт не поддержан, перейти к шагам 1-4 (и не пробовать
     батч повторно до конца сессии экрана — иначе на каждое нажатие лишний запрос).
     Любая другая ошибка → показать, остановиться (ничего не менялось).
1. Для каждой строки source = global → создать карточку (5.1)
2. Для каждой строки с изменённой ценой → PATCH цены (5.2)
3. Схлопнуть строки с одинаковым productId (сложить quantity)
4. Приход: 5.3a (сервер) или 5.3b (без склада)
```

Работайте с **локальной копией** списка: шаги 2–4 зависят от `id`, полученных на шаге 1. Каждый успешный шаг сразу записывайте и в состояние экрана, чтобы при повторном нажатии после ошибки не создавать карточки заново.

### 5.0 Единый батч-запрос (приоритетный путь)

Пробовать **первым**, до шагов 1-4. Один запрос на все строки IN_STOCK + IN_CATALOG сразу — сервер одной транзакцией создаёт недостающие карточки, обновляет цены и приходует. Полная спецификация: [../backend/mass-incoming-batch.md](../backend/mass-incoming-batch.md).

```http
POST /main/products/mass-incoming/
{
  "comment": "Массовое сканирование",
  "items": [
    { "product_id": "uuid", "quantity": "10" },
    { "product_id": "uuid", "quantity": "3", "price": "150" },
    { "barcode": "4601234567890", "name": "Кофе", "price": "300", "quantity": "5", "from_global": true },
    { "barcode": "4601234567891", "name": "Скотч", "price": "120", "quantity": "2", "from_global": false }
  ]
}
```

- Элемент с `product_id` — существующая карточка (`quantity` **прибавляется** к остатку, `price` — только если отличается от текущей).
- Элемент без `product_id` (есть `barcode`/`name`/`price`/`quantity`/`from_global`) — карточки ещё нет, создать и сразу приходовать указанным остатком; `from_global: true` для товаров из глобальной базы NurCRM, `false` — ручное создание неизвестного кода.
- Успех (`2xx`) → убрать все отправленные строки из списка, закрыть экран. Всё, шаги 1-4 не выполняются.
- `404`/`405`/`501` → эндпоинт не задеплоен, выполнить шаги 1-4 как раньше; запомнить на экран (не пробовать §5.0 снова до его закрытия).
- Другая ошибка → показать пользователю, остановиться. По контракту это all-or-nothing: при ошибке в БД ничего не изменилось, значит и в списке ничего убирать не нужно.

### 5.1 Карточка из глобальной базы

```http
POST /main/products/create-by-barcode/
{ "barcode": "4601234567890", "name": "Кофе", "price": "300", "quantity": 0 }
```

- `404/405/501` → повторить тем же телом `POST /main/products/create-manual/`.
- Успех: `source = company`, `productId = id`, `key = 'p:{id}'`, `initialPrice = price`.
- Ошибка: ««{Название}»: <текст>», проведение **останавливается** (остатки ещё не менялись).

### 5.2 Изменённая цена

Только для `productId != null`, `price.trim()` не пустой и `price != initialPrice`:

```http
PATCH /main/products/{id}/
{ "price": "150" }
```

Успех: `initialPrice = price`. Ошибка: ««{Название}»: Не удалось обновить цену», стоп.

### 5.3a Атомарный приход (serverMode == true)

```http
POST /warehouse/{warehouseId}/mass-incoming/
{
  "items": [
    { "product_id": "uuid", "quantity": "10", "list": "IN_STOCK" },
    { "product_id": "uuid", "quantity": "3",  "list": "IN_CATALOG" }
  ],
  "comment": "Массовое сканирование"
}
```

- Все или ничего. Успех: убрать проведённые строки и закрыть экран (веб возвращает на `/crm/sklad`).
- `404/405/501` → `serverMode = false`, перейти к 5.3b.
- Другая ошибка: показать текст, строки не трогать (сервер откатил всё).
- `price` в `items` **не отправляем**: цена уже сохранена в карточке на шаге 5.1/5.2, а смысл поля `price` в `mass-incoming` бэкенд не зафиксировал.

### 5.3b Приход без склада (serverMode == false)

Типичный случай для маркета: складов в `/main/warehouses/` нет. Строки проводятся по одной, **последовательно**:

```text
для каждой строки (index i из N):
  GET   /main/products/{id}/                  → current = quantity (число, иначе 0)
  PATCH /main/products/{id}/  { "quantity": "<current + row.quantity>" }
  успех → запомнить key как проведённый
  ошибка →
     убрать из списка все уже проведённые строки
     показать «Проведено {i} из {N}. Ошибка на «{name}»: {reason}.
              Проведённые позиции убраны из списка — нажмите «Провести приход» ещё раз для остальных.»
     стоп
все успешно → убрать проведённые строки, закрыть экран
```

- Остаток **перечитывается** прямо перед `PATCH`, чтобы не затереть продажи, прошедшие между сканом и проведением. Нельзя брать `stockQty` из скана.
- Проведённые строки убираются **сразу**: повторное нажатие не должно задвоить остаток.
- Это не атомарная операция. При обрыве сети часть позиций будет проведена, и UI честно показывает, какая именно. Когда бэкенд начнёт принимать склад маркета в `mass-incoming`, клиент автоматически перейдёт на 5.3a.

## 6. Прочий UX

- Поле ввода с автофокусом: ручной ввод кода + Enter работает так же, как скан. После обработки поле очищается сразу, не дожидаясь ответа.
- В строках IN_STOCK/IN_CATALOG количество редактируется (число ≥ 0). В UNKNOWN количество не показывается («—»).
- IN_STOCK показывает текущий остаток (`stockQty`).
- «Удалить» в строке убирает её из списка. «Создать карточку» есть только в UNKNOWN.
- Закрытие экрана с непустым списком → confirm «У вас есть несохранённые данные. Закрыть?» (на Android также перехватывать системный «назад»).
- Ошибка скана не блокирует следующие: новый скан очищает текст ошибки.

| `fromGlobal` | из базы NurCRM |
| `priceRequired` | Цена * |
| `priceInvalid` | Некорректная цена |
| `priceRequiredForCatalog` | Укажите цену продажи для товаров из базы NurCRM |
| `priceUpdateFailed` | Не удалось обновить цену |
| `checking` | Проверка штрихкодов: {{count}} |
| `partialPosted` | Проведено {{done}} из {{total}}. Ошибка на «{{name}}»: {{reason}}. … |

Удалены: `warehouseNotFound`, `endpointMissing`: этих состояний больше нет.

## 8. Чек-лист приёмки для Flutter

- [ ] Маркет-компания без складов: скан известных товаров → «Провести приход» проходит, остатки на `/crm/sklad` выросли. Ошибки «Не найден склад компании» нет.
