## 1. E-kassa: сопоставление позиций чека с фискальными данными

### 1.1 Проблема

`GET /main/sales/json/{sale_id}/receipt/` отдаёт два независимых массива:

- `items[]` — построчные данные маркета (название, qty, `unit_price`, `line_discount`, `line_total`);
- фискальный блок `ekassa_fiscal.fields` / `ekassa.fields`, тег **1059** — массив позиций, которые реально ушли в фискальный регистратор (для налоговой) с кодами/суммами ФФД.

Для печати построчная скидка маркета накладывается на позицию 1059. Без стабильного общего id сопоставление идёт по индексу массива или по `name + qty` — при **двух одинаковых товарах с разными скидками** и несовпадающем порядке 1059 ↔ `items[]` скидка может «прилипнуть» не к той строке, потому что имя+qty не различает дубликаты.

### 1.2 Контракт (нужен от бэка)

Одно и то же значение id должно быть и в `items[]`, и в каждом объекте массива 1059:

```json
// items[]
{
  "item_id": "3f2c…",
  "name": "Кола",
  "qty": 1,
  "unit_price": "50.00",
  "line_discount": "5.00",
  "line_total": "45.00"
}
```

```json
// ekassa(_fiscal).fields → 1059[]
{
  "1030": "Кола",
  "1023": 1,
  "1076": 5000,
  "1043": 4500,
  "item_id": "3f2c…"
}
```

Допустимые имена id-поля (клиент читает все, в порядке приоритета): `item_id`, `line_id`, `sale_item_id`, `id` — это **id строки чека**, не `product_id`. Если id нельзя положить в официальный тег ФФД — допустимо vendor-поле рядом с 1030/1023/…, важно только совпадение значения с `items[]`.

**Нельзя** использовать как ключ сопоставления: `product_id`, штрихкод, только `name`.

### 1.3 Что должен делать данные о фискальных кодах — что шлёт клиент при создании позиции

Матчинг id — про печать уже готового чека. Отдельно от этого, при формировании позиции корзины/продажи бэк должен знать фискальную категорию товара (код группы ФФД, ставка НДС/налога и т.п.), чтобы корректно заполнить теги 1030/1076/1043/1043... в фискальном чеке. Это конфигурируется на карточке товара (категория → фискальный код), а не передаётся из Flutter построчно — клиент не должен пытаться подставлять код товара из фискального справочника вручную.

**Если у товара нет фискальной привязки** (нет сопоставления с кодом ФФД):

- фискализация чека по этой позиции может не пройти или пройти с дефолтным/родовым кодом (зависит от настройки бэка на конкретный момент — уточняется у бэка при внедрении);
- Flutter должен уметь показать предупреждение кассиру **до** финализации фискального чека, если бэк вернул признак отсутствия фискальной привязки (ошибка/warning в ответе checkout или отдельное поле на позиции, например `fiscal_code_missing: true` — уточнить точное имя поля у бэка при реализации);
- не блокировать обычную (нефискальную) продажу из-за отсутствия фискальной привязки, если у компании не включена интеграция с ККМ.

### 1.4 Поведение фронта (эталон для Flutter)

Приоритет матчинга:

1. совпадение `item_id` / `line_id` / `sale_item_id` / `id`;
2. по индексу массива (только если длины `items[]` и 1059 совпадают);
3. `name + qty` (только если длины разные) — самый ненадёжный, различает дубликаты неверно.

```dart
String? _stableId(Map<String, dynamic> item) =>
    item['item_id']?.toString() ??
    item['line_id']?.toString() ??
    item['sale_item_id']?.toString() ??
    item['id']?.toString();

List<MatchedReceiptLine> matchReceiptItems({
  required List<Map<String, dynamic>> items,
  required List<Map<String, dynamic>> fiscalFields1059,
}) {
  final itemIds = items.map(_stableId).toList();
  final fiscalIds = fiscalFields1059.map(_stableId).toList();

  final hasStableIds = itemIds.every((id) => id != null) &&
      fiscalIds.every((id) => id != null);

  if (hasStableIds) {
    return items.map((item) {
      final id = _stableId(item);
      final fiscal = fiscalFields1059.firstWhere(
        (f) => _stableId(f) == id,
        orElse: () => const {},
      );
      return MatchedReceiptLine(item: item, fiscal: fiscal);
    }).toList();
  }

  if (items.length == fiscalFields1059.length) {
    // fallback: по индексу
    return List.generate(
      items.length,
      (i) => MatchedReceiptLine(item: items[i], fiscal: fiscalFields1059[i]),
    );
  }

  // fallback: name + qty — залогировать предупреждение, печать не блокировать
  debugPrint('receipt matching fallback: name+qty (ненадёжно для дублей)');
  return items.map((item) {
    final fiscal = fiscalFields1059.firstWhere(
      (f) => f['1030'] == item['name'] && f['1023'] == item['qty'],
      orElse: () => const {},
    );
    return MatchedReceiptLine(item: item, fiscal: fiscal);
  }).toList();
}
```

При фолбэке на `name+qty`, или если Σ построчных скидок расходится с order-level `discount`, — только предупреждение в лог (`console.warn`-эквивалент), **не** блокировать печать.

### 1.5 Приёмка

| # | Данные | Ожидание |
|---|--------|----------|
| 1 | Две «Кола», скидки 5 и 20, порядок 1059 обратный `items`, у обеих есть `item_id` | скидки на печати соответствуют правильному `item_id` |
| 2 | Нет id-полей, длины массивов равны | merge по индексу |
| 3 | Нет id-полей, длины разные | fallback `name+qty` + warn в логе, печать не блокируется |

## 2. Флаг ручного изменения цены

### 2.1 Отличие от discount (важно не путать с §receipt-price-edit-discount.md)

[receipt-price-edit-discount.md](./receipt-price-edit-discount.md) описывает **числовой контракт**: `unit_price` — фактическая цена продажи, `discount`/`line_discount` — только явная скидка, никогда не выводится из разницы цен.

Этот раздел — про **отдельный булевый/строковый флаг**, который явно маркирует происхождение расхождения между каталожной ценой и `unit_price`, когда бэк ещё не гарантирует корректность числового контракта (старые ответы, переходный период). Флаг и `discount` — независимые сигналы:

| | Что кодирует | Источник значения |
|---|---|---|
| **`discount` / `line_discount`** | Сумму скидки в валюте | Явное поле, установленное через `discount_total` |
| **`price_manually_edited`** (или `price_override_reason`) | Факт того, что кассир вручную поменял `unit_price`, а не факт наличия скидки | Булев/enum-флаг, отдельный от суммы |

Они нужны раздельно, потому что расчёт скидки (сумма) и причина расхождения цены (ручной ввод vs настоящая скидка) — разные вопросы: сумма скидки может быть равна нулю при ручной цене, а флаг всё равно должен быть `true`, чтобы клиент **не** пытался вывести псевдоскидку из разницы `catalog_price − unit_price`.

### 2.2 Контракт полей (нужен от бэка, один из двух вариантов)

На каждой позиции `items[]` в `/main/sales/json/{id}/receipt/` **и** в printable payload `POST /main/pos/sales/{id}/checkout/` (если там есть `items`):

**Вариант A (предпочтительный):**

```json
{
  "name": "Лемонад Kt",
  "qty": 1,
  "unit_price": 230.0,
  "line_discount": 0.0,
  "line_total": 230.0,
  "price_manually_edited": true
}
```

| Поле | Тип | Смысл |
|------|-----|-------|
| `price_manually_edited` | `bool` | `true` — кассир менял `unit_price` вручную; `false`/отсутствует — цена как в каталоге или расхождение объясняется скидкой |

**Вариант B:**

```json
{ "price_override_reason": "manual" }
```

| Значение | Смысл |
|----------|-------|
| `"manual"` | ручная цена — расхождение с каталогом **не** печатать как скидку |
| `"discount"` | расхождение — настоящая скидка |
| `null` / нет поля | поведение по умолчанию (ориентироваться на явные поля скидки) |

### 2.3 Когда флаг выставляется

- Устанавливается бэком в момент `PATCH /main/pos/carts/{cart_id}/items/{item_id}/` с телом `{ "unit_price": "..." }` (см. [receipt-price-edit-discount.md §2](./receipt-price-edit-discount.md#2-две-независимые-операции-на-клиенте)).
- **Не** устанавливается (или `false`) при изменении через `discount_total` / `order_discount_total` / `order_discount_percent`.
- Сохраняется на строке чека до печати/повторной печати — не пересчитывается на клиенте.

### 2.4 Как отображается на чеке / в отчётах

- На печатном чеке и в предпросмотре: если флаг `true` — строка скидки **не** выводится для этой позиции, даже если `unit_price` отличается от каталожной цены. Печатается только явный `line_discount`/`discount_total`.
- В UI строки корзины на кассе — ручная цена показывается как «Цена изменена», не как «Скидка» (см. также [receipt-price-edit-discount.md §6](./receipt-price-edit-discount.md#6-ui-кассы)).
- В отчётах/аналитике по скидкам позиция с `price_manually_edited: true` и `line_discount: 0` **не** должна попадать в суммы «скидки», иначе аналитика скидок исказится ручными изменениями цены.

### 2.5 Поведение клиента

```dart
bool isPriceManuallyEdited(Map<String, dynamic> item) {
  if (item['price_manually_edited'] == true) return true;
  if (item['price_override_reason'] == 'manual') return true;
  return false;
}

double? inferredLegacyDiscount(Map<String, dynamic> item, double catalogPrice) {
  // Эвристика — ТОЛЬКО для старых ответов без флага.
  if (isPriceManuallyEdited(item)) return null;
  final unitPrice = (item['unit_price'] as num).toDouble();
  final lineDiscount = (item['line_discount'] as num?)?.toDouble() ?? 0;
  if (lineDiscount > 0) return null; // скидка уже явная
  final gap = catalogPrice - unitPrice;
  return gap > 0.01 ? gap : null; // документированный риск для старых клиентов
}
```

1. Если `price_manually_edited === true` или `price_override_reason === "manual"` → **не** вызывать эвристику вывода скидки из разницы цен.
2. Печатать только явный `line_discount` / `discount_total`.
3. Эвристику держать как fallback только для старых ответов без флага (переходный период до раскатки бэка).

### 2.6 Приёмка

| # | Действия | Ожидание в JSON | Ожидание на чеке |
|---|----------|------------------|-------------------|
| 1 | Цена 250→230, скидок нет | `unit_price: 230`, `line_discount: 0`, `price_manually_edited: true` | нет строки скидки, итог 230 |
| 2 | Цена 250, скидка строки 20 | `line_discount: 20`, флаг `false`/нет | скидка 20 |
| 3 | Старый ответ без флага | как раньше | эвристика (документированный риск, только временно) |

## 3. Весовые товары — чек и фискализация

Базовые эндпоинты (список весовых, экспорт на весы, токен интеграции, настройки штрихкода) уже описаны в [products-catalog.md §5 «Весы / PLU»](./products-catalog.md#5-весы--plu) — здесь **не дублируются**. Ниже — то, что нужно для генерации строки чека и фискализации весовой позиции.

### 3.1 Формат штрихкода весов (декодирование)

Компания настраивает раскладку и режим через `GET/PATCH /users/settings/company/`:

| Поле | Значения | Назначение |
|------|----------|------------|
| `scale_barcode_layout` | `plu` \| `code` | Как извлекать идентификатор товара из штрихкода |
| `scale_barcode_mode` | `auto` \| `weight` \| `amount` | Как интерпретировать встроенное числовое значение |

**Раскладка `plu`:** `префикс(2) + PLU(5) + значение(5) + контрольная(1)` — итого 13 цифр (EAN-13-совместимо).

**Раскладка `code`:** `префикс(2) + внутренний код(6) + вес(4) + контрольная(1)`.

**Режимы значения:**

| Режим | Поведение |
|-------|-----------|
| `auto` | Префикс `20` → значение = вес в граммах; префикс `25` → значение = сумма в сомах × 100 |
| `weight` | Значение всегда в граммах → `qty = value / 1000` (кг) |
| `amount` | Значение всегда в сомах × 100 → `qty` пересчитывается делением суммы на цену товара |

Пример: этикетка `2100100001452`, PLU товара = `1`, реальный вес = 0.145 кг:

| layout | Результат |
|--------|-----------|
| `plu` | PLU, извлечённый как `100` — **не совпадает** с товаром |
| `code` | внутренний код `001000` → PLU `1`, вес `0145` г = 0.145 кг — **верно** |

Для весов Rongta RLS (префикс `21`) обычно нужна связка `layout=code` + `mode=weight`. Это конфигурация компании, а не выбор конкретного чека — Flutter **не** декодирует штрихкод сам, а передаёт «как есть» в `scan` (см. §3.2); декодирование выполняет бэк по текущим настройкам компании.

### 3.2 Формирование строки чека при сканировании весового штрихкода

```http
POST /main/pos/sales/{sale_id}/scan/
```

```json
{ "barcode": "2100100001452" }
```

Один и тот же эндпоинт обрабатывает и обычные, и весовые штрихкоды — Flutter не должен предварительно определять тип штрихкода на клиенте. Бэк:

1. определяет, что штрихкод весовой (по длине/префиксу);
2. разбирает его по `scale_barcode_layout` + `scale_barcode_mode` текущей компании;
3. находит товар по `plu` (layout `plu`) или по внутреннему коду (layout `code`);
4. добавляет позицию в корзину с `quantity` = извлечённый вес в кг, либо количеством, пересчитанным из суммы (`mode=amount`);
5. если PLU/код в штрихкоде не найден в системе — ошибка (HTTP 4xx с `detail`), позиция в корзину не добавляется.

```dart
Future<void> onScaleBarcodeScanned(String saleId, String rawBarcode) async {
  // Клиент НЕ парсит штрихкод сам — только передаёт как есть.
  final response = await api.post(
    '/main/pos/sales/$saleId/scan/',
    body: {'barcode': rawBarcode},
  );
  if (response.isError) {
    Notify.error(response.detail ?? 'Товар по весовому штрихкоду не найден');
    return;
  }
  cartRepo.applyScanResult(response.data);
}
```

### 3.3 Дробное количество и округление на чеке

- `qty` весовой позиции — дробное число (кг), не округляется до целого при отображении строки чека; при печати использовать то же количество знаков после запятой, что вернул бэк для `qty` (обычно 3 знака, граммы).
- `line_total = unit_price × qty`, округление суммы строки — до 2 знаков (копейки/тыйын), как и для штучных товаров; округление количества **не** производится отдельно клиентом — бэк уже прислал финальный `qty`.
- Ручное редактирование `qty` весовой позиции на кассе (например, довес/коррекция) идёт тем же `PATCH .../items/{item_id}/`, что и для обычных товаров — контракт `unit_price`/`discount_total` из [receipt-price-edit-discount.md](./receipt-price-edit-discount.md) действует одинаково для весовых и штучных строк.
- Фискализация (тег 1023 — количество) весовой позиции передаёт дробное количество как есть; Flutter не должен округлять `qty` до целого перед печатью или перед чтением фискального блока — это исказит соответствие 1059 ↔ `items[]` (см. §1).

## 4. Чеклист Flutter

### E-kassa matching

- [ ] Матчинг `items[]` ↔ 1059 по приоритету: `item_id`/`line_id`/`sale_item_id`/`id` → индекс (равные длины) → `name+qty`
- [ ] Не использовать `product_id`/штрихкод/только имя как уникальный ключ матчинга
- [ ] При фолбэке на `name+qty` или расхождении Σ построчных скидок с order-level `discount` — только warn в лог, печать не блокировать
- [ ] Показать предупреждение кассиру, если бэк вернул признак отсутствия фискальной привязки товара (точное имя поля уточнить у бэка)

### Флаг ручной цены

- [ ] Читать `price_manually_edited` (bool) и/или `price_override_reason` (`"manual"`/`"discount"`/null)
- [ ] Если флаг говорит «ручная цена» — не выводить псевдоскидку из разницы цен, печатать только явный `line_discount`
- [ ] Эвристику вывода скидки держать только как fallback для старых ответов без флага
- [ ] В UI строки — ручная цена отображается как «Цена изменена», не как «Скидка»
- [ ] Позиции с `price_manually_edited: true` и `line_discount: 0` не считать «скидкой» в клиентской аналитике

### Весовые товары

- [ ] Базовые эндпоинты весов — по [products-catalog.md §5](./products-catalog.md#5-весы--plu)
