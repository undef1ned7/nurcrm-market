## 1. «Оплатить весь долг» (bulk pay)

### 1.1 Реального bulk-эндпоинта нет

`POST .../deals/{dealId}/pay-all/` — это **предложение** бэку в доке, endpoint **не реализован**. Веб сегодня делает это циклом по уже существующему `pay/`. Flutter должен повторить тот же паттерн — не рассчитывать на `pay-all/`, пока бэк явно не подтвердит его существование.

### 1.2 Как это работает на вебе (повторить 1:1)

Кнопка «Оплатить весь долг (N сом)» показывается, когда есть хотя бы один неоплаченный/частично оплаченный взнос. По подтверждению — **последовательный** цикл вызовов существующего контракта оплаты взноса:

```http
POST /main/clients/{clientId}/deals/{dealId}/pay/
```

```json
{
  "idempotency_key": "<новый uuid на каждый вызов>",
  "installment_id": "<installment uuid>",
  "date": "2026-09-04"
}
```

Правила:

1. Перебирать только незакрытые взносы — фильтр по `paid_on == null` или `paid_amount < amount`, отсортированные по `due_date` ASC (от раннего к позднему).
2. `amount` не передавать — как при обычной оплате «на всю сумму взноса» (см. §5.6 п.5 в [client-debt-and-kpis.md](./client-debt-and-kpis.md)).
3. Новый `idempotency_key` (UUID) на **каждый** вызов цикла, не один на всю операцию.
4. Если долг длинный (ежедневный график на 30/60/90 платежей) — это N последовательных HTTP-запросов, может занять десятки секунд на слабом интернете. Показывать прогресс («Оплачено X из N»).
5. Если один из вызовов упал (сеть/сервер) — **остановить цикл**, показать «Оплачено X из N платежей», дать кнопку «Повторить». Уже оплаченные взносы **не** пересылать повторно при повторном нажатии (фильтруются по `paid_on`/остатку, см. п.1).
6. Операция **не атомарна**: частичный успех — ожидаемое и приемлемое поведение (как на вебе), не баг.
7. После каждого успешного вызова — тот же post-обработчик кэшфлоу, что и у одиночной оплаты по кнопке в строке графика (см. [cash-and-cashflows.md](./cash-and-cashflows.md) §6 `postCashflowIfNeeded`, если `BE_CASHFLOWS=false`).
8. По завершении (полном или частичном) — `GET` deal заново + обновить KPI карточки клиента.

### 1.3 Отличие от оплаты одного взноса

| | Оплата одного взноса | «Оплатить весь долг» |
|---|---|---|
| Запросов | 1 | N (по числу незакрытых взносов) |
| `installment_id` | конкретный | цикл по каждому незакрытому |
| Атомарность | одна операция | нет — частичный успех возможен |
| `idempotency_key` | один | новый на каждый вызов внутри цикла |
| Кассовые движения | 1 запись | до N записей (по одной на взнос), если бэк не выключит через будущий `pay-all/` |

### 1.4 Если бэк добавит `pay-all/`

Предложенный (не подтверждённый) контракт из дока:

```http
POST /main/clients/{clientId}/deals/{dealId}/pay-all/
```

```json
{
  "idempotency_key": "<uuid>",
  "date": "2026-09-04",
  "amount": "1234.56"
}
```

`amount` опционален — без него гасится весь `remaining_debt`. Ожидаемое поведение: распределение от самого раннего взноса к позднему, одна транзакция (all-or-nothing), `amount > remaining_debt` → 400, идемпотентность по `idempotency_key`. **Не реализовывать на Flutter, пока бэк не подтвердит наличие этого эндпоинта** — до тех пор использовать цикл из §1.2.

## 2. Способ оплаты при погашении долга

### 2.1 Множество значений

```
"cash" | "mbank" | "optima" | "obank" | "bakai" | "demir" | "other" | "transfer"
```

Совпадает с конвенцией checkout на кассе (см. [cash-and-cashflows.md](./cash-and-cashflows.md) §9.1). По умолчанию — `"cash"`. Поле **необязательное**: отсутствие трактуется бэком (ожидаемо) как `cash` — текущее поведение до появления поля.

### 2.2 Долг v1 — `PATCH /main/debts/{id}/`

```json
{
  "amount": "500.00",
  "payment_method": "mbank",
  "cashbox_role": "...",
  "branch_id": "...",
  "shift_id": "..."
}
```

`amount` — новый остаток долга (как раньше, без изменений семантики). `payment_method` — только новое поле.

### 2.3 Долг v2 — `POST /main/clients/{clientId}/deals/{dealId}/pay/`

```json
{
  "idempotency_key": "<uuid>",
  "installment_id": "<installment uuid>",
  "date": "2026-09-07",
  "amount": "300.00",
  "payment_method": "cash",
  "cashbox_role": "...",
  "branch_id": "...",
  "shift_id": "..."
}
```

- Для клиента — `income`, POS-маршрутизация (`buildPosRoutingFromUser`).
- Для поставщика (`clientType = suppliers`) — `expense`, `cashbox_role: expense_variable`, **без** `shift_id` (не влияет на смену).
- В «Оплатить весь долг» (§1) — один и тот же `payment_method` передаётся в **каждый** вызов цикла.

### 2.4 Маршрутизация прихода по способу оплаты (когда `AUTO_CASHFLOWS=true` на бэке)

| `payment_method` | Куда идёт приход | Влияет на `drawer_expected_cash` смены |
|---|---|---|
| `cash` | наличная касса смены (drawer) | **да** |
| `mbank` / `optima` / `obank` / `bakai` / `demir` / `other` / `transfer` | безналичная касса | **нет** |

Логика идентична правилу для продаж (см. [cash-and-cashflows.md](./cash-and-cashflows.md) §10.2 «золотой кейс сверки») — перевод в счёт долга не должен раздувать ожидаемую наличность в ящике при закрытии смены.

### 2.5 Что подтверждено, что нет

Документ `debt-payment-method-backend.md` оставляет **6 открытых вопросов бэку (D1–D6)**: есть ли у долга v1 отдельная таблица платежей, трактует ли бэк неизвестный `payment_method` как `transfer`, берёт ли бэк маршрутизацию на себя при `AUTO_CASHFLOWS=true` или ждёт от фронта `postCashflowIfNeeded`, нужен ли отдельный `bank`-параметр, поддерживается ли атрибуция по банку в отчётах, сохраняется ли `payment_method` на уровне взноса в v2. **На дату написания ответов в репозитории нет.**

Практическое следствие для Flutter:

- Поле слать можно уже сейчас — оно не блокер: старый бэк его проигнорирует, погашение пройдёт как раньше (наличными).
- **Не полагаться** на то, что `payment_breakdown` при закрытии смены или отчёты по кассе корректно учитывают способ оплаты долга, пока не подтверждено тестом на актуальном стенде (staging/prod). Если разбивка «нал/безнал» после погашения долга переводом ошибочно увеличивает наличность — это признак того, что D3 ещё не реализован бэком.
- Если критично для релиза — проверить вручную: погасить долг переводом (`mbank`), закрыть смену, сверить `drawer_expected_cash` — он не должен вырасти на сумму погашения.

## 3. Риск: v2-график может быть пересчитан бэком по v1

### 3.1 Известный баг (зафиксирован 2026-08-31)

На stage-стенде на дату фиксации бага бэкенд **принимал v2-payload без 400**, но **create-path вызывал legacy v1-генератор графика**, игнорируя `schedule_version: "v2"`, `interval_days`, `first_due_date` и явный `installments[]`. Пример:

Отправили (v2, 7 платежей раз в 2 дня):

```json
{
  "amount": "200.00",
  "debt_days": 7,
  "interval_days": 2,
  "first_due_date": "2026-09-01",
  "schedule_version": "v2",
  "installments": [
    { "number": 1, "amount": "28.57", "due_date": "2026-09-01" }
  ]
}
```

Получили в ответ (фактически v1: 1 платёж через 30 дней):

```json
{
  "schedule_version": "v1",
  "debt_days": 30,
  "interval_days": 1,
  "first_due_date": null,
  "daily_payment": "6.67",
  "installments": [
    { "number": 1, "due_date": "2026-09-30", "amount": "200.00" }
  ]
}
```

Расхождение по каждому ключевому полю:

| Поле | Отправили (v2) | Получили (баг) |
|---|---|---|
| `schedule_version` | `"v2"` | `"v1"` |
| `debt_days` (= число платежей в v2!) | `7` | `30` (legacy default) |
| `interval_days` | `2` | `1` |
| `first_due_date` | `"2026-09-01"` | `null` |
| `installments.length` | `7` | `1` |
| 1-й взнос | `28.57` / `2026-09-01` | `200.00` / `2026-09-30` |

### 3.2 Почему это опасно молча

- HTTP-статус **201**, никакой ошибки — приложение не узнает о проблеме само по себе.
- Клиент/кассир видит на экране один график (превью на кассе, посчитанный локально по формуле из [debt-installment-schedule.md](./debt-installment-schedule.md) §6), а сервер хранит **другой**. При следующем `GET` карточки долга покажется расхождение — уже после того, как касса закрыла чек и кассир ушёл к следующему клиенту.
- Затрагивает реальные деньги и сроки — просрочка будет считаться по неверной дате.

### 3.3 ОБЯЗАТЕЛЬНО: перепроверить перед релизом, не доверять спеке на слово

`docs/backend/kassa/debt-v2-backend-implementation.md` — это **implementation guide с ожидаемым поведением и тест-кейсами**, написанный для бэкенд-команды. Наличие этого документа **не означает, что бэк уже исправлен** на текущем staging/prod. Дата фиксации бага — 2026-08-31; на момент написания этого файла (2026-09-11) статус фикса на актуальном стенде **не подтверждён в репозитории nur-market**.

**Перед тем как Flutter полагается на v2-график в проде — обязательно выполнить ручную проверку на том backend-инстансе, к которому будет ходить прод-сборка:**

1. `GET /main/pos/cashier-settings/` — убедиться, что `debt_schedule_version` вообще выставляется в `"v2"` для тестовой компании (либо просто слать `schedule_version: "v2"` явно в теле, не полагаясь на настройки).
2. Создать тестовый долг с параметрами, которые **не совпадают** с legacy-дефолтом (30 дней, 1 платёж), например:
   ```json
   {
     "kind": "debt",
     "amount": "100.00",
     "debt_days": 3,
     "interval_days": 5,
     "first_due_date": "2026-10-01",
     "schedule_version": "v2",
     "auto_schedule": true
   }
   ```
   Ключевое условие теста: `interval_days` ≠ 1 и ≠ 30, `debt_days` (число платежей) ≠ 1, `first_due_date` — конкретная дата, отличная от «сегодня + 30».
3. Прочитать ответ **этого же POST** (201) — если `schedule_version` вернулся `"v1"`, или `installments.length == 1`, или `first_due_date == null` — баг **всё ещё жив**.
4. Отдельно перепроверить через `GET /main/clients/{id}/deals/{deal_id}/` — что график, отданный на чтении, совпадает с тем, что было в ответе на POST (бэк не должен «на лету» превращать v2 обратно в v1 при повторном чтении).
5. Сверить: `installments[]` содержит именно `debt_days` (3) записей с шагом `interval_days` (5) от `first_due_date`, а не один платёж на `amount / 30`.
6. Если тест не прошёл — v2-график **не готов** на этом стенде: держать `debt_schedule_version` = `v1` (или дефолт кассы) для прод-сборки Flutter, пока бэк не подтвердит фикс; сообщить об этом в канал синка с бэком, сославшись на P0-чеклист из `debt-v2-backend-implementation.md` §10.
7. Регресс-тест повторять при каждом обновлении backend build/deploy к которому цепляется прод-сборка — фикс мог быть внесён на одном стенде и не докатан на другой.

### 3.4 Итог для Flutter

- Не включать v2-график как основной путь в проде **на основании одного лишь чтения этой документации**.
- Признак живого бага — быстрый смок-тест: POST с `interval_days` ≠ 1 и явным `first_due_date`, затем сверка ответа. Если `debt_days` в ответе стал `30`, а `installments.length == 1` — это тот же баг.
- Полный контракт полей v1/v2 (какие слать, какие не слать, формула деления копеек) — в [debt-installment-schedule.md](./debt-installment-schedule.md), этот файл его не повторяет.

## 4. Чеклист Flutter

**«Оплатить весь долг»**

- [ ] Реализовано циклом по `pay/`, а не через `pay-all/` (эндпоинта нет)
- [ ] Новый `idempotency_key` на каждый вызов внутри цикла
- [ ] Взносы гасятся по возрастанию `due_date`, уже оплаченные — пропускаются
- [ ] `amount` не передаётся (гасим весь остаток взноса)
- [ ] При обрыве цикла — «Оплачено X из N», повторное нажатие продолжает с незакрытых
- [ ] После завершения (полного/частичного) — обновить deal + KPI карточки клиента

**Способ оплаты**

- [ ] `payment_method` шлётся и в PATCH v1 (`/main/debts/{id}/`), и в POST v2 (`.../pay/`)
- [ ] Значение по умолчанию — `"cash"`, поле необязательное
- [ ] Один и тот же `payment_method` во всех вызовах цикла «оплатить весь долг»
- [ ] Не считать `payment_breakdown`/сверку смены надёжной для долговых погашений без ручной проверки на актуальном бэке (D1–D6 открыты)

**v2-график — риск**

- [ ] Перед релизом v2 на прод выполнен ручной смок-тест из §3.3 на **актуальном** backend-инстансе (не по факту существования спеки)
- [ ] Тест повторяется при каждом новом деплое бэка, к которому цепляется прод-сборка
- [ ] Если баг жив — держать `debt_schedule_version = v1` для прод-сборки, эскалировать в бэк-команду
