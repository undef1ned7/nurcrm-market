# Модуль 5. Денежный ящик (Zadig / ESC-POS)

## 5.1 Цель

Кассир/владелец настраивает автоматическое и ручное открытие денежного ящика через ESC/POS kick-команду по уже подключённому чековому принтеру (WebUSB).

## 5.2 Текущее состояние

| Есть | Нет |
|------|-----|
| `src/pages/sell/ui/services/printService.ts` (+ `print/*`) — WebUSB, ESC/POS чеки | Kick ящика, UI настроек ящика |
| `localStorage` ключи `escpos_*` (vid/pid/font/cp/…) | Флаги `drawer_*` |
| `/crm/pos-print-settings` → `PosPrintSettings.tsx` | Блок «Денежный ящик» |
| Упоминание Zadig в ошибках USB (`print/usb.ts`) | Отдельный printer-bridge для market POS (bridge — cafe) |

## 5.3 Требования (FE only)

### Настройки (`/crm/pos-print-settings`)

- Секция **«Денежный ящик»**:
  - Тумблер «Открывать при печати чека» (default: off)
  - Выбор тайминга: **до** печати / **после** печати
  - Поле «ESC/POS команда» — список байт через запятую  
    Default: `27, 112, 0, 25, 250` (`ESC p m t1 t2`)
  - Валидация: только целые 0–255, непустой список
  - Кнопка **«Проверить открывание ящика»** — шлёт только kick, без чека
- Подсказка: на Windows для WebUSB нужен Zadig/WinUSB (как в текущих USB-ошибках). **Не** обещать printer-bridge для market POS.

### Хранение (MVP)

localStorage на устройстве кассы (как остальные `escpos_*`):

| Ключ | Тип | Описание |
|------|-----|----------|
| `escpos_drawer_enabled` | `"1"` / отсутствует | Открывать при печати |
| `escpos_drawer_when` | `"before"` \| `"after"` | Тайминг |
| `escpos_drawer_cmd` | string | Байты через запятую |

Серверные настройки — **вне MVP** (фаза 2, по желанию).

### Поведение при печати

В цепочке `handleCheckoutResponseForPrinting` / печати чека:

1. Если drawer disabled → как сейчас.
2. Если `before` → kick → печать чека.
3. Если `after` → печать чека → kick.
4. Ошибка kick **не должна** отменять уже успешный checkout; показать предупреждение в UI/toast.
5. Ошибка печати чека при `before`: kick уже мог сработать — допустимо; не ретраить kick автоматически.

### Техническая реализация

- Добавить в `printService` публичный метод, напр. `kickCashDrawer(bytes?: number[]): Promise<void>`.
- Низкоуровнево: собрать `Uint8Array` и отправить через существующий USB `transferOut` (тот же канал, что чек).
- Не тащить cafe `printer-bridge`, если только WebUSB-принтер.

## 5.4 Критерии приёмки

- [ ] В Pos Print Settings видна секция ящика; настройки переживают reload.
- [ ] «Проверить» открывает ящик при подключённом принтере (или показывает понятную ошибку USB).
- [ ] При включённом тумблере kick выполняется с выбранным таймингом при печати чека продажи.
- [ ] Невалидная команда не уходит на устройство; UI показывает ошибку валидации.
- [ ] Backend не требуется.

## 5.5 Вне scope

- Денежный ящик без принтера (отдельный COM/RJ11 без ESC/POS).
- Синхронизация настроек ящика между кассами через API.

# Модуль 3. Второй экран покупателя

## 3.1 Цель

На втором мониторе покупатель видит: режим ожидания, состав корзины и итог, экран «Спасибо» после оплаты. Управление — с основной кассы.

## 3.2 Текущее состояние

Реализации нет: нет route, BroadcastChannel, тумблера в настройках кассы.

Касса: `/crm/market/cashier` (`src/pages/cashier/...`), multi-cart (`useMarketCashierMultiCart`), оплата (`usePaymentPage`).

## 3.3 Требования FE (MVP)

### Настройки кассы

В существующих настройках кассира / вкладке «Касса»:

- Тумблер **«Включить второй экран»**
- Кнопка **«Открыть окно»** → `window.open` на dedicated route

Хранение MVP: `localStorage` (`market_customer_display_enabled` и т.п.).

### Route / окно

- Отдельный route, напр. `/crm/market/customer-display` (без sidebar/header или с минимальным chrome).
- Окно рассчитано на полноэкранный второй монитор; крупные шрифты, высокий контраст.
- Auth: либо тот же session cookie/token (same-origin), либо публичный display-mode **только** при наличии валидной сессии кассы. Не открывать CRM-меню покупателю.

### Синхронизация

Источник истины — **основное окно кассы**.

Канал MVP: `BroadcastChannel('nur-market-customer-display')` + fallback `storage` event.

Сообщения (черновик контракта):

```ts
type CustomerDisplayMessage =
  | { type: "hello"; logoUrl?: string; welcomeText?: string }
  | { type: "idle"; slides?: { imageUrl: string; caption?: string }[] }
  | {
      type: "cart";
      cartId?: string;
      items: {
        name: string;
        qty: number;
        price: number;
        discount?: number;
        lineTotal: number;
      }[];
      subtotal: number;
      discountTotal?: number;
      total: number;
      currency?: string;
    }
  | { type: "thanks"; total?: number; durationMs?: number }
  | { type: "clear" };
```

Правила:

- При смене активной корзины (multi-cart) второй экран показывает **активную** корзину.
- После успешной оплаты → `thanks` → через N сек (default 5) → `idle`.
- Если второе окно закрыто / канал недоступен — касса работает без ошибок.

### Режимы UI

1. **Ожидание:** логотип компании (из `company`), приветствие, опциональный слайдер (localStorage URLs или статичные ассеты).
2. **Корзина:** список позиций, кол-во, цена, скидка строки, крупный итог.
3. **Завершение:** «Спасибо за покупку!» + сумма.

### Backend (опционально, фаза 2)

| Задача | Когда |
|--------|-------|
| Сохранение welcome/slides на сервере | Общие настройки на сеть магазинов |
| QR на оплату | Только при готовой платёжной интеграции |

## 3.4 Критерии приёмки

- [ ] Из кассы открывается второе окно; без тумблера кнопка недоступна или скрыта.
- [ ] Добавление/удаление/скидка на кассе отражаются на втором экране ≤ 300 ms при том же origin.
- [ ] После оплаты — «Спасибо», затем idle.
- [ ] Закрытие второго окна не ломает кассу.
- [ ] Нет QR и серверных слайдов в MVP.

## 3.5 Риски

- Multi-cart: подписаться на тот же active cart, что UI кассира.
- Не тащить секреты (токены, пароль кассира) в payload второго экрана.
- Deferred/долг: показывать итог чека как на кассе; не изобретать отдельный расчёт долга.

# Модуль 4. Горячие клавиши быстрых продаж (F3 + 0..9)

## 4.1 Цель

`F3`, затем цифра `0..9` (в т.ч. Numpad) → **+1** заранее привязанного товара в активную корзину. Конструктор привязок на кассе. Бейджи `[F3+N]` на кнопках быстрых товаров.

## 4.2 Текущее состояние (конфликт)

Уже реализовано:

- У товара поле `hotkey_group` = `F1`…`F12`.
- На кассе нажатие F1–F12 открывает **модалку группы** (`useCashierProducts.ts` → `openHotkeyProductsModal`), список через `GET /main/products/list/?group=F…`.
- Паттерн: `HOTKEY_GROUP_PATTERN = /^F(?:[1-9]|1[0-2])$/` в `cashierPage.constants.ts`.

**F3 уже занят** под открытие группы F3. Модель ТЗ (chord → сразу в чек) ≠ текущая (F-key → модалка).

## 4.3 Гейт (обязателен до разработки)

Зафиксировать одно продуктовое решение письменно:

| Вариант | Поведение | Плюсы / минусы |
|---------|-----------|----------------|
| **A. Дополнить** | F3 один раз → режим ожидания цифры 1.5–2 с; F3+цифра → слот. Одиночный F3 **больше не** открывает группу (или открывает по F3+Enter) | Ближе к ТЗ; ломает привычку «F3 = группа» |
| **B. Заменить F1–F12** | Убрать группы; только 10 слотов F3+0..9 | Проще UX; миграция данных групп |
| **C. Другая клавиша** | Chord на F9 / `` ` `` / отдельная кнопка «Быстрый слот» | Нет конфликта с F3-группой |
| **D. Chord внутри** | F3 открывает группу как сейчас; слоты 0–9 — **другие** биндинги (Ctrl+Digit) | Меньше ломает; дальше от формулировки ТЗ |

**Блокер:** не мержить UI слотов, пока не выбран вариант (рекомендация инженерии: **A** или **C**).

## 4.4 Требования FE (MVP после гейта)

Предположение ниже — **вариант A**.

1. `keydown` capture: `F3` → `preventDefault`, войти в режим `awaitingDigit` на 2000 ms (визуальный индикатор на кассе).
2. Пока режим активен: `0–9` / Numpad0–9 → найти `productId` слота → добавить qty+1 в активную корзину (тот же путь, что скан/быстрый товар).
3. Повторный F3 в режиме — сброс или продление таймера (зафиксировать одно).
4. Если слот пуст — toast «Слот N не назначен».
5. Конструктор: UI «Слоты быстрых товаров» — 10 ячеек, выбор товара из поиска/каталога, очистка слота.
6. Бейджи `[F3+N]` на соответствующих кнопках быстрых товаров (если товар в слоте).
7. Хранение MVP: `localStorage` ключ вида `market_f3_slots_{companyId}` → `Record<"0"|"1"|...|"9", productId>`.

Timeout / уход со страницы кассы сбрасывает режим ожидания.

## 4.5 Backend (фаза 2, желательно)

```
GET  /main/pos/quick-slots/     → { "0": "<product_id>"|null, ... "9": ... }
PUT  /main/pos/quick-slots/     → то же тело (owner/admin или can_edit_pos)
```

- Scope: на компанию или на кассу/ветку — решить с BE.
- Миграция: сосуществование с `hotkey_group` или one-way export «первый товар группы F3 → слот» — только после выбора гейта.

## 4.6 Критерии приёмки

- [ ] Гейт задокументирован (выбранный вариант).
- [ ] F3+цифра добавляет товар; конфликт с группами разрешён по выбранному варианту.
- [ ] Слоты сохраняются на устройстве (MVP) и переживают reload.
- [ ] Не мешают оплате / модалкам (как текущий hotkey handler — early return при открытых модалках).

# Модуль 1. Массовое добавление товаров на склад

## 1.1 Цель

Полноэкранный режим сканирования: классификация штрихкодов в три списка, правка количеств, создание карточек, **атомарный** приход на склад.

## 1.2 Текущее состояние

| Есть | Нет |
|------|-----|
| `lookupWarehouseProductByBarcode` → `main/products/warehouse-barcode/{code}/` | Endpoint статусов IN_STOCK / IN_CATALOG / UNKNOWN одним контрактом |
| Fallback `global-barcode`, alternate/ambiguity helpers | `mass-incoming` / пакетный атомарный приход |
| `POST warehouse/{uuid}/products/scan/` | Fullscreen UI «Массовое сканирование» |
| `createReceiptDocument` → `warehouse/documents/receipt/` | Миграция UNKNOWN → карточка → список 2 в одном UX |
| `POST /main/products/create-by-barcode/` | |

**Важно:** текущий lookup возвращает товар или 404, **не** три статуса ТЗ.  
**Важно:** [`../backend/alternate-barcodes.md`](../backend/alternate-barcodes.md) — без BE-правок доп. коды на lookup/scan работают частично.

## 1.3 Frontend (можно готовить параллельно)

### UX

1. Кнопка **«Массовое сканирование»** на складе (`/crm/sklad`).
2. Полноэкранный UI; поле ввода с автофокусом; возврат фокуса через 1 с после обработки.
3. Debounce скана **300 ms** (антидубль от сканера).
4. Три списка:
   - **IN_STOCK** — есть на текущем складе
   - **IN_CATALOG** — есть в каталоге компании, нет на этом складе / нужен приход
   - **UNKNOWN** — неизвестен
5. Ручное редактирование количества в списках 1–2.
6. Модалка «Создать карточку» для UNKNOWN с подставленным штрихкодом → после успеха элемент переходит в IN_CATALOG.
7. Звуки: success / unknown / error (можно Web Audio / короткие mp3).
8. `beforeunload` / confirm при закрытии с несохранёнными данными.
9. Кнопка «Провести приход» активна только при непустых списках 1–2.

### Пока нет BE barcode-check

Допустимо:

- Мок классификации на FE через существующие lookup + эвристику **только в dev/feature-flag**.
- **Запрещено** в проде проводить приход построчно «как будто mass-incoming» — риск частичного успеха и рассинхрона остатков.

## 1.4 Backend (обязательно)

### 1.4.1 Проверка штрихкода

`GET /warehouse/{warehouse_id}/barcode-check/{code}/`  
(или `POST` с телом — на усмотрение BE; важны поля ответа)

**Ответ 200 (пример):**

```json
{
  "status": "IN_STOCK" | "IN_CATALOG" | "UNKNOWN",
  "barcode": "4601234567890",
  "product": {
    "id": "uuid",
    "name": "…",
    "barcode": "…",
    "unit": "pcs",
    "stock_qty": 12.0
  },
  "ambiguous": false,
  "matches": []
}
```

Правила поиска: `{barcode} ∪ alternate_barcodes` (см. alternate-barcodes.md).  
При неоднозначности: `409` + `matches[]` (как в кассе) или `ambiguous: true` в 200 — **один** контракт на оба клиента.

### 1.4.2 Атомарный mass-incoming

`POST /warehouse/{warehouse_id}/mass-incoming/`

```json
{
  "items": [
    { "product_id": "uuid", "quantity": "10", "list": "IN_STOCK" },
    { "product_id": "uuid", "quantity": "3", "list": "IN_CATALOG" }
  ],
  "comment": "optional"
}
```

- Либо один документ прихода + проводка, либо эквивалент с **all-or-nothing** транзакцией.
- При ошибке — 4xx/5xx, остатки не меняются частично.
- Альтернатива: расширить существующий receipt document batch + post в одной транзакции — зафиксировать в чеклисте BE.

### 1.4.3 Создание карточки

Переиспользовать / уточнить `POST /main/products/create-by-barcode/` (поля обязательные для market).
