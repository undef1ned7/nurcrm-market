# 1. «Проверка цен»: считать склад на сервере

**Приоритет:** высокий
**Новый эндпоинт:** `GET /main/products/price-check/`

---

## 1.1. Как сейчас

Вкладка «Проверка цен» показывает итоги склада и товары, требующие внимания: в убыток, с низкой маржой, без закупки, с минусом на складе.

Для этого фронт скачивает **весь каталог**:

- `GET /main/products/list/?page_size=200`, затем по `next` — до **100 страниц** (`MAX_PAGES` в `catalog.ts`);
- каждый товар — полный объект (изображения, партии, акции, `cashflows`…), ~2 КБ JSON без сжатия;
- пересчёт в браузере (`checkCatalogPrices` в `pricing.ts`);
- **повтор каждые 2 минуты**, пока вкладка открыта.

Проблемы:

1. **Предел 20 000 товаров.** Дальше фронт останавливается, и итоги склада («Склад по закупке», «Будущая прибыль», «Средняя маржа») считаются только по части товаров. Сейчас фронт хотя бы предупреждает об этом.
2. **Нагрузка.** Склад на 20 000 товаров — 100 запросов и около 40 МБ JSON (без сжатия) на каждое обновление, у каждого открытого окна.
3. **Медленно на телефоне и слабом интернете.** Пока не скачаны все страницы, итогов нет.

## 1.2. Что нужно

Один запрос, который отдаёт уже посчитанные итоги, счётчики по фильтрам и **одну страницу** нужных строк.

```
GET /main/products/price-check/
```

### Параметры

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `filter` | `all` \| `loss` \| `lowMargin` \| `noCost` \| `negativeStock` | `all` | какие строки вернуть (правила — §1.3) |
| `threshold` | число 0–100 | `15` | порог «низкой маржи», % |
| `search` | строка | — | по названию **и штрихкоду** (включая `alternate_barcodes`) — сейчас на фронте ищется только по названию |
| `page`, `page_size` | int | `1`, `200` | пагинация строк; `page_size` до 500 |
| `ordering` | `name` \| `margin` \| `-margin` \| `stock_profit` \| `-stock_profit` | `name` | сортировка строк |
| `branch` | id / `main` | как в `/main/products/list/` | если склад филиала считается отдельно |

Услуги (`kind = service`) **не участвуют** ни в итогах, ни в строках.

- Денежные значения — строки с 2 знаками, как в остальном API. `markup`, `margin`, `stock_profit`, `average_margin` — `null`, когда посчитать нельзя (§1.3).
- `counts` считаются **с учётом `search`**, но **без учёта `filter`** — фронт показывает их на кнопках фильтров.
- `summary` — **по всему складу**, без учёта `search` и `filter`.
- `calculated_at` — когда посчитано (если итоги кэшируются, см. §1.5).

## 1.3. Правила расчёта — должны совпадать с фронтом один в один

Сейчас это функция `checkCatalogPrices` в `src/shared/lib/pricing.ts`, тесты — `src/shared/lib/pricing.test.ts`. После перехода фронт будет только показывать ответ, поэтому формулы должны быть те же.

Обозначения для товара: `cost = purchase_price`, `price = price`, `qty = quantity`, «есть закупка» = `cost > 0`.

**Строка товара**

| Поле | Формула | Когда `null` |
|---|---|---|
| `markup` | `(price − cost) / cost × 100` | нет закупки |
| `margin` | `(price − cost) / price × 100` | нет закупки или `price ≤ 0` |
| `stock_profit` | `(price − cost) × max(qty, 0)` | нет закупки |

**Метки (`flags`)** — порядок важен, у товара может быть несколько:

1. Есть закупка:
   - `price < cost` → `loss`
   - иначе `price = cost` → `noMarkup`
   - иначе `margin < threshold` → `lowMargin`
2. Нет закупки → `noCost`
3. Отдельно: `qty < 0` → `negativeStock`

**Фильтры**

| `filter` | Какие строки |
|---|---|
| `all` | все товары (кроме услуг) |
| `loss` | `loss` **или** `noMarkup` |
| `lowMargin` | `lowMargin` |
| `noCost` | `noCost` |
| `negativeStock` | `negativeStock` |

**Итоги (`summary`)** — отрицательный остаток считается как 0:

| Поле | Формула |
|---|---|
| `stock_at_cost` | Σ `max(qty,0) × max(cost,0)` по всем товарам |
| `stock_at_price` | Σ `max(qty,0) × max(price,0)` по всем товарам |
| `future_profit` | Σ `(price − cost) × max(qty,0)` **только по товарам с закупкой** |
| `average_margin` | `future_profit / Σ(price × max(qty,0) по товарам с закупкой) × 100`; `null`, если знаменатель 0 |

### Контрольный пример (точная копия `describe("проверка цен")` из `pricing.test.ts`)

Порог 15 %:

| id | Товар | cost | price | qty | flags |
|---|---|---|---|---|---|
| 1 | Убыток | 100 | 90 | 2 | `loss` |
| 2 | В ноль | 50 | 50 | 1 | `noMarkup` |
| 3 | Низкая маржа | 90 | 100 | 10 | `lowMargin` (маржа 10 %) |
| 4 | Без закупки | 0 | 70 | 5 | `noCost` |
| 5 | Минус | 10 | 20 | −3 | `negativeStock` |
| 6 | Хорошо | 50 | 100 | 4 | — |

Ожидаемо:

- `future_profit` = 2×(−10) + 0 + 10×10 + 0 (минусовый остаток не считается) + 4×50 = **280**
- `average_margin` = 280 / (2×90 + 50 + 1000 + 0 + 400) × 100 = 280 / 1630 × 100 ≈ **17,18**
- `stock_at_price` = 180 + 50 + 1000 + 350 + 400 = **1980**
- `filter=loss` → 1, 2; `filter=noCost` → 4; `search=хорош` → 6

## 1.4. Где это считать

Удобнее всего — одним агрегирующим запросом по таблице товаров компании (`Sum`/`Case`/`When` в Django ORM), без выгрузки объектов в Python. Метки и фильтры — те же условия в `WHERE`.

`markup`/`margin` для строк считаются аннотациями; сортировка `ordering=margin` — по аннотации.

## 1.5. Кэш (по желанию)

Если агрегат на крупных складах дорогой — кэшировать `summary` и `counts` на 1–2 минуты по ключу `(company, branch, threshold)` и сбрасывать при изменении товара, приходе, продаже. Строки (`results`) можно не кэшировать. Фронт покажет `calculated_at`.

## 1.6. Что сделает фронт после

- Уберёт выгрузку всего каталога для этой вкладки: один запрос на открытие + запрос на смену фильтра/поиска/страницы.
- Уберёт предупреждение «Загружено 20 000 из …» — предела не будет.
- Поиск по штрихкоду заработает из `search`.
- Автообновление — повтор этого же запроса (лёгкого), а лучше по признаку из задачи 2.

Блок «Заканчивается на складе» в «Сводке» и срез ABC «Склад» тоже скачивают весь каталог (`fetchCatalogSnapshot`). Их можно перевести на этот же эндпоинт или отдельные агрегаты — обсудим после первой версии.

## 1.7. Как проверим

1. Склад на 20 000+ товаров: вкладка открывается одним запросом, итоги совпадают с суммой по базе.
2. Контрольный пример §1.3: те же метки и фильтры.
3. `search` по основному и дополнительному штрихкоду находит товар.
4. Услуги не попадают ни в итоги, ни в строки.
5. Ответ на 20 000 товаров — быстрее 1 секунды.

## Ответ BE

**Готово (BE, 08.10.2026).** `GET /main/products/price-check/` по контракту §1.2:

- `summary`, `counts`, одна страница строк с `markup`, `margin`, `stock_profit` и метками `loss`, `noMarkup` («в ноль»), `lowMargin`, `noCost`, `negativeStock`.
- Формулы те же, что в `checkCatalogPrices`. Контрольный пример §1.3 даёт те же цифры: будущая прибыль 280, средняя маржа 17,18 %, склад по цене продажи 1 980.
- `search` — по названию, артикулу, основному и дополнительным штрихкодам.
- Услуги и архивные товары не учитываются. Комплект (`kind = bundle`) считается товаром.
- Предела 20 000 товаров нет. На 25 000 товаров ответ за 0,12–0,49 с.
- Отдаёт `ETag`; повторный запрос с тем же `If-None-Match` получает `304` без тела (~40 мс), см. задачу 2.

**Фронт (08.10.2026)** — `src/entities/product/api/priceCheck.ts`, `src/pages/market-calculator/ui/usePriceCheck.ts`:

- Вкладка открывается одним запросом; «Показать ещё» — следующая страница (`page=2…`). Каталог для неё больше не выкачивается, предупреждение «Загружено 20 000 из …» убрано.
- Фильтр, поиск и порог уходят на сервер (поиск и порог — после паузы 300 мс). Подпись поля — «Поиск по названию, артикулу или штрихкоду».
- Автообновление раз в 2 минуты сначала спрашивает `catalog-version/`: та же версия — ничего не качается. Без версии — повтор с `If-None-Match`, `304` оставляет таблицу.
- Если на сервере нет эндпоинта (`404`) — прежний расчёт в браузере по выкачанному каталогу, с предупреждением об обрезке. Нужен на время выкатки на все стенды.
- Перепроверено стресс-тестом `MarketCalculator.regress.test.tsx`: 25 000 товаров — 1 запрос, контрольный пример, поиск по штрихкоду, `304`, смена версии, медленная сеть.

**Открыто для BE — CORS.** API на другом домене (`app.nurcrm.kg`), поэтому:

- чтобы фронт видел `ETag`, его нужно отдавать в `Access-Control-Expose-Headers`;
- чтобы браузер пропустил `If-None-Match`, его нужно добавить в `Access-Control-Allow-Headers` (в `django-cors-headers` по умолчанию его нет).

Пока этого нет, фронт работает без `304`: автообновление держится на `catalog-version/`. Если условный запрос отклонён CORS, фронт повторяет его без заголовка и до перезагрузки страницы больше его не шлёт.
