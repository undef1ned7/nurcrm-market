# Акт сверки клиента: двойное начисление долга («Продажа» + «Сделка: Долг»)

**Эндпоинт:** `GET /main/clients/{id}/reconciliation/json/?currency=KGS&start=&end=`
**Экран:** карточка клиента → «Акт сверки» (`ReconciliationModal.tsx` → `ReconciliationPdfDocument.tsx`).
**Статус:** фронт защищён (2026-10-02), **ждёт бэк** — корень проблемы в расчёте на сервере.
**Связано:** [debt-v2-backend-implementation.md](./debt-v2-backend-implementation.md), [auto-cashflows-backend.md](./auto-cashflows-backend.md).

---

## 1. Симптом (реальный акт)

Продажа в долг 15 000 сом, клиент внёс 6 платежей по 2 500 = 15 000. Должно быть сальдо **0**. В акте:

| Документ | Дебет | Кредит |
|---|---|---|
| Продажа a2a414fb…ffcd | 15 000 | |
| Сделка: Долг Гулумкан Исакова (Долг) | 15 000 | |
| Оплата №1…№6 | | 6 × 2 500 |
| **Итого** | **30 000** | **15 000** |
| **Сальдо** | **15 000** | |

Колонки «по данным клиента» зеркальны (Дт 15 000 / Кт 30 000).

## 2. Причина (гипотеза; подтвердить по данным)

Фронт при продаже в долг делает **два** вызова подряд (`usePaymentPage.ts`):

1. `POST` checkout → создаётся **продажа** (бэк пишет начисление на сумму чека);
2. `POST /main/clients/{id}/deals/` с `kind=debt`, `amount = total` (полная сумма чека, не остаток), `prepayment` отдельно, v2-график.

Сделка нужна для **графика платежей**, а не как второе начисление. Если акт строится как union «все продажи + все сделки + все оплаты», долг считается дважды.

**Просим проверить:** `GET .../reconciliation/json/` для этого клиента — есть ли обе строки с ненулевым `a_debit`; и общий источник: вычисляется ли строка сделки как отдельная проводка.

## 3. Требуемое поведение

1. **Одна продажа → одно начисление.** `deals(kind=debt)`, созданная для продажи, в оборот акта (Дт/Кт и сальдо) **не входит**.
   - Связать сделку с продажей (`deal.sale_id` / `sale.deal_id`), если связи ещё нет — иначе дубль не определить надёжно.
   - Сделка `kind=debt`, созданная **без** продажи (ручной долг в карточке клиента), остаётся самостоятельным начислением.
2. **Оплаты по графику** (`installment_payment`, `deal_prepayment`) уменьшают долг один раз — и не дублируются, если одновременно создан cashflow.
3. **Предоплата** при продаже: сделка приходит с `amount = total`, `prepayment = X`. Начисление = `total` (продажа), оплата `X` — отдельная строка Кт. Сделка снова не добавляет Дт.
4. **Отмена/возврат продажи** убирает начисление продажи; платежи не удаляются — разница уходит в переплату (Кт-сальдо).
5. Обороты и итоговое сальдо считать на бэке и отдавать в ответе (см. §4), фронт не должен их восстанавливать суммированием.

## 4. Контракт ответа (дополнение)

Строки (`rows[]`) — как сейчас, плюс **необязательные** поля:

```json
{
  "opening_company": 0,
  "opening_client": 0,
  "closing_company": 0,
  "closing_client": 0,
  "totals": { "a_debit": 15000, "a_credit": 15000, "b_debit": 15000, "b_credit": 15000 },
  "rows": [
    { "date": "2026-10-02", "ref_type": "sale", "ref_id": "a2a414fb-…", "title": "Продажа …", "a_debit": 15000, "a_credit": 0, "b_debit": 0, "b_credit": 15000, "affects_balance": true },
    { "date": "2026-10-02", "ref_type": "deal", "ref_id": "…", "sale_id": "a2a414fb-…", "kind": "debt", "title": "Сделка: Долг … (Долг)", "a_debit": 0, "a_credit": 0, "affects_balance": false }
  ]
}
```

- `affects_balance: false` — строка информационная (сделка-график, связанная с продажей); суммы можно отдавать нулями или как есть — фронт их не учитывает.
- `ref_type` — явный тип операции: `sale | payment | installment_payment | deal | deal_prepayment | return | refund | adjustment`. Сейчас тип фронт вынужден угадывать по `title` («Сделка: …», «Продажа …»).
- `ref_id`, `sale_id` — для связи сделки с продажей.

Старый формат ответа остаётся валидным: все новые поля опциональны.

## 5. Что уже делает фронт (временная защита)

Файл `src/pages/documents/ui/components/reconciliationRows.ts`:

- `affects_balance === false` (также `is_informational`, `is_reference`) → строка справочная, в обороты не входит.
- Эвристика, если флага нет: строка-сделка вида «долг» (`ref_type=deal` / `Сделка: … (Долг)`, `kind=debt`) **парится с продажей** на ту же сумму по `a_debit` с разницей по дате ≤ 3 суток, одна продажа гасит не более одной сделки. Парная сделка → справочно, `Дт` не считается.
- В PDF строка помечена «(справочно, в оборот не входит)»; добавлен блок «Начислено / Оплачено / Остаток задолженности (или Переплата)»; в модалке — уведомление, сколько дублей исключено.

Эвристика — **костыль**: ошибётся, если у клиента две продажи на одну сумму в течение 3 суток и одна из них без сделки. После фикса на бэке (§3) она перестанет срабатывать сама; удалить после выката и подтверждения `affects_balance`.

## 6. Тест-кейсы (должны быть автотестами на бэке)

| # | Данные | Ожидание |
|---|---|---|
| 1 | Продажа в долг 10 000, оплат нет | Дт 10 000, Кт 0, сальдо 10 000 |
| 2 | Продажа 10 000 + оплата 10 000 | сальдо 0 |
| 3 | Продажа 10 000 + оплата 6 000 | сальдо 4 000 |
| 4 | **Продажа 15 000 + сделка-долг 15 000 + 6 × 2 500** | **сальдо 0**, Дт 15 000 (не 30 000) |
| 5 | Продажа 15 000 с предоплатой 5 000 + сделка (`amount=15000`, `prepayment=5000`) | Дт 15 000, Кт 5 000, сальдо 10 000 |
| 6 | Ручная сделка-долг 7 000 без продажи | Дт 7 000 (считается) |
| 7 | Продажа 15 000, возврат товара 5 000 | сальдо 10 000 |
| 8 | Продажа 15 000, оплата 15 000, возврат 5 000 | Кт-сальдо 5 000 (переплата), не «хаотичный» дебет |
| 9 | Повторный вызов создания сделки для той же продажи (повтор из очереди `enqueuePendingDebtDeal`) | идемпотентно: вторая сделка не создаётся/не попадает в акт |
| 10 | Отмена продажи с частичной оплатой | начисление убрано, оплаты остались, виден остаток переплаты |

## 7. Идемпотентность

Фронт повторяет создание сделки из очереди (`processPendingDebtDeals`), если первый вызов упал по сети. Нужен уникальный ключ `(sale_id, kind=debt)` на сделке либо `Idempotency-Key`, иначе повтор создаст вторую сделку на ту же продажу.
