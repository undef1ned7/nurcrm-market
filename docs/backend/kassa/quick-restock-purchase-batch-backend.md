# «Добавление товара» на карточке склада не попадало в «Историю закупок» — фикс + вопросы бэку

**Экран:** `/crm/sklad/{productId}` → кнопка «Добавить» → модалка «Добавление товара» (`AddProductModal.tsx`).
**Симптом:** ввели количество/цену, сохранили — остаток и цена на карточке обновились, но в блоке «История закупок» под карточкой ничего не появилось.

## Причина

Модалка никогда не создавала партию/приход — она делала прямой `PATCH /main/products/{id}/` с `quantity: остаток + количество`. «История закупок» (`product.purchase_batches`) заполняется только когда товар оприходуется через `POST /main/suppliers/{supplierId}/receipt/` — этот путь используется на отдельной странице «Приход от поставщика» (`SupplierReceiptPage`), а «Добавление товара» на карточке его не вызывал вообще.

## Что исправлено на фронте

`AddProductModal.tsx` теперь ветвится по наличию выбранного поставщика:

**Поставщик выбран** → идёт по тому же контракту, что и «Приход от поставщика»:

```
POST /main/suppliers/{supplierId}/receipt/
{
  "items": [{ "product": "<productId>", "qty": 100, "purchase_price": 50 }],
  "payment_type": "cash" | "debt" | "prepayment",
  // + маршрутизация кассы (buildExpenseVariableRouting), если cash/prepayment
}
```

Затем отдельным partial-PATCH фиксируем розничную цену, введённую в форме (приход её не принимает — пересчитывает по `markup_percent`, см. [supplier-receipt-selling-price-backend.md](./supplier-receipt-selling-price-backend.md)):

```
PATCH /main/products/{productId}/
{ "price": "<retailPrice>", "client": "<supplierId>" }
```

Долг/предоплата (`/main/debts/`, `createDeal`) и cashflow (`postCashflowIfNeeded` с `source_cashbox_flow_id = receiptId`) — без изменений логики, один в один с «Приходом от поставщика».

**Поставщик не выбран** → прежнее поведение без изменений: `PATCH /main/products/{id}/ { quantity, purchase_price, price }`. Это осознанно **не** попадает в «Историю закупok» — в UI теперь есть поясняющая подпись под выбором поставщика.

## Нужно подтвердить / проверить на бэке

1. **Ответ `POST /main/suppliers/{id}/receipt/` содержит `id` (или `uuid`)** верхнего уровня — фронт берёт его как `receiptId` и передаёт в cashflow как `source_cashbox_flow_id`, чтобы связать движение кассы с приходом. Если поле называется иначе — сообщите точное имя.
2. **`items` с одной позицией** — эндпоинт уже используется с несколькими товарами разом (мульти-приход), убедитесь, что массив из одного элемента обрабатывается так же (остаток +qty, партия создаётся, `purchase_batches` товара пополняется).
3. **Гонка между приходом и последующим PATCH цены.** Сразу после `POST .../receipt/` фронт шлёт `PATCH { price, client }` (только эти два поля). Приход в той же операции пишет `quantity`/`purchase_price`/пересчитанный `price`. Партиальный PATCH должен менять **только** переданные поля и не сбрасывать `quantity`/`purchase_price`, которые только что установил приход. Это стандартное поведение PATCH, но так как раньше фронт после прихода никогда не делал последующий PATCH — прошу явно проверить на этом сценарии.
4. **`client` на Product** — приход, вероятно, и так фиксирует последнего поставщика где-то на своей стороне (партия хранит `supplier`/`receipt_id`). Наш `PATCH { client: supplierId }` дополнительно проставляет `Product.client`. Если это поле бэк уже выставляет сам при приходе — наш PATCH просто идемпотентен, конфликта нет. Уточните на всякий случай.

## Открытый вопрос (продуктовое решение, не баг)

**Оприходование без поставщика нигде не логируется** — ни в «Истории закупок», ни в каком-либо другом аудите. Пользователь может накрутить остаток/себестоимость на карточке без какого-либо следа операции (кроме `updated_at` товара).

Если это нежелательно — варианты для бэка:

- (a) разрешить `POST /main/suppliers/{id}/receipt/` без поставщика (`supplier: null` где-то в системе, или отдельный `POST /main/products/{id}/manual-restock/`), чтобы такие операции тоже попадали в партии с пометкой «без поставщика»;
- (b) завести отдельный лёгкий аудит-лог на Product (кто/когда/сколько добавил, без интеграции с закупками);
- (c) оставить как есть — это осознанный «быстрый» путь корректировки остатка, не претендующий на бухгалтерскую историю.

Решать продукту/бэку — фронт под любой из вариантов дошлёт нужные поля.

## QA-сценарии

| # | Шаги | Ожидаемо |
|---|---|---|
| 1 | Открыть товар → «Добавить» → выбрать поставщика → 100 шт по 50 сом, полная оплата → сохранить | Остаток +100, «История закупок» получает новую партию с этим поставщиком и суммой, розничная цена на карточке равна введённой |
| 2 | То же, но с розничной ценой, отличной от расчётной по наценке | После сохранения `product.price` равна введённой в форме, а не пересчитанной по markup |
| 3 | То же, тип оплаты «В долг» | Партия создана, cashflow не создаётся (`cashAmount = 0`), запись в `/main/debts/` (тариф «Старт») и сделка появляются |
| 4 | То же, тип оплаты «Предоплата» | Партия создана, cashflow на сумму предоплаты с `source_cashbox_flow_id = receiptId`, остаток долга — в сделке |
| 5 | Добавить товар **без** поставщика | Остаток/цены обновились, «История закупок» **не** пополнилась (ожидаемо) |
