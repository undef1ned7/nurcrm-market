# Способ оплаты при погашении долга (наличные / перевод + банк)

Фронт добавил на **двух экранах** выбор способа оплаты при погашении долга. Бэку нужно **принять и сохранить новое поле `payment_method`** и учесть его при маршрутизации кассового движения и в отчётах.

| Экран                                                    | Модалка                       | Эндпоинт погашения                                                |
| -------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------- |
| «Долги» `/crm/debts` → строка → «Оплатить»               | `PayDebtModal`                | `PATCH /main/debts/{id}/` (долг **v1**)                           |
| Карточка клиента/поставщика `/crm/clients/{id}` → «Долг» | `DebtModal` (график платежей) | `POST /main/clients/{clientId}/deals/{dealId}/pay/` (долг **v2**) |

**Статус:** фронт реализован на обоих экранах.

---

## Что изменилось на фронте

В модалку добавлен выбор способа оплаты:

- **Наличными** (по умолчанию) — `payment_method: "cash"`;
- **Переводом** — открывается список банков; `payment_method` = id банка.

Список банков (совпадает с checkout-конвенцией кассы):
`mbank`, `optima`, `obank`, `bakai`, `demir`, `other`.

Если способ = «Переводом», но банк не выбран (теоретически невозможно — есть значение по умолчанию `mbank`), фронт шлёт `payment_method: "transfer"`.

Итоговое множество значений `payment_method`:

```
"cash" | "mbank" | "optima" | "obank" | "bakai" | "demir" | "other" | "transfer"
```

Общий модуль фронта: `src/shared/lib/tools/debtPaymentMethod.ts`
(`resolveDebtPaymentMethod`, `debtPaymentMethodLabel`, `DEBT_PAYMENT_BANKS`).
Экраны: `src/features/debts/ui/{Debts.tsx,components/PayDebtModal.tsx}` (v1),
`src/pages/clients/ui/ClientDetails/components/DebtModal.tsx` (v2).

В `DebtModal` (v2) выбранный способ применяется **и** к кнопке «Оплатить» в строке графика, **и** к «Оплатить весь долг» (каждый взнос гасится своим `pay/`-вызовом с тем же `payment_method`).

---

## 1. Запросы на погашение долга

Без изменений в URL и семантике сумм — добавлено одно поле `payment_method`.

### 1a. Долг v1 — `PATCH /main/debts/{id}/`

PATCH с **новой уменьшенной суммой остатка** (как раньше):

```
PATCH /main/debts/{id}/
{
  "amount": "500.00",              // новый остаток долга (было 1500, погасили 1000)
  "payment_method": "mbank",       // ← НОВОЕ
  "cashbox_role": "...",           // routing, как раньше (buildPosRoutingFromUser)
  "branch_id": "...",
  "shift_id": "..."
}
```

### 1b. Долг v2 (сделка с графиком) — `POST /main/clients/{clientId}/deals/{dealId}/pay/`

Оплата одного взноса (как раньше), плюс `payment_method`:

```
POST /main/clients/{clientId}/deals/{dealId}/pay/
{
  "idempotency_key": "<uuid>",
  "installment_id": "<installment uuid>",
  "date": "2026-09-07",
  "amount": "300.00",              // опционально: частичная оплата взноса
  "payment_method": "cash",        // ← НОВОЕ
  "cashbox_role": "...",           // routing как раньше (POS для клиента,
  "branch_id": "...",              //   buildExpenseVariableRouting для поставщика)
  "shift_id": "..."
}
```

Для **поставщика** (`clientType = suppliers`) погашение — это `expense`; `payment_method` имеет тот же смысл (чем платили поставщику: наличные / перевод).

### Что нужно от бэка (для обоих)

1. **Принять `payment_method`** (не падать на неизвестном поле). Значение — из множества выше; допускается стратегия «неизвестное → трактуем как `transfer`».
2. **Сохранить способ оплаты в записи о погашении** (payment/history взноса или долга), чтобы он попадал в историю и отчёты. Если у долга v1 нет отдельной таблицы платежей — как минимум сохранить на самой операции/движении кассы.
3. **Учесть способ при создании авто-кассового движения** (`AUTO_CASHFLOWS=true`), см. §3.

`payment_method` — **необязательное** поле: старые клиенты и мобильные приложения его не шлют. Отсутствие = `cash` (текущее поведение).

---

## 2. Fallback-движение по кассе с фронта (`VITE_BE_CASHFLOWS != "true"`)

Пока авто-кассовые движения на бэке не включены, фронт сам создаёт приход через `postCashflowIfNeeded`. Теперь payload содержит `payment_method` и метку способа в названии:

```
POST /main/cashflows/         (существующий контракт addCashFlows)
{
  // v1: "Возврат долга: Иван Петров (МБанк)"
  // v2: "оплата долга: Иван Петров №3 (Наличные)"
  "name": "Возврат долга: Иван Петров (МБанк)",
  "amount": "1000.00",
  "type": "income",              // для поставщика в v2 — "expense"
  "payment_method": "mbank",     // ← НОВОЕ
  "cashbox": "<resolved>",
  ...
}
```

Просьба: **сохранять `payment_method` на записи cashflow** (новое nullable-поле), чтобы после включения `AUTO_CASHFLOWS` данные были однородны и разбивка по способам оплаты (`payment_breakdown`) работала и для долгов.

---

## 3. Маршрутизация авто-кассового движения (когда `AUTO_CASHFLOWS=true`)

При погашении долга бэк создаёт `income`. Способ оплаты должен влиять так же, как в продаже:

| `payment_method`                                                        | Куда идёт приход                                                    | Влияет на `drawer_expected_cash` |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------- |
| `cash`                                                                  | наличная касса смены (drawer)                                       | **да**                           |
| `mbank` / `optima` / `obank` / `bakai` / `demir` / `other` / `transfer` | безналичная касса (`cashbox_role` для переводов / привязка к банку) | **нет**                          |

То есть перевод в счёт долга **не должен** увеличивать ожидаемую наличность в ящике при сверке смены — ровно как безналичная продажа. Наличное погашение — увеличивает.

Атрибуцию банка (`mbank` и т.д.) желательно сохранять на движении для аналитики «Финансы» и разбивки по банкам, если такая уже есть для продаж.

---

## 4. Отчёты и аналитика

- **`payment_breakdown` при закрытии смены** — приход от погашения долга должен попадать в соответствующую строку (нал / безнал / по банку), а не только в общий итог.
- **Дневной/месячный отчёт кассы** — способ оплаты в детализации движения, если детализация показывает способ.
- **Сверка смены** (`expected_cash`) — см. таблицу §3: только `cash` влияет на ожидаемую наличность.

## Вопросы к бэку (D1–D6)

- **D1.** Есть ли у долга v1 (`/main/debts/`) отдельная таблица платежей, или погашение — это просто PATCH `amount`? Где корректно хранить `payment_method` погашения?
- **D2.** Подтвердите: неизвестное значение `payment_method` бэк трактует как `transfer` (безнал), не падает 400.
- **D3.** При `AUTO_CASHFLOWS=true` — бэк берёт маршрутизацию прихода по `payment_method` на себя (§3), или фронт должен продолжать слать routing-поля и `postCashflowIfNeeded`?
- **D4.** Нужно ли фронту слать отдельно `bank` (id банка) и `payment_method` (`cash`/`transfer`), или достаточно одного `payment_method` с id банка внутри (текущая реализация фронта)?
- **D5.** Поддерживается ли атрибуция по банку в отчётах/аналитике для приходов (не только для продаж)? Если нет — принимать ли `payment_method` пока только как `cash` / `transfer`?
- **D6.** Долг v2: `POST .../deals/{dealId}/pay/` принимает `payment_method` на уровне взноса? Сохраняется ли он в объекте платежа взноса (`installments[].payments[]` или аналог), чтобы отображать способ в истории?

## Не блокер

Фронт работает и сегодня: при отсутствии поддержки на бэке `payment_method` просто игнорируется, погашение проходит как раньше (наличными). Приоритет доработки бэка — по согласованию; критичен пункт §3 (перевод не должен раздувать ожидаемую наличность смены).
