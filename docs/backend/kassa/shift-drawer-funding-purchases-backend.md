# «Оплачено из кассы (ящика) смены» на закупках/долгах поставщику

**Страницы:** `/crm/sklad` (приход поставщика, добавление товара, брак — принятие pending), `/crm/clients/{id}` (оплата долга поставщику)
**Статус:** ✅ фронт реализован и включён для всех — **без изменений на backend**, использует уже существующий ручной эндпоинт `/crm/kassa`
Префикс: `{host}/api` · TZ: **Asia/Bishkek (UTC+6)**

Читать вместе с: [scenario-shift-drawer-funding.md](./scenario-shift-drawer-funding.md) (сквозной сценарий + чек-лист QA), [shift-cash-reconciliation-backend.md](./shift-cash-reconciliation-backend.md) (`drawer_expected_cash`, `affects_shift_drawer`), [auto-cashflows-backend.md](./auto-cashflows-backend.md) (модель кассы/cashflow, ручная касса), [BACKEND-QUESTIONS.md](./BACKEND-QUESTIONS.md) (п. 51-52 — подтверждение, что этот механизм уже работает).

## 1. Задача клиента

Кассир открывает смену, в течение смены принимает приход товара от поставщика (или платит долг поставщику, принимает pending-позиции) и **физически оплачивает это наличными из своего кассового ящика**, а не из отдельного места. До этой доработки система не знала об этом: приход поставщика всегда маршрутизировался на кассу «Переменные расходы» (`cashbox_role: expense_variable`) отдельно от POS-кассы смены, и `drawer_expected_cash` при закрытии смены не учитывал эту трату — кассир видел необъяснённую недостачу.

Полное описание симптома и корневой причины — уже в [shift-cash-reconciliation-backend.md](./shift-cash-reconciliation-backend.md) §«Если деньги физически взяли из ящика» (там это было отмечено как «будущее, опционально»). Этот документ фиксирует, что фронт эту опцию реализовал.

## 2. Что фронт делает технически

**Никаких новых полей в бизнес-эндпоинтах (приход поставщика, создание товара, оплата долга) не добавлено.** Маршрутизация самой покупки не изменилась — она по-прежнему всегда идёт на `expense_variable`, как описано в `auto-cashflows-backend.md`.

Когда кассир отмечает чекбокс «Я заплатил из кассы (ящика) смены» и операция проходит успешно, фронт **дополнительно** отправляет второй, независимый запрос через уже существующий ручной эндпоинт кассы:

```
POST /construction/cashflows/
{
  "cashbox": "<id POS-кассы, привязанной к открытой смене кассира>",
  "type": "expense",
  "amount": "1234.56",
  "name": "Приход поставщика — оплата из кассы смены: ООО Ромашка",
  "status": "approved" | "pending"
}
```

Это тот же контракт, что использует ручной ввод в `/crm/kassa` (см. `auto-cashflows-backend.md` §«Ручная касса (без изменений)»). `status` вычисляется по той же формуле, что уже использует `/crm/kassa` (`AddCashFlowsModal.tsx`): `approved`, если пользователь `owner` или выключены «Запросы на подтверждение» (`cashflowRequestsEnabled === false`), иначе `pending`.

По ответу backend на [BACKEND-QUESTIONS.md, п. 51](./BACKEND-QUESTIONS.md#8-p2--уточнения) — `shift_drawer_outflow`/`affects_shift_drawer=True` **уже реализован** для таких ручных записей на кассе смены. То есть эта запись автоматически, без какой-либо дополнительной логики на backend, попадает в `drawer_expected_cash` открытой смены при её закрытии — ровно то поведение, которое нужно.

### Итог: два независимых cashflow на одну операцию

```
Покупатель → наличные → POS-касса смены → drawer_expected_cash (как обычно)

Поставщик ← оплата (expense_variable, как обычно, не влияет на смену)
         ↑
Кассир: «Оплачено из кассы смены» →  ручной expense на POS-кассе смены
                                       (affects_shift_drawer=True → уменьшает
                                       drawer_expected_cash при закрытии)
```

Оба cashflow создаются отдельными запросами, **не атомарно** (в отличие от auto-cashflows бизнес-операций). Фронт сначала выполняет основную операцию (приход/создание товара/оплата долга) и только при её успехе — второй запрос на списание из кассы смены. Если основная операция падает — второй запрос не отправляется. Если падает второй запрос — первая операция **не откатывается** (то есть приход/оплата долга остаются в силе), пользователю показывается предупреждение «добавьте вручную в «Касса»».

## 3. Единственный реальный запрос к backend (не блокер)

Чтобы определить `cashbox` (id) для запроса выше, фронту нужно знать, какая именно касса привязана к открытой смене кассира. Сегодня ответы `POST /construction/shifts/open/` и `GET /construction/shifts/{id}/` отдают только `cashbox_name` (человекочитаемое имя), но **не** id — хотя, по модели из [auto-cashflows-backend.md §«Shift»](./auto-cashflows-backend.md), поле `cashbox` (uuid) на смене уже существует и используется на backend для резолва кассы при открытии смены.

**Просьба:** добавить `cashbox` (uuid) в сериализатор Shift рядом с уже существующим `cashbox_name`, в обоих эндпоинтах (`open/`, `GET .../{id}/`, и в списке `GET /construction/shifts/`, если он тоже отдаёт `cashbox_name`). Пример:

```json
{
  "id": "shift-uuid",
  "cashbox": "1636c624-4ae6-418c-a5f7-2597f719f496",
  "cashbox_name": "Касса филиала номер 1",
  "status": "open",
  ...
}
```

Это **не блокер** — до появления поля фронт временно резолвит кассу сам (см. §4), но с оговоркой по надёжности.

## 4. Временный резолв кассы на фронте (пока нет `shift.cashbox`)

Реализовано в `src/entities/shift/lib/shiftDrawerFunding.ts` (`resolveShiftDrawerCashboxId`):

1. Если `shift.cashbox` когда-нибудь появится — используется напрямую (задел на будущее, см. §3).
2. Иначе среди активных касс компании (`GET /construction/cashboxes/`) ищется касса с той же ролью, которую backend использовал бы при резолве POS-кассы для этого пользователя (`pos_branch` + совпадение `branch_id`, либо `pos_main`) — по тому же алгоритму, что описан в `auto-cashflows-backend.md` §«Алгоритм `resolve_cashbox`», шаги 3c/3d.
3. Если под этой ролью активна **ровно одна** касса — она и есть касса смены.
4. Если их несколько (известный баг дублирующихся `pos_main`, см. [pos-main-duplicate-role-bug.md](./pos-main-duplicate-role-bug.md)) — фронт пытается уточнить по совпадению `name` с уже известным `shift.cashbox_name`.
5. Если однозначно определить не удалось — чекбокс на UI просто не показывается (фронт не гадает и не списывает не с той кассы).

**Эта эвристика — единственная причина, по которой стоит закрыть §3.** С полем `shift.cashbox` риск дублирующихся ролей перестаёт быть проблемой для этой фичи.

## 5. Известное ограничение (принято, не баг)

Запись о списании из кассы смены **не связана** `source_id`/`source_kind` с исходной бизнес-операцией (приходом, покупкой, оплатой долга) — это `source_kind: "manual"`, как любая ручная запись `/crm/kassa`. Если исходную операцию потом отклонят/откатят через Pending (`reject cascade`, см. `auto-cashflows-backend.md` §«Reject cascade»), парная запись о списании из ящика останется как есть и её нужно будет отменить вручную.

Если backend в будущем захочет полноценно связать эти две записи (например, отдельным `source_kind: "shift_drawer_outflow"` с `source_id`, ссылающимся на исходную операцию, и включением в reject cascade) — фронт готов передавать дополнительные поля при выборе такого контракта. Пока это не запрашивается как отдельная задача — см. вопрос Q3 ниже.

## 6. Сценарии, где показывается чекбокс

Чекбокс показывается только когда: у текущего пользователя есть открытая смена **и** фронт смог однозначно определить кассу этой смены (§4) **и** способ оплаты по операции — наличные (не долг/не предоплата целиком в долг).

| #   | Экран / файл (фронт)                                                          | Операция                                                                         | Сумма списания                                                       |
| --- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | `SupplierReceiptPage` → `useSupplierReceipt.tsx`                              | Приход поставщика (`POST /main/suppliers/{id}/receipt/`), оплата cash/предоплата | `cashExpenseAmount`                                                  |
| 2   | `AddModal.tsx` (склад, быстрое добавление товара)                             | Создание товара с закупкой (`POST /main/products/create-manual/`)                | сумма закупки (cash/предоплата)                                      |
| 3   | `AddProduct/AddProductModal.tsx` (карточка товара — приход)                   | Приход/корректировка остатка с закупкой                                          | `expense` (полная/предоплата)                                        |
| 4   | `AddProductPage` → `useAddProductSubmitFlow.ts` / `ManualEntryForm.tsx`       | Создание товара (полная форма)                                                   | `amountForCash`                                                      |
| 5   | `AddProductBarcode` → `useAddProductBarcode.ts` / `AddProductBarcodeView.tsx` | Создание товара по штрихкоду                                                     | `amountForCash`                                                      |
| 6   | `AcceptPendingModal.tsx` (склад, «Принятие товаров»)                          | Массовое принятие pending-позиций, один чекбокс на всю пачку                     | сумма по каждой принятой позиции                                     |
| 7   | `DebtModal.tsx` (карточка контрагента-поставщика)                             | Оплата долга поставщику (одного взноса или «оплатить весь долг»)                 | оплаченная сумма (одна запись на всю пачку при «оплатить весь долг») |
