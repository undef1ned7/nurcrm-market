# Сценарий: «Деньги фактически отдал наличными» при возврате безналичного чека

**Аудитория:** кассиры, QA, бэкенд, владелец продукта
**Фронт:** реализовано и включено для всех, без флага
**Бэкенд:** доработок не требуется для этого сценария — используется существующий ручной эндпоинт `/crm/kassa` (та же механика, что в [shift-drawer-funding-purchases-backend.md](./shift-drawer-funding-purchases-backend.md))

Полный технический контракт и открытые вопросы к backend: [sale-return-cashflow-backend.md §9.1](./sale-return-cashflow-backend.md#91-переопределение-способа-возврата-денег-реальный-инцидент).
См. также: [scenario-shift-drawer-funding.md](./scenario-shift-drawer-funding.md) — тот же класс проблемы («деньги физически двигались, а система не знает»), но для закупок у поставщика.

---

## 1. Проблема, которую решает сценарий

Система считает, сколько денег должно быть в ящике кассира, по формуле:

```
было на начало смены + наличные продажи − изъятия из ящика = должно быть в ящике
```

Возврат чека, оплаченного **переводом/картой**, по умолчанию считается, что деньги ушли клиенту **тем же способом** — переводом. Поэтому такой возврат **не** уменьшает ожидаемый остаток в ящике: система думает, что наличных кассир никому не отдавал.

Если кассир по факту отдал наличные (а не сделал перевод) — эта сумма физически исчезает из ящика, но нигде не записывается. При закрытии смены получается расхождение (недостача), которое неотличимо от настоящей потери денег.

**Реальный кейс:** клиент купил товар на 1940 сом, оплатил переводом. Вернул чек, тут же купил другой товар на 1450 сом. Разницу — 490 сом — кассир отдал наличными. Расхождение при закрытии смены ~500 сом.

---

## 2. Как этим пользоваться (кассир)

1. Экран продаж → находим чек → **«Возврат»**.
2. Если исходный чек оплачен **любым безналичным способом одним платежом** — картой,
   переводом или конкретным банком (МБанк, Optima, О!Банк, Bakai — всё, что доступно
   на экране оплаты кассира), кроме наличных, долга и split-оплаты — под сводкой по
   чеку появляется отдельная строка:

   ```
   ☐ Деньги фактически отдал наличными (исходная оплата была переводом/картой)
   ```

   Условие проверяется не по конкретному названию банка, а по принципу «способ
   оплаты — не наличные, не долг, не split» — поэтому чекбокс одинаково появится и
   для карты, и для перевода, и для оплаты через МБанк/Optima/О!Банк/Bakai.

3. Если кассир реально отдаёт клиенту наличные из своего ящика — **отмечает чекбокс** перед тем, как нажать «Вернуть весь чек» или «Частичный возврат».
4. Если возврат оформляется как обычно (деньги ушли клиенту тем же переводом/картой, что и пришли) — чекбокс **не трогаем**, оставляем пустым.
5. Подтверждаем возврат (полный или частичный — чекбокс работает в обоих случаях, сумма считается по фактически возвращаемым позициям).

**Когда чекбокса нет:**
- исходная оплата — наличные (тут и так всё уже учитывается верно);
- исходная оплата — чистый долг (деньги никто не платил, возвращать физически нечего);
- чек оплачен split’ом (часть наличными, часть картой) — риск задвоить сумму, чекбокс намеренно скрыт (см. §9.1 документа для backend);
- у кассира нет открытой смены.

## 3. Что происходит технически

Два независимых шага, второй — только если чекбокс отмечен:

**1) Обычный возврат, без изменений:**

```http
POST /main/pos/sales/{sale_id}/return/
{ "idempotency_key": "...", "branch_id": "...", "cashbox_role": "pos_branch" }
```

**2) Только если отмечен чекбокс и шаг 1 прошёл успешно:**

```http
POST /construction/cashflows/
{
  "cashbox": "<id кассы открытой смены>",
  "type": "expense",
  "amount": "1940.00",
  "name": "Возврат наличными (оплата чека была безналом) — чек №a1b2c3d4",
  "status": "approved" | "pending"
}
```

Второй запрос — та же ручная запись кассы, которую backend уже умеет учитывать в `drawer_expected_cash` смены (подтверждено на прошлой фиче, см. [BACKEND-QUESTIONS.md п.51](./BACKEND-QUESTIONS.md)).

Если шаг 1 не удался — шаг 2 не выполняется. Если шаг 2 не удался (сеть, ошибка сервера) — возврат чека **всё равно остаётся оформленным**, кассир видит жёлтое предупреждение:

```
Возврат оформлен, но списание из кассы смены не записалось —
добавьте вручную в «Касса».
```

## 4. Где проверять результат

### 4.1. Сразу после возврата — лента кассы

`/crm/kassa` → выбрать кассу открытой смены кассира → в ленте движений должна появиться новая запись `expense` на сумму возврата, с названием вида «Возврат наличными (оплата чека была безналом) — чек №...».

### 4.2. При закрытии смены

Экран закрытия смены (`CloseShiftPage`) → поле **«Ожидаемая сумма»** (`drawer_expected_cash`) должно быть уменьшено ровно на сумму такого возврата, по сравнению с тем, что было бы без него. Разница между этим полем и фактически пересчитанными наличными (`cash_diff`) — теперь отражает настоящее расхождение, а не забытый возврат.

### 4.3. Отчёты и аналитика

- Отчёт кассы за день/месяц (`/crm/kassa` → карточка кассы → отчёт) — сумма возврата видна как отдельный расход.
- Аналитика «Финансы» — попадает в `expense_total` компании за день.

## 5. Чек-лист ручного прогона (QA)

Числа — из реального инцидента, чтобы сразу видеть, что фикс действительно его закрывает.

| # | Шаг | Ожидание |
|---|---|---|
| 1 | Открыть смену (размен, например, 5379). Продать товар на 1940 сом, оплата — перевод | `drawer_expected_cash` не меняется (продажа безналична) |
| 2 | Вернуть чек полностью, **чекбокс не трогать** | `drawer_expected_cash` не изменился — как и должно быть по умолчанию |
| 3 | То же самое, но с отмеченным чекбоксом «Деньги фактически отдал наличными» | В ленте кассы появилась запись `expense` на 1940; `drawer_expected_cash` уменьшился на 1940 |
| 4 | Частичный возврат 1 позиции из 3 в чеке, оплаченном картой, чекбокс отмечен | Сумма списания = стоимость именно этой позиции, не всего чека |
| 5 | Чек оплачен наличными | Чекбокса нет вообще (обычная логика возврата и так корректна) |
| 6 | Чек оплачен split (нал + карта) | Чекбокса нет — намеренное ограничение, см. §9.1 |
| 7 | Чек в чистый долг, без предоплаты | Чекбокса нет — возвращать физически нечего |
| 8 | У кассира нет открытой смены | Чекбокса нет |
| 9 | Отметить чекбокс, но обрубить сеть перед ответом на шаг 2 (DevTools → offline) | Возврат чека всё равно завершается успешно; кассир видит предупреждение про ручное добавление в «Касса» |
| 10 | Закрыть смену после сценария №3 | `cash_diff` = реальная разница между пересчитанными наличными и `drawer_expected_cash`, без «фантомных» 1940 сом |
| 11 | Чек оплачен конкретным банком (МБанк/Optima/О!Банк/Bakai), не «переводом»/«картой» буквально | Чекбокс появляется точно так же — условие не завязано на конкретное название способа оплаты |

**Проверено на проде (23.09):** полный возврат чека с `payment_method: "mbank"` —
`POST /main/pos/sales/{id}/return/` вернул `200 OK`, `status: "canceled"`. На этом
прогоне и нашли баг п.11 (чекбокс изначально не показывался для банков) — уже
исправлено.

## 6. Что ещё не закрыто (нужен backend)

Сценарий закрывает только одно направление: «оплатили безналом → вернули наличными». Обратный случай («оплатили наличными → вернули переводом») система по-прежнему считает автоматически неправильно (покажет **излишек**, а не недостачу) — фронт не может это исправить без нового поля `refund_method` в API возврата. Подробности и предлагаемый контракт — [sale-return-cashflow-backend.md §9.1](./sale-return-cashflow-backend.md#91-переопределение-способа-возврата-денег-реальный-инцидент).
