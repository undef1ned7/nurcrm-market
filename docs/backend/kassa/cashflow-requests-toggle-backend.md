# Касса: выключатель «Запросы на подтверждение»

**Экран:** `/crm/set` → «Касса» (владелец/админ, любая сфера) — новая секция «Запросы на подтверждение», над существующими полями кода удаления/лимита скидки.
**Статус:** фронт готов (мягкая деградация + авто-одобрение бэклога, см. §5), **бэкенд — ТЗ, не реализовано**.
Префикс: `{host}/api` · TZ: **Asia/Bishkek (UTC+6)**

Читать вместе с: [cashier-settings.md](./cashier-settings.md) (та же модель `MarketCashierSettings`, тот же эндпоинт), [cashflow-edit-cancel-request-backend.md](./cashflow-edit-cancel-request-backend.md), [sale-return-cashflow-backend.md](./sale-return-cashflow-backend.md) (R4 — статус компенсации).

---

## 1. Задача

Сейчас в кассе несколько независимых мест создают `CashFlow` со статусом `pending` («на подтверждение владельцу»), и все они попадают в общий список «Запросы» (`?status=pending&cashbox={id}`):

1. Ручной приход/расход, который добавляет **не‑владелец** (`AddCashFlowsModal` на чекауте, `useKassa`/`handleAddCashbox` в кассе не‑рыночных сфер) — сейчас жёстко `status = role === "owner" ? "approved" : "pending"`.
2. Компенсирующее движение при возврате чека (`pos_sale_return`) — по факту реализации на staging создаётся `pending` (см. [sale-return-cashflow-backend.md](./sale-return-cashflow-backend.md) §R4/RELEASE A3), кроме тарифа «Старт».
3. Заявка на редактирование/отмену уже одобренного движения (`edit-request`/`cancel-request`) — по дизайну **всегда** создаёт `pending`-заявку, независимо от роли (см. [cashflow-edit-cancel-request-backend.md](./cashflow-edit-cancel-request-backend.md)); это единственный способ поменять `approved`-запись.

Часть клиентов не хочет approval-воркфлоу вообще (маленькая команда, один кассир = владелец, либо владелец полностью доверяет кассирам) — для них очередь «Запросы» — чистое трение. Нужен **переключатель на уровне компании**, который отключает создание pending-заявок для всех трёх источников разом и включён **по умолчанию выключенным** (новый дефолт продукта — без approval, если явно не включили).

## 2. Модель данных

Новое поле в существующем singleton `MarketCashierSettings` (см. [cashier-settings.md](./cashier-settings.md) §2 — та же запись `get_or_create(company=request.user.company)`, доступна **всем сферам**, не только «Магазин»):

| Поле | Тип | Описание |
|---|---|---|
| `cashflow_requests_enabled` | `BooleanField(default=False)` | `True` — ручные записи не‑владельца, компенсация возврата и правка/отмена одобренного движения создают `pending`-заявку, ждущую подтверждения владельца/админа. `False` (**default**) — все три источника проводятся немедленно (`approved`) / выполняются напрямую |

Совместимость: поле относится к той же модели, что `delete_item_code`/`max_discount_percent`/`debt_schedule_version`, но **не привязано к сфере «Магазин»** — читать/писать его нужно для компаний любой сферы (услуги, производство и т.д. тоже создают `CashFlow` через кассу).

## 3. Контракт API

### 3.1 `GET /main/pos/cashier-settings/`

Добавить поле в ответ **всем ролям** (не только owner/admin — кассиру нужно знать, ждать ли approval после отправки формы):

```json
{
  "delete_item_code_required": false,
  "max_discount_percent": null,
  "debt_schedule_version": "v2",
  "cashflow_requests_enabled": false
}
```

Нет записи / поле отсутствует → фронт трактует как `false` (см. §5 — совпадает с текущим дефолтом «функции выключены» при недоступном эндпоинте).

### 3.2 `PATCH /main/pos/cashier-settings/`

Доступ: **только `owner`/`admin`** (как остальные поля этой модели).

```json
{ "cashflow_requests_enabled": true }
```

Фронт сейчас всегда шлёт это поле в PATCH (вместе с рыночными полями, если сфера — «Магазин»; для остальных сфер шлётся только оно). Валидация — обычный `bool`, `400` при некорректном типе.

**Ответ 200** — тот же объект, что и `GET`.

## 4. Влияние на бизнес-логику (что должен поменять бэк)

### 4.1 Ручные записи не‑владельца

Точки создания: `POST /construction/cashflows/` (эндпоинт общий, используется и рыночным чекаутом, и кассой прочих сфер).

Текущее правило статуса на фронте — `role === "owner" ? "approved" : "pending"` (и отдельно `isMarket ? "approved" : ...` для сферы «Магазин», это не трогаем). Если бэк **сам** определяет статус при создании (после миграции на `AUTO_CASHFLOWS`, см. [auto-cashflows-backend.md](./auto-cashflows-backend.md)), нужно учитывать `cashflow_requests_enabled`:

```
status = "approved" if (
    actor.role in ("owner", "admin")
    or is_market_sector(company)
    or not settings.cashflow_requests_enabled
) else "pending"
```

Если статус всё ещё присылает фронт явным полем в `POST` — ничего на бэке менять не нужно, фронт уже учитывает флаг (см. §5). Просьба подтвердить, какой вариант в проде.

### 4.2 Компенсация возврата чека (`pos_sale_return`)

См. [sale-return-cashflow-backend.md](./sale-return-cashflow-backend.md) §R4 — сейчас компенсирующий `expense` создаётся `pending` безусловно (кроме тарифа «Старт»). Нужно:

```
compensation_status = "approved" if not settings.cashflow_requests_enabled else "pending"
```

(правило тарифа «Старт» — как было, не меняем; `cashflow_requests_enabled` — дополнительное условие поверх него).

Это меняет уже реализованный на staging код — файл/метод оттуда, где вычисляется статус компенсирующего движения в `_execute_sale_return`.

### 4.3 Правка/отмена одобренного движения (`edit-request` / `cancel-request`)

Это отдельный случай: сейчас `POST .../edit-request/` и `.../cancel-request/` **всегда** создают pending-заявку — это единственный путь изменить `approved`-запись, и это не «лишнее трение», а единственный механизм.

Предлагаемое поведение при `cashflow_requests_enabled = false`:

- **owner/admin** — правка/отмена применяется **сразу**, без заявки. Нужен новый путь (на выбор бэка):
  - **Вариант A.** Те же эндпоинты `edit-request/`/`cancel-request/` при `cashflow_requests_enabled=false` не создают заявку, а сразу применяют изменение к `CashFlow` (эффективно ведут себя как прямой `PATCH`/сторно) и возвращают уже применённый объект вместо `pending`-заявки.
  - **Вариант B.** Новые эндпоинты прямого действия (`PATCH /construction/cashflows/{id}/` уже существует для полей, но не отмены; понадобится что-то вроде `POST /construction/cashflows/{id}/cancel/` без approval-шага) — owner/admin вызывает их напрямую, старые `*-request/` эндпоинты трогать не нужно.
- **остальные роли** — доступ к правке/отмене `approved`-записи остаётся закрыт (кнопки на фронте скрыты) независимо от флага; включение флага не должно расширять права кассира, оно только снимает обязательность approval для действий, которые и так разрешены его роли.

**Открытый вопрос к бэку (блокирует реализацию §4.3):** какой вариант (A/B) предпочтителен? Пока ответа нет, фронт при `cashflow_requests_enabled=false` просто скрывает кнопки «Изменить»/«Отменить» — редактирование одобренного движения станет недоступно из UI до реализации одного из вариантов (это не регресс: сегодня `VITE_CASHFLOW_CHANGE_REQUESTS` выключен в проде, значит кнопок и так ещё нет нигде, кроме staging).

### 4.4 Бэклог уже существующих pending-заявок

У части компаний в очереди «Запросы» уже висят старые pending-записи (созданные до этой настройки, когда approval был обязателен всегда). Поскольку новый дефолт `cashflow_requests_enabled=false` — эти компании внезапно получают выключенный approval, но зависший бэклог остаётся не подтверждён, если его не разгрести отдельно.

**Реализовано на фронте** (см. §5.7) — без ожидания бэкенда: как только клиент определяет `cashflow_requests_enabled=false`, он сам одним пакетным вызовом одобряет весь текущий pending-бэклог компании, тем же эндпоинтом `PATCH /construction/cashflows/bulk/status/`, которым пользуется ручная кнопка «Одобрить» на экране «Запросы». Это касается **всех источников**, включая заявки на правку/отмену (одобрение `edit-request` применяет предложенные значения, `cancel-request` — сторнирует движение — как и при ручном одобрении).

Это самодостаточное решение и не требует отдельной миграции на бэке — но если на бэке есть **собственные** батчевые джобы/скрипты, которые трогают статусы `CashFlow` пачками, стоит убедиться, что они не конфликтуют с этим фронтовым авто-одобрением (гонка при одновременном изменении одной записи). Значимых доработок бэка для этого пункта не требуется, если `PATCH .../bulk/status/` и `edit-request`/`cancel-request` уже ведут себя идемпотентно при повторном вызове на уже обработанной записи (ожидаем `200`/no-op, а не `500`).

## 5. Поведение фронта (уже реализовано)

1. Флаг читается через тот же `GET /main/pos/cashier-settings/`, что и остальные настройки кассы (`src/shared/api/marketCashierSettings.ts`, `src/entities/cash/model/cashSlice.ts` — `fetchCashflowRequestsSetting`). Ошибка/нет поля → `false` (мягкая деградация, как и другие поля этой модели).
2. `AddCashFlowsModal` (чекаут) и `useKassa`/`handleAddCashbox` (касса не‑рыночных сфер) больше не ставят `pending` для не‑владельца, если `cashflow_requests_enabled === false` — сразу `approved`.
3. Вкладка/пункт «Запросы» в кассе не‑рыночных сфер скрывается, если флаг выключен (условие объединено с уже существующей проверкой тарифа «Старт»).
4. Кнопки «Изменить»/«Отменить» на одобренном движении (`FlowChangeRequestModal`) показываются только при **одновременно** включённых: фичефлаге `VITE_CASHFLOW_CHANGE_REQUESTS` (глобальный кил-свитч выката) **и** `cashflow_requests_enabled` (настройка компании).
5. Настройки (`/crm/set` → «Касса») — новая секция-переключатель видна владельцу/админу **любой** сферы (раньше вкладка была доступна только сфере «Магазин»); поля кода удаления/лимита скидки/отсрочки долга остаются видны только сфере «Магазин», как было.
6. Компенсация возврата чека (§4.2) — фронт ничего не решает, статус приходит с бэка; см. открытый пункт ниже.
7. **Авто-одобрение бэклога** (`autoApprovePendingCashflows`, `src/entities/cash/model/cashSlice.ts`) — срабатывает автоматически при загрузке кассы/страницы «Запросы» (из `fetchCashflowRequestsSetting`, один раз за сессию вкладки), если `cashflow_requests_enabled=false`: постранично собирает все `status=pending` записи компании (`GET /construction/cashflows/?status=pending`) и одобряет их одним `PATCH .../bulk/status/`. Ничего не спрашивает у пользователя — тихая фоновая операция. Ошибки (сеть, 403 у не-owner-сессии) проглатываются молча, без ретраев в рамках той же сессии.
