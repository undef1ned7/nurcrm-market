# Долг v2: частичная оплата, просрочка остатка, перенос срока и «обещанная дата»

**Экран:** карточка клиента/поставщика → модалка «Долг» (`DebtModal.tsx`) → график платежей.
**Статус:** фронт реализован (2026-10-02), **ждёт бэк**: п.2 (новый эндпоинт) и п.3 (`promised_date` в ответе). Пп.1 и 4 работают на текущем контракте.
**Связано:** [debt-v2-backend-implementation.md](./debt-v2-backend-implementation.md), [debt-pay-arbitrary-amount-backend.md](./debt-pay-arbitrary-amount-backend.md), [auto-cashflows-backend.md](./auto-cashflows-backend.md). Только **v2**-долги (`schedule_version: "v2"`).

---

## Сценарий

Покупатель взял в долг, срок взноса — 1-е число. Сказал «оплачу 1-го с зарплаты», зарплату не выдали. Пришёл и отдал **500 сом** из, допустим, 1000 со словами «остальное верну 5-го».

Чего не хватало:

| # | Проблема | Решение |
|---|----------|---------|
| 1 | Взнос с частичной оплатой и прошедшим сроком показывался как «Частично оплачен», просрочка остатка терялась | Фронт: просрочка считается независимо от частичной оплаты (бэку ничего не нужно, но см. §1 — нужны единые правила) |
| 2 | После первой оплаты график **заблокирован** (правка только `title`/`note`) — нельзя сдвинуть срок остатка | Новый эндпоинт переноса срока по одному взносу, работающий **после** оплат (§2) |
| 3 | Негде зафиксировать «обещал 5-го» без изменения графика | Поле `promised_date` у взноса (§3) |
| 4 | Дата оплаты в `pay/` всегда «сегодня» | Фронт теперь шлёт выбранную дату (§4) — бэк должен её принимать |

Пени/штрафы **не делаем** — см. вопрос Q4.

## 1. Просрочка и частичная оплата — правила (согласовать с фронтом)

Взнос считается **просроченным**, если одновременно:

- `paid_on` пуст (не закрыт полностью), и
- `due_date < сегодня` (TZ **Asia/Bishkek**).

Это верно и для взноса с `paid_amount > 0` (частично оплачен). Просрочена **остаточная** часть: `amount − paid_amount`. Фронт показывает такой взнос бейджем «Частично оплачен» + «Просрочен · N дн.»; `N = сегодня − due_date` в днях.

**Просьба к бэку:** везде, где бэк определяет просрочку (ночной cron `market.debt.overdue`, список/KPI долгов, `remaining_overdue`-агрегаты, если есть), использовать то же правило — частично оплаченный взнос с прошедшим сроком **считается просроченным**, пока `paid_on` не выставлен. Сумма просрочки в агрегатах = сумма остатков таких взносов.

Опционально (удобно, но не блокер) — отдавать вычисленные поля в `installments[]`, чтобы фронт не дублировал логику:

```json
{
  "is_overdue": true,
  "overdue_days": 4,
  "overdue_amount": "500.00"
}
```

Пока их нет, фронт считает сам по `due_date`/`paid_on`.

## 2. Перенос срока по взносу — **NEW**

```http
PATCH /main/clients/{clientId}/deals/{dealId}/installments/{installmentId}/
```

```json
{
  "idempotency_key": "<uuid>",
  "due_date": "2026-10-05",
  "promised_date": "2026-10-05",
  "note": "Вернёт с зарплаты"
}
```

Все поля, кроме `idempotency_key`, опциональны, но **минимум одно из** `due_date` / `promised_date` / `note` обязательно (иначе `400`). Фронт шлёт только изменённые поля.

| Поле | Тип | Смысл |
|------|-----|-------|
| `due_date` | `YYYY-MM-DD` | Новый **срок по графику**. Меняет график: просрочка пересчитывается от новой даты. |
| `promised_date` | `YYYY-MM-DD` \| `null` | Дата, до которой клиент **обещал** заплатить. График и просрочка **не меняются**. `null` — снять обещание. |
| `note` | string | Комментарий (причина переноса). Пишется в историю изменений взноса. |

### Правила

1. **Доступно после оплат.** В отличие от `PATCH /deals/{id}/` (где при наличии платежей меняются только `title`/`note`), этот эндпоинт работает **всегда**, пока взнос не закрыт полностью.
2. Взнос с `paid_on != null` → `409`/`400` (`installment_already_paid`).
3. Менять можно только `due_date`/`promised_date`/`note` **одного** взноса. `amount`, `number`, `paid_amount` — не трогать; другие взносы сделки **не сдвигаются автоматически** (если нужен каскад — Q2).
4. `due_date` и `promised_date` не раньше сегодняшней даты (Asia/Bishkek) → иначе `400` (фронт тоже блокирует, но бэк не должен полагаться на клиента). Сдвиг срока **назад** относительно текущего `due_date`, но не в прошлое — разрешён.
5. Порядок взносов не проверяем: `due_date` может оказаться раньше `due_date` предыдущего взноса (допускается любое значение ≥ сегодня; пересортировка по `number` — Q2).
6. `promised_date` не ограничиваем сверху (может быть позже последнего `due_date` графика).
7. Сохранять историю: кто, когда, старое → новое значение `due_date`/`promised_date`, `note`. (Нужна для споров «мы договаривались на 5-е».)
8. Идемпотентность — как у `pay/`: повтор с тем же `idempotency_key` возвращает тот же результат, историю не дублирует.
9. **Кассовых движений нет** — операция не двигает деньги.
10. Права: те же, что у редактирования долга / оплаты (кассир с доступом к долгу).
11. `due_date` сделки `first_due_date` и `daily_payment`/`monthly_payment` **не пересчитывать**; `first_due_date` остаётся датой первого взноса исходного графика.

### Ответ `200`

Обновлённая сделка целиком (как у `pay/`), фронт перечитывает через `GET`, но может использовать ответ напрямую:

```json
{
  "id": "991d6ff0-...",
  "remaining_debt": "500.00",
  "installments": [
    {
      "id": "…",
      "number": 1,
      "amount": "1000.00",
      "paid_amount": "500.00",
      "paid_on": null,
      "due_date": "2026-10-05",
      "promised_date": null,
      "is_overdue": false
    }
  ]
}
```

### Ошибки

| Код | `code` | Когда |
|-----|--------|-------|
| 400 | `nothing_to_change` | не передано ни одного из `due_date`/`promised_date`/`note` |
| 400 | `date_in_past` | `due_date` или `promised_date` < сегодня |
| 404 | — | взнос не принадлежит этой сделке/клиенту/компании |
| 409 | `installment_already_paid` | взнос закрыт полностью |
| 409 | `deal_not_v2` | сделка v1 (график одной датой — переносится существующим `PATCH /deals/{id}/` до первой оплаты) |

## 3. `promised_date` в `installments[]`

Новое поле в каждом взносе (`GET /deals/{id}/`, ответы `pay/`, `PATCH installment`):

```json
{ "number": 1, "due_date": "2026-10-01", "promised_date": "2026-10-05", "...": "..." }
```

- `null` по умолчанию.
- Фронт показывает под сроком «Обещано: 05.10.2026»; если обещанная дата **прошла**, а взнос не закрыт — красным «Обещание не выполнено: 05.10.2026».
- Когда взнос закрыт полностью (`paid_on`) — `promised_date` можно оставить в истории, но в UI не показывается.
- При частичной оплате **не сбрасывать** `promised_date` автоматически (покупатель обещал вернуть остаток к этой дате).
- В списке просроченных долгов (cron/уведомления) желательно **не** слать повторное «просрочено», пока не наступил `promised_date` (Q3).

## 4. Фактическая дата оплаты в `pay/`

Фронт в диалоге оплаты теперь даёт выбрать **«Дата оплаты»** (по умолчанию сегодня, **не позже** сегодня). Уходит в существующее поле `date`:

```http
POST /main/clients/{clientId}/deals/{dealId}/pay/
```
```json
{
  "idempotency_key": "<uuid>",
  "installment_id": "<uuid>",
  "amount": "500.00",
  "date": "2026-10-01",
  "payment_method": "cash"
}
```

Что нужно от бэка:

1. Принимать `date` ≤ сегодня; `date` > сегодня → `400`. Раньше `date` в основном совпадал с сегодняшним, поэтому проверьте, что бэк его реально использует, а не подменяет `now()`.
2. `paid_on` взноса и дата платежа в истории = переданная `date`.
3. **Дата кассового движения** (`CashFlow`) — решает бэк (см. [auto-cashflows-backend.md](./auto-cashflows-backend.md)): либо фактическое время создания (деньги физически внесены сегодня, **рекомендуем**, чтобы не ломать сверку смены), либо `date`. Главное — не создавать движение в закрытой смене задним числом. Задокументируйте выбор: фронт cashflow'ы не создаёт (решение 2026-09-29: движения создаёт бэк).
4. Просрочка пересчитывается от `date` платежа: взнос, оплаченный `date ≤ due_date`, — не просрочен, даже если внесён в систему позже срока.

## 5. Тест-кейсы для приёмки

| # | Сценарий | Ожидание |
|---|----------|----------|
| 1 | Взнос 1000, срок 1-е, на 3-е оплачено 500 (`amount: "500.00"`) | `paid_amount=500`, `paid_on=null`, остаток 500, `is_overdue=true`, `overdue_days=2`, `overdue_amount=500` |
| 2 | То же, затем `PATCH installment` `{due_date: "5-е"}` | `due_date=5-е`, `is_overdue=false`, платёж и `paid_amount` не тронуты, в истории запись «1-е → 5-е» |
| 3 | `PATCH` `{promised_date: "5-е"}` при `due_date` 1-е | `due_date` прежний (просрочен), `promised_date=5-е`; график/суммы не изменены |
| 4 | `PATCH` `{promised_date: null}` | обещание снято |
| 5 | `PATCH` на полностью оплаченный взнос | `409 installment_already_paid` |
| 6 | `PATCH` `{}` | `400 nothing_to_change` |
| 7 | `PATCH` `{due_date: вчера}` | `400 date_in_past` |
| 8 | `PATCH` с тем же `idempotency_key` дважды | один результат, одна запись в истории |
| 9 | `PATCH` взноса чужой сделки / другой компании | `404` |
| 10 | `PATCH` для сделки v1 | `409 deal_not_v2` |
| 11 | `pay/` с `date` в будущем | `400` |
| 12 | `pay/` с `date` = 1-е (срок 1-е), вносим 3-го | `paid_on=1-е`, просрочки по этому платежу нет |
| 13 | После оплаты 500 и переноса на 5-е: на 5-е оплата остатка 500 | взнос закрыт, `paid_on=5-е`, `remaining_debt=0` |
| 14 | Cron `market.debt.overdue` на взнос из п.1 | уведомление приходит (частичная оплата не отключает просрочку) |
| 15 | `PATCH` не создаёт `CashFlow` | кассовых движений нет |

## Открытые вопросы к бэкенду

| # | Вопрос |
|---|--------|
| Q1 | Отдаёте ли вычисленные `is_overdue` / `overdue_days` / `overdue_amount` в `installments[]`? Тогда фронт переключится на них (сейчас считает сам). |
| Q2 | Перенос `due_date` одного взноса — только его, или давать флаг `shift_following: true` (сдвинуть на то же число дней все последующие неоплаченные взносы)? Фронт пока **не** шлёт каскад; нужно ли — решать продуктово. |
| Q3 | Подавлять ли ночное уведомление `market.debt.overdue`, пока `promised_date >= сегодня`? Предлагаем: подавлять, а в день после `promised_date` слать «обещание не выполнено». |
| Q4 | Пени/штрафы за просрочку (процент в день, фиксированная сумма) — нужны ли? Фронт **не реализован**: нужна продуктовая постановка (ставка по компании/сделке, начисление отдельным взносом или в `remaining_debt`, обнуление при переносе срока). |
| Q5 | Бэк поддерживает `date` ≠ сегодня в `pay/` для `paid_on`, и какую дату получает `CashFlow` (см. §4.3)? |
| Q6 | Нужен ли отдельный endpoint истории изменений срока взноса (`GET .../installments/{id}/history/`)? Фронт пока историю не показывает. |
