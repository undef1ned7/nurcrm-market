# Фильтр «Кассир» в списке продаж смены (`/crm/shifts/{id}`)

**Экран:** `/crm/shifts/{id}` → вкладки «Движение товаров» и «Движение денег» (`ShiftDetail.tsx`) → `FilterBar`.
**Статус:** ✅ **выкачено и на фронте, и на бэке.** BE подтвердил и реализовал Q1–Q3 из §4: параметр `cashier` (можно несколько через запятую) на `GET .../shifts/{id}/sales/`, `page_size` до 500 (раньше был жёстко зафиксирован на 100), `cashier_id` в каждой продаже и готовый `cashier_breakdown` в ответе смены. Фронт переведён на серверную фильтрацию — раздел §6 ниже.

Читать вместе с: [shift-sale-positions-backend.md](./shift-sale-positions-backend.md) (тот же экран, тот же список продаж), [auto-cashflows-backend.md](./auto-cashflows-backend.md) (модель кассы/смены).

---

## 1. Контекст

Клиент компании работает с **одной физической кассой** — на неё нет разделения по филиалам, и намеренно ожидается **одна открытая смена на всех кассиров** (не отдельная смена на каждого сотрудника — см. обсуждение в тикете поддержки). При этом несколько сотрудников по очереди пробивают чеки в рамках одной и той же смены, и владельцу нужно посмотреть, **кто из кассиров сколько продал** внутри общей смены — без разделения самой смены/кассы.

Решение: смена и касса остаются общими; в интерфейсе смены добавляется **фильтр по кассиру** поверх уже существующих `status` / `payment_method` / `q`.

## 2. Как это работает на фронте теперь (после ответа BE)

Файл: `src/pages/shifts/ui/ShiftDetail.tsx`.

1. Список продаж смены грузится с сервера уже отфильтрованным — `GET /construction/cash/shifts/{shiftId}/sales/` с параметрами `status`, `payment_method`, `q`, **`cashier`** (id, из выбора в выпадашке) и `page_size=500` (см. `fetchShiftSalesAsync`, `src/entities/shift/model/shiftThunk.tsx:114-131`).
2. Список кассиров для выпадающего списка (обе вкладки — «Товары» и «Деньги» используют один и тот же список) строится из `shift.cashier_breakdown` — готовой разбивки в ответе `GET /construction/shifts/{id}/`, а не из уже загруженной страницы продаж. Так видны все кассиры смены независимо от текущих `status`/`q`, и без похода на `/users/employees/`.
3. Клиентской фильтрации по `cashier_display` больше нет — весь фильтр отрабатывает на бэке через `cashier=<id>`.

## 3. Ограничения старого (клиентского) решения — закрыты

До ответа BE фильтр работал клиентски (по `cashier_display`, только на первой странице списка). Это создавало три проблемы — все три закрыты доработкой бэка:

| # | Проблема | Как закрыто |
|---|---|---|
| L1 | Грузилась только первая страница — кассир со 2-й страницы мог не попасть в фильтр. | `page_size` теперь до 500 (было жёстко 100) — типовая смена умещается в один запрос; сам фильтр всё равно теперь серверный и от постраничной загрузки не зависит. |
| L2 | Фильтрация по `cashier_display` (строке) — тёзки смешивались. | Есть `cashier_id` в каждой продаже и в `cashier_breakdown` — фильтр и опции строятся по id. |
| L3 | Фильтрация в браузере после получения всех данных. | `cashier=<id>` теперь параметр запроса — бэк отдаёт уже отфильтрованный список. |

## 4. Что было нужно от бэкенда — ✅ сделано (Q1–Q3)

### 4.1 Обязательно

| # | Запрос | Описание |
|---|---|---|
| Q1 | `GET /construction/cash/shifts/{shiftId}/sales/?cashier={id}` | Добавить параметр `cashier` (id сотрудника) к уже существующим `status`/`payment_method`/`date_from`/`date_to`/`ordering`/`q` на этом эндпоинте. Фильтрация — по продавцу конкретного чека (полю, из которого сейчас формируется `cashier_display`), а не по владельцу смены (`shift.cashier`) — в общей смене это разные вещи. |
| Q2 | Стабильный `id` кассира в каждом объекте продажи списка | Сейчас фронт использует только `cashier_display` (строка). Нужно поле вида `cashier_id` (или `cashier: {id, full_name}` объектом) в ответе `GET /construction/cash/shifts/{id}/sales/`, чтобы фильтровать/группировать по id, а не по совпадению имени. |
| Q3 | Список кассиров для выпадающего списка фильтра | Подтвердить: можно ли переиспользовать существующий `GET /users/employees/?is_active=1` (уже используется в Аналитике для похожего фильтра — `src/entities/sale/api/saleConsultants.ts:23-41`) для построения списка кассиров смены, или нужен отдельный источник (например, «кассиры, у которых есть продажи в этой смене» отдельным полем в ответе смены)? |

### 4.2 Опционально — агрегаты по кассиру

Если не сложно, было бы полезно сразу отдавать разбивку по кассирам в ответе смены (`GET /construction/shifts/{id}/`), аналогично уже существующему `payment_breakdown` ([shift-payment-breakdown-backend.md](./shift-payment-breakdown-backend.md)):

```json
"cashier_breakdown": [
  { "cashier_id": "db063122-...", "cashier_display": "Балнура Мыломойка", "sales_count": 12, "sales_total": "4500.00" },
  { "cashier_id": "a1b2c3d4-...", "cashier_display": "Аман",              "sales_count": 5,  "sales_total": "1200.00" }
]
```

Это избавило бы фронт от необходимости прогонять весь список продаж смены через клиентскую агрегацию (как сейчас сделано для `payment_breakdown` при отсутствии бэкового поля — см. `resolveShiftPaymentBreakdown`).

## 6. Тест-кейсы для приёмки

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | `GET .../sales/?cashier={id}` для кассира с продажами в смене | Возвращаются только его продажи, `count` соответствует его фактическому числу чеков |
| 2 | `GET .../sales/?cashier={id}` для кассира без продаж в этой смене | `count: 0`, `results: []`, не 404/500 |
| 3 | `cashier` + `status`/`payment_method`/`q` одновременно | Фильтры комбинируются через AND, как остальные параметры этого эндпоинта |
| 4 | Два сотрудника с одинаковым `full_name`, разный `cashier_id` | Фильтр по `cashier` разделяет их корректно (проверяет Q2) |
| 5 | Смена с >1 страницы продаж, фильтр по кассиру со 2-й страницы (по старой клиентской логике) | После доработки (Q1) — кассир находится сразу через параметр, без пролистывания страниц |

## 7. Статус

✅ Закрыто с обеих сторон. Фронт больше не хранит и не фильтрует список кассиров на клиенте — источник истины полностью на бэке (`cashier_breakdown`, `cashier=<id>`, `page_size`).
