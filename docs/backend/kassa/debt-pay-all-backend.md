# «Оплатить весь долг» одной кнопкой — модалка «Долг» (/crm/clients/{id})

**Экран:** карточка клиента/поставщика → модалка «Долг» (`DebtModal.tsx`) → график платежей.
**Статус:** фронт реализован **сегодняшними средствами** (цикл по существующему `pay/`); этот документ — предложение бэку добавить настоящий bulk-эндпоинт, чтобы упростить и ускорить операцию.

---

## Что уже работает на фронте (без изменений бэка)

Кнопка «Оплатить весь долг (N сом)» появляется в модалке, когда есть хотя бы один неоплаченный/частично оплаченный взнос (`installments[]`). По клику — подтверждение суммы, затем фронт **последовательно** вызывает уже существующий контракт для каждого незакрытого взноса:

```
POST /main/clients/{clientId}/deals/{dealId}/pay/
{
  "idempotency_key": "<uuid>",   // новый на каждый вызов
  "installment_id": "<installment uuid>",
  "date": "2026-09-04"
  // amount не передаём — как при обычной оплате «на всю сумму взноса»
}
```

После каждого успешного вызова — `postCashflowIfNeeded` с `source_cashbox_flow_id = installment.number` (тот же паттерн, что и у одиночной оплаты по кнопке в строке). Если один из вызовов упал — цикл останавливается, показывается «Оплачено X из N платежей», пользователь может нажать кнопку ещё раз для продолжения (уже оплаченные взносы не пересылаются повторно — фильтруются по `paid_on`/остатку).

Это **соответствует уже задокументированному контракту** (`docs/backend/kassa/debt-v2-backend-implementation.md`, §7.3: «Без изменений контракта; оплата по `installment_id`»), поэтому бэк ничего делать не обязан — фича уже рабочая.

---

## Зачем всё-таки нужен bulk-эндпоинт

Для долга с ежедневным графиком (`debt_days`) незакрытых взносов может быть **десятки** (30, 60, 90). Текущий цикл на фронте означает:

- N последовательных HTTP-запросов подряд (медленно, десятки секунд на слабом интернете);
- N отдельных платёжных записей и (при `AUTO_CASHFLOWS`) N записей в кассе на одну и ту же операцию «клиент погасил долг» — шумно для бухгалтерии/отчётов;
- **не атомарно**: если запрос №15 из 30 упадёт по сети — 14 взносов уже оплачены, 16 нет. Пользователю показываем частичный результат и просим повторить — приемлемо, но не идеально.

## Предлагаемый контракт

```
POST /main/clients/{clientId}/deals/{dealId}/pay-all/
{
  "idempotency_key": "<uuid>",
  "date": "2026-09-04",
  "amount": "1234.56"   // опционально: сколько именно платим (≤ remaining_debt).
                         // без поля — гасим remaining_debt целиком.
}
```

Поведение:

1. Распределить `amount` (или весь `remaining_debt`, если поле не передано) по незакрытым взносам **от самого раннего к самому позднему** (`due_date` ASC), закрывая каждый полностью, пока сумма не исчерпана; последний частично захваченный взнос получает остаток.
2. Одна транзакция в БД — либо применяется полностью, либо откатывается целиком при ошибке (то, чего не может дать цикл на фронте).
3. Создать **одну** запись платежа/кассового движения на всю операцию (а не по одной на взнос) — либо задокументировать, что бэк создаёт N записей (по одной на закрытый взнос) намеренно для трассируемости; в этом случае фронту не нужно будет самому звать `postCashflowIfNeeded` в цикле.
4. Ответ — обновлённый `deal` целиком: `remaining_debt`, `installments[]` с новыми `paid_amount`/`paid_on`/`balance_after` для каждого — фронт использует их напрямую вместо повторного `GET`.
5. `amount > remaining_debt` → 400. `remaining_debt == 0` → 400 (нечего платить).
6. Идемпотентность — как у `pay/`: повтор с тем же `idempotency_key` не должен задвоить оплату.

## Если добавите — что поменяет фронт

- Кнопка «Оплатить весь долг» вызовет один `POST .../pay-all/` вместо цикла.
- Один `postCashflowIfNeeded` вместо N — если бэк не берёт создание кассового движения на себя целиком (см. п.3 выше, нужно определиться).
- Уберётся код частичного отката/сообщения «оплачено X из N» — операция станет all-or-nothing на уровне одного запроса.

## Не блокер

Реализация bulk-эндпоинта не блокирует текущую фичу — она уже работает через цикл. Приоритет — по усмотрению бэка (актуально в первую очередь для клиентов с длинными ежедневными графиками).
