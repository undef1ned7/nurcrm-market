# Поиск продаж по штрих-коду

**Страница:** `/crm/market/history` («Продажи» в меню) — `src/pages/sales-history/ui/History.tsx`
**Статус фронта:** готово — новый фильтр отправляется как `barcode` в уже существующий запрос списка
**Статус бэка:** требуется реализация (параметр не поддержан)
Префикс: `{host}/api` · TZ: **Asia/Bishkek (UTC+6)**

---

## 1. Зачем

В разделе «Продажи» кассир/владелец видит список чеков, но не может найти **все продажи, в
которых был конкретный товар** (по штрих-коду) — например, чтобы проверить, сколько раз
продали товар с определённым штрих-кодом, или найти чек по штрих-коду с ценника при споре с
клиентом.

---

## 2. Что уже делает фронт

Страница уже фильтрует список через query-параметры на существующем эндпоинте:

```http
GET /main/pos/sales/?status=&start=&end=&consultant=
```

Добавлен новый параметр, отправляется всегда вместе с остальными фильтрами (debounce 400мс
после ввода):

```http
GET /main/pos/sales/?barcode=4601234567890
```

Поле необязательное — при пустом значении ведёт себя как сейчас (параметр не отправляется).

---

## 3. Что нужно от бэка

`GET /main/pos/sales/` — принимать `barcode` (string) и возвращать **только те продажи, у
которых хотя бы одна строка (`SaleItem`) имеет совпадающий штрих-код** — основной
(`barcode_snapshot`/`product.barcode`) или дополнительный (`alternate_barcodes`, см.
[alternate-barcodes.md](../alternate-barcodes.md)). Остальные фильтры (`status`, `start`,
`end`, `consultant`) применяются одновременно (AND), как сейчас.

Совпадение — точное (`==`), не `contains`: штрих-код — точный идентификатор товара, частичный
поиск не нужен и рискует давать ложные совпадения по префиксу.

### Желательно (не блокер): `matched_item_name`

Каждый элемент списка — добавить `matched_item_name`: название позиции, которая совпала по
штрих-коду (когда `barcode` передан в запросе). Если в чеке несколько строк с этим штрих-кодом
(редко, но возможно при повторном сканировании одного товара несколькими позициями) — взять
первую. Фронт уже показывает это поле отдельной колонкой «Найденный товар» (только когда поиск
по штрих-коду активен):

```json
{
  "id": "uuid",
  "created_at": "2026-09-11T10:20:00+06:00",
  "status": "paid",
  "total": "450.00",
  "matched_item_name": "Молоко 1 л"
}
```

Без этого поля фильтр всё равно работает — просто колонка не показывает конкретную позицию,
кассиру нужно открыть чек и посмотреть список товаров самому.

---

## 4. Поведение до выката BE

Пока бэк не поддерживает `barcode` — если параметр молча игнорируется (обычное поведение
Django REST Framework для незнакомого query-параметра), список вернётся **без фильтрации** —
фронт покажет все продажи, а не только совпавшие. Это единственный риск P0: пользователь может
не заметить, что фильтр не сработал. Если проще сделать `400` на неизвестный параметр —
фронт это тоже переживёт (`loadError`, список просто не обновится) — оба варианта приемлемы,
предпочтительнее фильтрация (первый).

---

## 5. Тест-сценарии

1. Чек с товаром, штрих-код `4601234567890` → `GET ?barcode=4601234567890` возвращает этот чек.
2. Чек без этого товара → не попадает в выборку.
3. Товар был продан по дополнительному штрих-коду (`alternate_barcodes`) → чек находится так же,
   как по основному.
4. `barcode` + `status=paid` вместе → пересечение (AND), не объединение.
5. Несуществующий штрих-код → `200`, пустой `results: []`, не `404`.
6. Штрих-код с пробелами по краям (случайный ввод/скан) → бэк триммит перед сравнением.
