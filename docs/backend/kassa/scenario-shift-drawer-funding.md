# Сценарий: «Оплачено из кассы (ящика) смены»

**Аудитория:** QA, бэкенд, владелец продукта
**Фронт:** реализовано и включено для всех, без флага
**Бэкенд:** доработок не требуется — используется существующий ручной эндпоинт `/crm/kassa`

Полный технический контракт: [shift-drawer-funding-purchases-backend.md](./shift-drawer-funding-purchases-backend.md).
См. также: [shift-cash-reconciliation-backend.md](./shift-cash-reconciliation-backend.md) (формула `drawer_expected_cash`), [auto-cashflows-backend.md](./auto-cashflows-backend.md) (модель кассы/cashflow).

---

## 1. Проблема, которую решает сценарий

Кассир открывает смену, в течение дня принимает приход товара от поставщика (или платит по долгу поставщику, принимает pending-позиции) и **платит наличными прямо из своего кассового ящика** — а не откуда-то ещё. До этой фичи система об этом не знала: такие операции всегда шли на кассу «Переменные расходы» и никак не влияли на `drawer_expected_cash` смены. При закрытии смены кассир видел недостачу, которую не мог объяснить — деньги реально потрачены, а в отчёте по смене это нигде не показано.

Реальный кейс, который и стал поводом для фичи (см. §«Симптом» в [shift-cash-reconciliation-backend.md](./shift-cash-reconciliation-backend.md)): размен 50 сом, наличные продажи 33 768 сом, закупки наличными 54 625 сом — из той же кассы, что и ящик кассира. Без этой фичи разница просто повисает как «расхождение», без указания причины.

## 2. Сквозной сценарий (кассир, одна смена)

```
09:00  Кассир открывает смену, вносит размен 500 сом
10:15  Продажа клиенту, оплата наличными 1 500 сом
11:40  Приезжает поставщик, кассир принимает приход на 3 000 сом
       и расплачивается наличными прямо из ящика кассы
18:00  Кассир закрывает смену
```

### 2.1. Открытие смены

Без изменений — см. [SCENARIO-POST-MIGRATION.md §2.2](./SCENARIO-POST-MIGRATION.md#22-открытие-смены-кассир).

```http
POST /construction/shifts/open/
{ "opening_cash": "500.00", "branch_id": "...", "cashbox_role": "pos_branch" }
```

### 2.2. Продажа (без изменений)

```http
POST /main/pos/sales/{id}/checkout/
{ "payment_method": "cash", "shift_id": "<shift_id>", ... }
```

`drawer_expected_cash` после этого шага: `500 + 1500 = 2000`.

### 2.3. Приход поставщика — ключевой шаг сценария

Кассир открывает «Приход поставщика» (`/crm/sklad` → приход), заполняет накладную на 3 000 сом, тип оплаты — «Наличные». Так как у него есть открытая смена и система смогла определить её кассу, под полем оплаты появляется чекбокс:

```
☐ Я заплатил из кассы (ящика) смены — спишется с кассы «Касса филиала №1»
```

Кассир его отмечает и подтверждает приход.

**Что происходит технически — два независимых запроса:**

**1) Обычный приход, без изменений** (создаёт expense на «Переменные расходы», не влияет на смену):

```http
POST /main/suppliers/{supplier_id}/receipt/
{
  "items": [...],
  "payment_type": "cash",
  "cashbox_role": "expense_variable"
}
```

**2) Только если чекбокс отмечен и запрос (1) прошёл успешно — ручная запись на кассу самой смены:**

```http
POST /construction/cashflows/
{
  "cashbox": "<id кассы открытой смены>",
  "type": "expense",
  "amount": "3000.00",
  "name": "Приход поставщика — оплата из кассы смены: ООО Ромашка",
  "status": "approved"
}
```

Backend уже учитывает такие ручные записи на кассе смены в `drawer_expected_cash` (флаг `affects_shift_drawer`, подтверждено в [BACKEND-QUESTIONS.md, п. 51](./BACKEND-QUESTIONS.md)) — никакой дополнительной логики не требуется.

Если чекбокс **не** отмечен — второй запрос не отправляется вообще, поведение как раньше: закупка полностью «уходит» на `expense_variable` и в ящике смены не видна.

Если чекбокс отмечен, но второй запрос упал (сеть, 4xx/5xx) — приход **остаётся оформленным** (откат первой операции не делается), кассир видит предупреждение:

```
Товары оприходованы, но списание из кассы смены не записалось —
добавьте вручную в «Касса».
```

### 2.4. Закрытие смены

```http
POST /construction/shifts/{id}/close/
{ "closing_cash": "2000.00" }
```

`drawer_expected_cash = opening_cash + cash_sales_total − shift_drawer_outflows = 500 + 1500 − 3000 = -1000`... в реальности размен+продажи обычно перекрывают такую закупку, но суть в том, что **теперь эта сумма фигурирует в расчёте явно**, а не как необъяснённая недостача. Кассир видит ожидаемый остаток, который уже учитывает его собственное решение заплатить из ящика, и `cash_diff` при сверке отражает только настоящее расхождение (ошибка пересчёта, недостача и т.п.), а не забытую закупку.

## 3. Где ещё в интерфейсе есть этот чекбокс

Механика (§2.3) идентична во всех точках — единственное отличие: что именно создаётся первым запросом и как считается сумма.

| # | Экран | Первый запрос (без изменений) | Когда виден чекбокс |
|---|---|---|---|
| 1 | Приход поставщика (`SupplierReceiptPage`) | `POST /main/suppliers/{id}/receipt/` | оплата наличными или предоплата |
| 2 | Склад → быстрое добавление товара (`AddModal`) | `POST /main/products/create-manual/` | закупка не в долг |
| 3 | Карточка товара → приход (`AddProductModal`) | `PATCH /main/products/{id}/` или `.../receipt/` | оплата не «в долг» |
| 4 | Полная форма «Добавить товар» (`AddProductPage`) | `POST /main/products/create-manual/` | закупка не в долг |
| 5 | Добавление по штрихкоду (`AddProductBarcode`) | `POST /main/products/create-by-barcode/` | закупка не в долг |
| 6 | Принятие pending-позиций (`AcceptPendingModal`) | `PATCH /main/products/{id}/` (status→accepted) | один чекбокс на всю пачку, применяется к каждой принятой позиции |
| 7 | Оплата долга поставщику, карточка контрагента (`DebtModal`) | `POST /main/clients/{id}/deals/{dealId}/pay/` | способ оплаты = «Наличные»; при «оплатить весь долг» — одна запись на сумму всех фактически оплаченных взносов |
| 8 | Оплата долга поставщику, KPI-дровер (`ClientKpiDetailDrawer`) | `POST .../deals/{dealId}/pay/` (циклом по сделкам) | контрагент — поставщик; одна запись на итоговую оплаченную сумму |

**Условие показа чекбокса везде одинаковое:** у пользователя есть открытая смена **и** фронт смог однозначно определить кассу этой смены (см. §4) **и** способ оплаты по операции — наличные, а не долг.

**Намеренно нет чекбокса:**
- в списании брака (`MarriageModal`) — там не происходит оплаты контрагенту, это списание стоимости испорченного товара;
- в возврате от поставщика (`supplierReturnsApi`) — это приход денег нам, а не расход из ящика.

## 4. Когда чекбокс не появится

| Ситуация | Причина |
|---|---|
| У кассира нет открытой смены | Списывать не с чего |
| У компании несколько активных касс с ролью `pos_main` (см. [pos-main-duplicate-role-bug.md](./pos-main-duplicate-role-bug.md)) и их не удаётся различить по имени | Фронт не гадает, с какой именно кассы списывать — лучше скрыть функцию, чем ошибиться кассой |
| Операция целиком в долг / без наличной части | Списывать из ящика нечего |

Как только backend начнёт отдавать `cashbox` (id) прямо в ответе Shift API (открытый вопрос Q1 из [shift-drawer-funding-purchases-backend.md](./shift-drawer-funding-purchases-backend.md#7-вопросы-к-backend-q1q3)), второй пункт таблицы перестанет быть проблемой.

## 5. Чек-лист ручного прогона (QA)

| # | Шаг | Ожидаемый результат |
|---|---|---|
| 1 | Открыть смену (размен 500), не отмечать чекбокс, оформить приход на 3000 наличными | В смене никаких новых записей в ящике; `drawer_expected_cash` не изменился от закупки |
| 2 | Тот же приход, но с отметкой чекбокса | В ленте кассы смены появилась запись-расход на 3000; `drawer_expected_cash` уменьшился на 3000 |
| 3 | Закрыть смену после шага 2 | `cash_diff` при сверке отражает реальную недостачу/излишек, без «скрытой» закупки |
| 4 | Повторить для «Принятие pending» с несколькими позициями и одним чекбоксом на пачку | Одна запись расхода на каждую фактически принятую позицию (или их сумма — см. реализацию), все входят в `drawer_expected_cash` |
| 5 | «Оплатить весь долг» поставщику с 3 просроченными взносами, чекбокс отмечен | Одна запись расхода на сумму **всех** фактически оплаченных взносов (не 3 отдельные записи) |
| 6 | Включены «Запросы на подтверждение», пользователь не owner | Запись списания создаётся `pending`, не входит в `drawer_expected_cash` до одобрения владельцем |
| 7 | Отключить смену (закрыть её) до принятия pending-позиции | Чекбокс на экране принятия pending пропадает |
| 8 | Уронить второй запрос вручную (например, через DevTools → offline перед подтверждением) | Приход/оплата долга всё равно завершается успешно, показывается предупреждение про ручное добавление в «Касса» |

## 6. Итог для команды

- Кассир теперь может честно отметить, что взял наличные из своего ящика на закупку/оплату поставщику — и это отражается при закрытии смены.
- Backend ничего дорабатывать не должен — используется существующий контракт ручной кассы.
- Единственная открытая просьба к backend — отдавать id кассы смены явным полем, чтобы убрать редкий edge-case с дублирующимися `pos_main`-кассами (см. §4).
