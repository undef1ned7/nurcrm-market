# Долг клиента → связь с чеком (POS-продажей), из которого он создан

**Страницы:** `/crm/clients/:id` → карточка клиента → список сделок → долг (`DealsSection`, `DebtModal`)
**Статус:** фронт готов и уже умеет отображать связь, **бэкенд — поле в контракте отсутствует, нужна реализация**.
Префикс: `{host}/api` · TZ: **Asia/Bishkek (UTC+6)**

Связанные эндпоинты:

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/main/clients/{clientId}/deals/` | список сделок клиента (долги, предоплаты, продажи) |
| `GET` | `/main/clients/{clientId}/deals/{dealId}/` | детали одной сделки (открывается `DebtModal`) |
| `POST` | `/main/pos/sales/{sale_id}/checkout/` | чек с `payment_method: "debt"` — здесь долг и создаётся |
| `GET` | `/main/pos/sales/{id}/` | детали чека (уже используется фронтом для превью) |

Читать вместе с: [cash-and-cashflows.md](../../flutter/cash-and-cashflows.md) (создание deal при checkout в долг), [debt-installment-schedule-backend.md](./debt-installment-schedule-backend.md).

---

## 1. Проблема

Долг (`Deal.kind == "debt"`) в большинстве случаев возникает не сам по себе, а как следствие конкретной продажи — кассир пробивает чек, покупатель платит `payment_method: "debt"` (полностью или частично), и на эту сумму создаётся `Deal`.

Сегодня ответ API на `GET /main/clients/{clientId}/deals/` и `GET /main/clients/{clientId}/deals/{dealId}/` **не содержит ссылки на исходный чек** — ни `sale_id`, ни вложенного объекта продажи. В ответе есть только: `amount`, `debt_amount`, `remaining_debt`, `title`, `note`, `installments[]`, `client_full_name`.

**Проблема для пользователя:** когда у клиента накапливается несколько долгов (несколько разных покупок в долг), в списке видно только суммы и даты — невозможно понять, к какой именно покупке (какому товару/чеку) относится конкретная запись долга, если не открывать сам чек в отдельном месте и не сверять вручную по сумме и дате. При частых покупках в долг это быстро становится нечитаемым.

**Запрошенная фича:** в ответе сделки-долга должна быть ссылка на исходный чек (`sale_id`), чтобы:
1. в списке долгов клиента показывать компактную метку «Чек №{id}»;
2. по клику открывать полный чек (товары, сумма, дата, кассир) — уже есть готовый переиспользуемый компонент предпросмотра чека на фронте, ему достаточно получить `id` чека.

## 2. Что уже сделано на фронте (готово, ждёт бэк)

Фронт уже реализован так, чтобы принять связь как только бэк её отдаст — никакой доработки на фронте после появления поля не потребуется, если бэк вернёт один из перечисленных ниже вариантов имени поля.

`resolveDealSaleId()` (`src/shared/lib/tools/clientDeals.ts`) читает первое непустое значение из списка кандидатов, в порядке приоритета:

```ts
const candidates = [
  deal.sale_id,
  deal.pos_sale_id,
  deal.source_sale_id,
  deal.receipt_id,
  deal.sale,      // тоже ок, если это id или объект {id: ...}
  deal.receipt,   // тоже ок, если это id или объект {id: ...}
  deal.source_sale,
];
```

Если значение — объект (`{id, uuid, ...}`), берётся `id` (или `uuid`). Если ничего не найдено — долг считается созданным вручную (это нормальный случай, никакой ошибки не показывается, просто нет кнопки «Показать чек»).

- В списке сделок клиента (`DealsSection`) для долга с `sale_id` показывается кликабельная метка «Чек №{id}», по клику открывается превью чека (`ReceiptPreviewModal`, тот же компонент, что и в кассовых журналах).
- В самой карточке долга (`DebtModal`) в шапке — кнопка «Чек №{id}» с тем же превью; если связи нет — ненавязчивая подпись «Без чека».
- **Ничего не ломается**, если бэк пока не отдаёт поле — просто везде показывается состояние «без чека», как для долгов, реально созданных вручную.

## 3. Что нужно от бэкенда

### 3.1. Минимум — плоское поле `sale_id`

В сериализаторе `Deal` (используется и в списке, и в детальном ответе) добавить поле:

```json
{
  "id": "deal-uuid",
  "kind": "debt",
  "amount": "1500.00",
  "sale_id": "sale-uuid-or-null",
  "...": "..."
}
```

- `sale_id` — id соответствующего `PosSale` (`/main/pos/sales/{id}/`), если долг создан из чека при `checkout(payment_method="debt")` (в т.ч. частичная предоплата + остаток в долг).
- `null`, если долг создан вручную через `POST /main/clients/{clientId}/deals/` без привязки к продаже — это штатный случай, отдельной ошибки/статуса не требуется.
- Поле должно быть и в списке (`GET .../deals/`), и в детальном ответе (`GET .../deals/{id}/`) — список нужен для метки в таблице, деталка — для кнопки в модалке (сейчас это два разных пути в коде, оба должны получить поле одинаково).

### 3.2. Откуда брать значение

Технически: в момент `checkout()` с `payment_method="debt"` (или сплит-оплатой с долей `debt`), при создании `Deal` для этой продажи проставлять `Deal.source_sale = sale` (FK, `null=True`) и отдавать `source_sale_id` как `sale_id` в сериализаторе.

Если между чеком и долгом сейчас нет прямой FK-связи в модели данных (создаются независимо в одной транзакции без явной ссылки) — минимально достаточно добавить сам FK и проставлять его в той же транзакции, где создаётся `Deal` из `checkout`. Обратной миграции для старых долгов (созданных до этого изменения) не требуется — старые записи корректно останутся с `sale_id: null`, фронт это уже обрабатывает как «долг без чека».

### 3.3. Опционально — embed вместо ID (если это дешевле для бэка)

Если так проще реализовать на бэке, вместо (или вместе с) плоского `sale_id` можно вернуть вложенный объект:

```json
{
  "sale": { "id": "sale-uuid", "created_at": "2026-09-11T14:00:00+06:00", "total": "1500.00" }
}
```

Фронт это тоже подхватит (см. `resolveDealSaleId`, обрабатывает как id, так и объект с `.id`) — но полноценный чек (товары, скидки) фронт всё равно догружает отдельным запросом `GET /main/pos/sales/{id}/` по id, так что embed нужен только если объект уже есть под рукой в БД без лишних join'ов; специально денормализовывать под это не нужно.

### 3.4. Что НЕ нужно менять

- Схему `PosSale` трогать не нужно — обратная связь (какие долги породил чек) фронту не требуется, только прямая (долг → чек).
- Существующие поля `amount`, `remaining_debt`, `installments[]` и т.д. не меняются.
- Долги без чека (созданные вручную) не требуют никакой миграции статуса — это валидное постоянное состояние, а не «незаполненное поле, которое надо когда-нибудь дозаполнить».

## 4. Тест-кейсы для приёмки

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Checkout чека на 1000 сом, `payment_method: "debt"`, без предоплаты | `Deal.sale_id` = id этого чека; `GET .../deals/{id}/` возвращает это же значение |
| 2 | Checkout со сплитом: часть cash, часть debt | `Deal.sale_id` заполнен так же, как в п.1 |
| 3 | Ручное создание долга через `POST /main/clients/{clientId}/deals/` без чека | `sale_id: null` |
| 4 | Список долгов клиента с несколькими записями, часть из чеков, часть вручную | В каждой записи `sale_id` соответствует своему источнику, не «залипает» на последнем созданном чеке |
| 5 | Старые долги, созданные до раскатки фичи | `sale_id: null` (не 500, не пустая строка вместо null) |
| 6 | `GET /main/pos/sales/{sale_id}/` по значению из `Deal.sale_id` | Всегда 200 (ссылка не «битая» — sale не удалён/не из другой компании) |
