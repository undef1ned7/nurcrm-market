# Оплата произвольной суммы «в счёт долга» — модалка KPI «Долг» (карточка клиента)

**Экран:** карточка клиента/поставщика → KPI-плашка «Долг» → модалка со списком сделок (`ClientKpiDetailDrawer.tsx`), **не** модалка одной сделки (`DebtModal.tsx`, см. [debt-pay-all-backend.md](./debt-pay-all-backend.md) — это другой экран и другая задача).
**Статус:** фронт реализован **сегодняшними средствами** (цикл по существующему `pay/` для нескольких сделок сразу); этот документ — предложение бэку добавить настоящий bulk-эндпоинт **на уровне клиента**, а не одной сделки.

---

## Контекст: чем это отличается от «Оплатить весь долг» одной сделки

В карточке клиента KPI «Долг» агрегирует **несколько** сделок (`Deal`, `kind=debt`) — на скриншоте это три отдельные продажи в долг с разными `id`, каждая свой график платежей. Раньше можно было оплатить только:
- один взнос конкретной сделки (кнопка «Оплатить» в графике, `DebtModal.tsx`);
- весь долг **одной** сделки целиком (кнопка «Оплатить весь долг» там же).

Не было способа сказать «клиент принёс 600 сом наличными, распредели по всем его долгам» — приходилось открывать каждую сделку по очереди. Это и добавили.

---

## Что уже работает на фронте (без изменений бэка)

Новое поле «Оплатить часть долга» в модалке KPI «Долг» — принимает сумму (≤ суммарный остаток по всем сделкам клиента), и по кнопке «Оплатить»:

1. Сортирует сделки-долги клиента (`debtRows`) **от самой старой к самой новой** по дате (в UI список показан наоборот — новые сверху, для оплаты порядок разворачивается, чтобы гасить сначала старые долги).
2. Для каждой сделки по очереди: `GET /main/clients/{clientId}/deals/{dealId}/` → берёт `installments[]`, фильтрует неоплаченные.
3. Для каждого неоплаченного взноса по очереди — платит **тем же существующим эндпоинтом**, что и одиночная оплата:

```http
POST /main/clients/{clientId}/deals/{dealId}/pay/
```
```json
{
  "idempotency_key": "<uuid, новый на каждый вызов>",
  "installment_id": "<installment uuid>",
  "date": "2026-09-11",
  "amount": "123.45"
}
```

— `amount` **не передаётся**, если введённой суммы хватает на весь остаток этого взноса (гасим полностью, как обычная оплата); передаётся, если введённая сумма заканчивается ровно на этом взносе (частичная оплата **одного** взноса — контракт уже поддержан бэком, ничего нового).

4. Как только сумма исчерпана — цикл останавливается (даже если у клиента остались другие неоплаченные сделки/взносы).
5. После каждого платежа — `postCashflowIfNeeded` (как и у одиночной оплаты).
6. При ошибке посреди цикла — уже оплаченная часть суммы остаётся оплаченной (транзакции успели пройти), пользователю показывается «Успели оплатить X сом — проверьте остаток и попробуйте ещё раз».

Это **работает уже сегодня**, ничего от бэка не требуется для базовой функциональности — только N последовательных вызовов уже существующего `pay/`.

---

## Зачем всё-таки нужен bulk-эндпоинт на уровне клиента

Всё то же, что в [debt-pay-all-backend.md](./debt-pay-all-backend.md), но раскрытие на несколько *разных* сделок делает риски заметнее:

- N×M последовательных HTTP-запросов (N сделок × M незакрытых взносов в каждой) — для клиента с 3–5 активными долгами это может быть 30–100+ запросов подряд;
- **не атомарно на уровне всей операции**: сеть оборвалась на 47-м из 80 запросов — 46 взносов из разных сделок уже оплачены, остальные нет; восстановить, «что уже успело пройти», сложнее, чем в случае одной сделки, потому что это разные `Deal` с разными графиками;
- при `AUTO_CASHFLOWS` — N×M отдельных записей в кассе на одну бытовую операцию «клиент принёс 600 сом» — шумно для отчётов и сверки кассы;
- сортировка «от старых долгов к новым» сейчас реализована на клиенте (`debtRows.sort(...)` по дате сделки) — бэк может использовать более надёжный критерий (например, `first_due_date` каждой сделки/ближайший неоплаченный взнос), а не дату создания сделки.

## Предлагаемый контракт

```http
POST /main/clients/{clientId}/deals/pay-any/
```
```json
{
  "idempotency_key": "<uuid>",
  "amount": "600.00",
  "date": "2026-09-11",
  "branch_id": "...",
  "cashbox_role": "pos_branch",
  "shift_id": "..."
}
```

Поведение:

1. Выбрать все сделки клиента с `kind=debt` и `remaining_debt > 0`, отсортировать по **наиболее раннему неоплаченному сроку** (ближайший `due_date` среди незакрытых взносов, либо `first_due_date` сделки — на усмотрение бэка, главное — задокументировать критерий, чтобы фронт мог показать тот же порядок в UI).
2. Распределить `amount` по этим сделкам последовательно: в каждой — по незакрытым взносам от раннего к позднему, закрывая полностью, пока сумма не закончится; последний частично захваченный взнос получает остаток.
3. Если `amount` больше суммарного `remaining_debt` по всем долгам клиента → `400` с понятным `detail` (фронт уже присылает валидированную сумму, но бэк не должен полагаться на клиента).
4. Если у клиента нет ни одной сделки-долга с остатком → `400`.
5. Одна транзакция в БД — либо применяется полностью, либо откатывается целиком.
6. Кассовое движение — на усмотрение бэка: одна запись на всю операцию (предпочтительно для читаемости отчётов) **или** по одной на каждый закрытый/частично закрытый взнос (для трассируемости) — в любом случае это должно быть задокументировано явно, чтобы фронт не дублировал `postCashflowIfNeeded` поверх того, что уже сделал бэк (см. общий принцип auto-cashflows: [auto-cashflows-backend.md](./auto-cashflows-backend.md)).
7. Ответ — список затронутых сделок с обновлённым состоянием:

```json
{
  "paid_total": "600.00",
  "deals": [
    {
      "id": "d30e0334-...",
      "remaining_debt": "0.00",
      "installments": [ /* обновлённые paid_amount / paid_on / balance_after */ ]
    },
    {
      "id": "691951b2-...",
      "remaining_debt": "76.20",
      "installments": [ /* ... */ ]
    }
  ]
}
```

8. Идемпотентность — как у `pay/`: повтор с тем же `idempotency_key` не должен задвоить оплату.

## Если добавите — что поменяет фронт

- Один `POST .../deals/pay-any/` вместо цикла `GET deal → N×pay`.
- Уберётся клиентская сортировка «от старых к новым» — бэк уже вернёт результат в применённом порядке.
- Уберётся ручной `postCashflowIfNeeded` в цикле, если бэк берёт создание движения кассы на себя (см. п.6).
- Атомарность на уровне суммы: либо всё применилось, либо ничего — уйдёт сообщение «успели оплатить X, остальное не получилось».

## Тест-кейсы для приёмки

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | У клиента 3 долга (301, 238.36, 236.84), оплата 600 | Первый долг закрыт полностью (301), второй частично (299 из 238.36 — стоп, т.к. 600−301=299>238.36 → второй тоже полностью закрыт (238.36), остаток 60.64 уходит в третий частично); третий: `remaining_debt = 236.84 − 60.64 = 176.20` |
| 2 | Оплата ровно на всю сумму (776.20) | Все три долга закрыты, `remaining_debt = 0` на каждом |
| 3 | Оплата больше суммарного остатка | `400`, ничего не применяется |
| 4 | Оплата 0 или отрицательная сумма | `400` |
| 5 | Повтор запроса с тем же `idempotency_key` | Тот же результат, не задвоение |
| 6 | У клиента нет долгов | `400` |
| 7 | Один из долгов клиента — сделка **поставщика** (если `clientId` — общий client/supplier) | Не должен попасть в выборку `kind=debt` для этого клиента — только его собственные долги |

## Открытые вопросы к бэкенду

| # | Вопрос |
|---|---|
| Q1 | Критерий сортировки долгов клиента при распределении — по дате создания сделки, по `first_due_date`, или по ближайшему неоплаченному взносу? Нужно единое решение, которое фронт продублирует в отображении (сейчас сортирует по дате создания). |
| Q2 | Кассовое движение — одна запись на операцию или по одной на каждый закрытый взнос? От этого зависит, нужно ли фронту продолжать вызывать `postCashflowIfNeeded`. |
| Q3 | Это тот же самый предполагаемый `pay-all/`-эндпоинт с расширенным скоупом (на уровне клиента, а не сделки, см. [debt-pay-all-backend.md](./debt-pay-all-backend.md)), или два разных эндпоинта — один для «весь долг одной сделки», другой для «сумма по всем долгам клиента»? Предлагаем разделить (пути разные: `.../deals/{dealId}/pay-all/` vs `.../deals/pay-any/`), т.к. семантика различается (сделка знает свою дату, клиент — нет единой). |
| Q4 | Нужна ли отдельная обработка, если среди долгов клиента есть сделки с разными `schedule_version` (v1/v2, см. [debt-installment-schedule-backend.md](./debt-installment-schedule-backend.md))? Предполагаем — нет, распределение работает одинаково через `installments[]` независимо от версии графика. |

## Не блокер

Реализация bulk-эндпоинта не блокирует текущую фичу — она уже работает через цикл на фронте (см. раздел выше). Приоритет — по усмотрению бэка; актуальность растёт с числом активных долгов на клиента (для 1–2 долгов разница почти не заметна пользователю).
