**Дата:** 2026-10-02
**Экран:** карточка клиента → «Акт сверки» (`GET /main/clients/{id}/reconciliation/json/`).
**Статус:** решения по архитектуре согласованы; **код и прод не менялись**. Анализ п. 5–9 и dry-run (§7) ещё не выполнены.
**Связано:** [client-reconciliation-double-debt-backend.md](./client-reconciliation-double-debt-backend.md) (первичное описание бага и временный фронтовый костыль).

Реальный ответ бэка использует **`entries`**, **`opening_balance`**, **`closing_balance`**, **`totals`**, **`debt`**. Все новые поля добавляются в существующую структуру, ключи не переименовываются.

## 1. Что сломано (подтверждено)

`ClientReconciliationJSONAPIView` (`apps/main/pos_views.py`, класс с ~строки 1425) считает дебет из трёх независимых источников и не учитывает `ClientDeal.sale_id`:

1. `Sale.total` (все, кроме отменённых);
2. `ClientDeal.amount` для видов `sale`, `amount`, `debt`;
3. предоплата `ClientDeal.prepayment` — в кредит.

Кредит по оплатам берётся из `DealInstallment` по `paid_on`. Та же логика продублирована в блоке «сальдо начальное».

Воспроизведено на прод-данных (клиент «Гулумкан Исакова»): продажа 15 000 + связанная (`sale_id` заполнен) сделка-долг 15 000 + 6 × 2 500 оплат ⇒ Дт 30 000, Кт 15 000, сальдо 15 000 вместо 0.

### Масштаб (прод-БД `nurcrm2`, снято read-only 2026-10-02)

| Группа | Кол-во | Сумма | Клиентов |
|---|---|---|---|
| Долговые сделки **со связью** с неотменённой продажей (двойной Дт) | 2 119 | 6,68 млн | 292 |
| Долговые сделки **без связи**, похожие на дубль продажи (сумма совпадает, ±3 сут.) | 1 847 | 3,09 млн | 319 |
| Долговые сделки, связанные с **отменённой** продажей (всё ещё в Дт акта) | 5 | 35 000 | — |
| Продажи не в долг с клиентом (в акте Дт без Кт) | 1 276 | 7,60 млн | 486 |
| `ClientDeal.kind=sale` (ручные, без `sale_id`) | 15 116 | 262,27 млн | — |

Прочее: из 4 099 долговых продаж у 2 115 одна связанная сделка, у 1 984 связи нет; только одна продажа имеет 2+ сделки.

### Как сделка получает связь с продажей сейчас

Фронт: `checkout` → `POST /clients/{id}/deals/` (`kind=debt`, `amount=total`, **без `sale_id`**). Связь ставит бэк эвристикой:

- checkout (`pos_views.py` ~5498–5525, `services/__init__.py` ~279–291): ищет сделку клиента `kind=debt`, `sale IS NULL`, созданную за **последние 60 с**, с суммой ≈ долгу продажи → пишет `deal.sale = sale`; если нет — создаёт сделку сам;
- `ClientDealListCreateAPIView.perform_create` (`views.py` ~3288): если `sale` не передан, берёт последнюю долговую сделку клиента за **120 с** и **обновляет её** вместо создания новой.

Идемпотентности у `ClientDeal` нет (у `Sale` есть `idempotency_key`). Повтор позже 60/120 с или без `sale_id` ⇒ вторая сделка.

## 2. Принятые решения

1. **Источник начисления — `Sale`.** Связанная (`sale_id IS NOT NULL`) сделка `kind=debt` не попадает в Дт/Кт и оборот акта. В акте остаётся справочной строкой: `affects_balance: false`, `ref_type`, `ref_id`, `sale_id`.
2. **Начальное сальдо** считается по тому же правилу, что и обороты.
3. **Новые сделки:** `sale_id` принимается в `POST /deals/`; защита от дублей; частичный уникальный индекс `sale_id WHERE kind='debt'` (должен корректно работать с `NULL` и другими видами сделок).
4. **Старые 1 847 несвязанных пар — не менять.** Только dry-run (§7), без `UPDATE`.
5. **Продажи не в долг** — сначала изучить модель оплаты, не исключать из акта (§6).
6. **`ClientDeal.kind=sale`** — автоматически не исключать, сначала анализ (§6).
7. **Частичные оплаты:** Кт по фактически оплаченной сумме (`paid_amount`), не по `amount` (§5, C).
8. **Итоги:** `closing_*`, `totals`, начальное сальдо и обороты считает **бэк** из одного правила; фронт не пересчитывает.
9. **Прод:** ничего не менять. Пароль root из чата не использовать и не хранить в коде/репозитории; после работ сменить и перейти на SSH-ключи.

## 4. A. Backend: акт сверки

- Дт по `Sale` — как сейчас (с учётом решения по §6, п. 5).
- `ClientDeal` в Дт: только если **нет** `sale_id` (ручные долги/договоры); связанные `kind=debt` выводить строкой с `affects_balance: false` и нулевыми суммами оборота.
- Каждая строка `entries[]` получает: `ref_type` (`sale | deal | deal_prepayment | installment_payment`; уже есть), `ref_id` (уже есть), **новые** `sale_id` (для сделки), `affects_balance` (bool).
- **Начальное сальдо** — тот же набор правил (`created_at < start`), включая исключение связанных сделок и новый расчёт Кт по взносам.
- **Предоплата:** при связанной сделке Кт-предоплату брать по одному правилу (либо `Sale.paid_now`, либо `deal.prepayment`) и не дублировать — выбрать после изучения §6.
- **Отменённые продажи:** сделка `kind=debt` отменённой продажи не должна давать Дт (5 таких записей сейчас считаются).
- `totals`, `closing_balance`, `debt{...}` — из тех же строк, что и `entries` (без суммирования отдельных запросов). `running_balance_after` не меняется.
- Тот же расчёт должен использовать PDF-вью `ClientReconciliationClassicAPIView` (дублирующая логика ниже по файлу) — **вынести в общий сервис**, чтобы JSON и PDF не расходились.

## 5. B и C

### B. Создание сделки

- `POST /clients/{id}/deals/` и `POST /clientdeals/` принимают `sale_id` (в `ClientDealSerializer` поле уже есть — проверить, что `perform_create` его уважает).
- Если для `sale` уже есть сделка `kind=debt` → вернуть существующую (идемпотентно), а не создавать вторую.
- Эвристики «последняя сделка за 120 с» / «за 60 с» оставить **только** как fallback для клиентов без `sale_id` (старые версии фронта), затем убрать.
- Частичный уникальный индекс (Django): `UniqueConstraint(fields=["sale"], condition=Q(kind="debt") & Q(sale__isnull=False), name="uniq_debt_deal_per_sale")`.
  - В PostgreSQL `NULL` в уникальном индексе не конфликтуют; условие делает правило явным.
  - **Перед миграцией** устранить единственную продажу с 2+ сделками (найти и решить отдельно — это правка данных, согласовать).
  - Сделка `canceled` не блокирует создание новой `debt`, т.к. условие по `kind`.
- Для идемпотентности повторов по сети — принять `Idempotency-Key` (в проекте уже есть у возвратов/смен, BE2-11).

### C. Взносы (`DealInstallment`)

Поля: `amount`, `paid_amount` (`paid_amount ≤ amount`), `paid_on`, `due_date`.

- Сейчас Кт = `amount` при `paid_on IS NOT NULL` — частично оплаченный взнос (где `paid_on` пуст) в акт не попадает.
- Новое правило (согласовано): Кт = `paid_amount`, условие `paid_on IS NOT NULL AND paid_amount > 0`.
- ⚠️ **Проверить до изменения:** когда именно ставится `paid_on` — только при полной оплате или и при частичной. Если при частичной он пуст, согласованное условие всё равно её не увидит. Посмотреть `DealPayment` (`deal.payments`) и `ClientDealPayAPIView` (`views.py` ~3604): возможно, надёжнее брать Кт из платежей с их датами, а не из взносов. Также изучить `DealInstallmentHistory` и статусы/поля оплаты, чтобы не сломать просрочки и «обещанную дату».
- Дата строки Кт — фактическая дата оплаты (платежа), не `due_date`.

## 7. D. Dry-run по 1 847 несвязанным парам (только SELECT)

**Никаких UPDATE.** Результат — таблица/CSV для ручной проверки.

Колонки: `sale_id`, `deal_id`, клиент, `sale_total`, `deal_amount`, `sale_created_at`, `deal_created_at`, разница по времени (сек), причина предложения, `sale_candidates` (сколько продаж подходит сделке), `deal_candidates` (сколько сделок подходит продаже), категория.

Критерии кандидата: тот же `company_id` и `client_id`; сделка `kind=debt`, `sale_id IS NULL`; продажа `payment_method=debt`, `status<>canceled`, не связана ни с одной сделкой; `|sale.total − deal.amount| ≤ 0.01`; окно по времени (смотреть распределение, начать с ±120 с, отдельно показать до ±3 сут.).

Категории:
- **unique** — 1 сделка ↔ 1 продажа, взаимно;
- **deal→many** — одной сделке подходит несколько продаж;
- **sale→many** — одной продаже подходит несколько сделок;
- **many↔many** — клиент с несколькими одинаковыми суммами в окне;
- **no match** — подходящей продажи нет.

Особо показать неоднозначные категории и случаи с несколькими одинаковыми суммами у одного клиента. Привязка делается только для `unique` и только после отдельного подтверждения; неоднозначные — вручную.

Скелет запроса (выполнять в `SET default_transaction_read_only = on`):

```sql
WITH d AS (
  SELECT id, company_id, client_id, amount, created_at
  FROM main_clientdeal
  WHERE kind = 'debt' AND sale_id IS NULL
), s AS (
  SELECT id, company_id, client_id, total, created_at
  FROM main_sale
  WHERE payment_method = 'debt' AND status <> 'canceled'
    AND NOT EXISTS (SELECT 1 FROM main_clientdeal x WHERE x.sale_id = main_sale.id)
), pairs AS (
  SELECT d.id AS deal_id, s.id AS sale_id, d.client_id,
         s.total AS sale_total, d.amount AS deal_amount,
         s.created_at AS sale_at, d.created_at AS deal_at,
         EXTRACT(EPOCH FROM (d.created_at - s.created_at)) AS diff_sec
  FROM d JOIN s ON s.company_id = d.company_id AND s.client_id = d.client_id
   AND ABS(s.total - d.amount) <= 0.01
   AND ABS(EXTRACT(EPOCH FROM (d.created_at - s.created_at))) <= 259200
)
SELECT p.*,
       COUNT(*) OVER (PARTITION BY deal_id) AS sale_candidates,
       COUNT(*) OVER (PARTITION BY sale_id) AS deal_candidates
FROM pairs p
ORDER BY client_id, sale_at;
```
