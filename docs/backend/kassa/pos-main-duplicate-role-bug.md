# Баг: несколько активных касс с ролью `pos_main` на одну компанию

**Статус:** подтверждено на staging реальным ответом API, 2026-09-11
**Критичность:** высокая — ломает маршрутизацию checkout/долга без смены и филиала, аналитику «Финансы»
Префикс: `{host}/api` · TZ: **Asia/Bishkek (UTC+6)**

Читать вместе с: [auto-cashflows-backend.md](./auto-cashflows-backend.md) (роли касс, `resolve_cashbox`),
[BACKEND-QUESTIONS.md](./BACKEND-QUESTIONS.md) §6 (миграция `0023`, `get_inferred_role()`),
[cashbox-delete-backend.md](./cashbox-delete-backend.md).

## 1. Факт (staging, `GET /construction/cashboxes/`, компания `4b759359-2239-4e2a-a07e-f0e42a4dd19d`)

```
GET https://stageapp.nurcrm.kg/api/construction/cashboxes/  →  200 (from service worker)
```

7 касс, из них **4 (!) с `role: "pos_main"`**:

| `name` | `role` | `is_consumption` | `is_active` |
|---|---|---|---|
| **карыз** (кырг. «долг») | `pos_main` | `false` | `true` |
| **Расход** | `pos_main` | `false` | `true` |
| **Касса 2** | `pos_main` | `false` | `true` |
| **Основная касса компании** | `pos_main` | `false` | `true` |
| Касса филиала номер 1 | `pos_branch` | `false` | `true` |
| Переменные расходы | `expense_variable` | `false` | `true` |
| Постоянные расходы | `expense_fixed` | `false` | `true` |

Полный ответ приложен ниже (§7) — сохранён как факт для регрессионного теста.

**Ключевое наблюдение:** у **всех 7 касс** `is_consumption: false`, включая «Переменные расходы»
(`role=expense_variable`) и «Постоянные расходы» (`role=expense_fixed`). То есть `is_consumption`
**не участвует** в определении `role` — роль присваивается только по ключевым словам в названии
(`auto-cashflows-backend.md` §«Временный fallback без поля role»), а всё, что не подошло — по
умолчанию `pos_main`. Это прямо подтверждает ответ BE №45 из `BACKEND-QUESTIONS.md`:

> «Касс без роли нет; без ключевых слов → `pos_main` по умолчанию»

«Расход» и «карыз» — явно кассы, которые пользователь заводил для чего-то своего (расходы,
учёт долгов), но ни то, ни другое слово не входит в список ключевых слов (`переменн`, `постоянн`,
`филиал`, `основн`) → обе получили `pos_main`. «Касса 2» — ровно тот кейс, который в
`auto-cashflows-backend.md` §«Пример компании» уже был помечен как двусмысленный
(«pos_branch или pos_main — по привязке в админке»).

## 2. Как создаются дубли — подтверждённый путь с фронта

`nur-market`, `/crm/kassa` → «Создать кассу» (`src/features/kassa/ui/Kassa.tsx`):

```http
POST /construction/cashboxes/
{ "name": "<введённое название>", "is_consumption": <чекбокс «Прочие расходы»> }
```

Фронт **никогда** не передаёт `role` или `branch_id` — их всегда резолвит бэк. Раз `is_consumption`
не влияет на `role` (см. §1), то **любая** новая касса, чьё название не содержит нужных ключевых
слов, получает `pos_main` — независимо от того, отмечена ли галочка «Прочие расходы». Именно так,
судя по всему, появились «Расход» и «карыз» — пользователи хотели кассу для расходов/учёта долгов,
а получили ещё один `pos_main`.

Это не единичный старый мусор из миграции `0023` — это **воспроизводимо на живом бэке сегодня**
через штатный UI создания кассы.

## 3. Почему это ломает работу

`resolve_cashbox()` (`auto-cashflows-backend.md` §«Алгоритм»), шаг для отсутствия смены/филиала:

```
3d. return Cashbox WHERE company, role=pos_main, is_active
```

Ожидается **одна** запись (чек-лист прод: «У каждой компании ровно одна `pos_main`
(активная)», тест-кейс R2: «shift.cashbox = **основная**» — в единственном числе).
При 4 активных `pos_main`:

- Неизвестно (не описано и не покрыто тестами R1–R14), что делает `_get_unique_cashbox` —
  бросает `MultipleObjectsReturned`, берёт `.first()` по недетерминированному порядку, или
  как-то иначе. **Просьба сообщить фактическое поведение.**
- Если разные вызовы (`open shift`, `checkout` без смены, `pay debt` без филиала) попадают
  в **разные** из четырёх касс — деньги «размазываются» по кассам, которые фронт и пользователь
  считают одной и той же «основной кассой».
- Косвенное подтверждение в самих данных: у кассы **«карыз»** — `sales_count: 4`,
  `sales_total: "36050.00"`, `cash_sales_total: "36050.00"`, но `income_total: "0.00"`.
  Продажи есть, а прихода по кассе нет — согласуется с тем, что `pos_sale`-cashflow по этим
  продажам мог уйти в **другую** `pos_main`-кассу, а не в ту, где числится сама продажа.
- На фронте вкладка «Финансы» (`src/pages/analytics/ui/hooks/useAnalyticsData.tsx`) для
  дефолтного фильтра берёт первую кассу с именем, содержащим «основн», иначе — `cashBoxes[0]`.
  При 4 `pos_main` результат зависит от порядка в ответе API и может не совпадать с той кассой,
  куда реально идёт checkout.

## 4. Что нужно от бэка

### 4.1. Немедленно — на этой и всех затронутых компаниях

1. Найти все компании с `count(role='pos_main', is_active=true) > 1`.
2. Для каждой — определить «настоящую» `pos_main` (по объёму операций / истории —
   в примере выше это явно **«Основная касса компании»**, 321 продажа vs 4/10/0 у остальных)
   и перевести остальные в другую, корректную роль **или** заархивировать
   (`is_active=false`, без удаления cashflows — см. [cashbox-delete-backend.md](./cashbox-delete-backend.md) §3.2).
3. Прислать список затронутых компаний и итоговое распределение ролей после исправления.

### 4.2. Корень проблемы — создание кассы

Убрать «default → `pos_main`» как исход при создании новой кассы:

- **Вариант A (рекомендуется).** `POST /construction/cashboxes/` принимает явный `role`
  (и `branch_id` для `pos_branch`). Если `role` не передан **и** название не матчится ни под один
  keyword — **не** присваивать `pos_main` автоматически: либо требовать `role` в теле (`400`,
  если отсутствует и это не первая касса компании), либо присваивать нейтральную
  роль/`role=null` и требовать назначения через админку перед тем, как касса начнёт участвовать
  в `resolve_cashbox`.
- **Вариант B.** Оставить keyword-fallback только для **миграции существующих** данных;
  для **новых** касс, создаваемых после миграции `0023`, — `role` обязателен в `POST`.
- В любом случае: если у компании **уже есть** активная `pos_main`, повторное присвоение
  `role=pos_main` новой кассе — заблокировать (`409`) или потребовать явного подтверждения.

### 4.3. DB-constraint

Превратить рекомендацию из `auto-cashflows-backend.md` §«Уникальность» в реальный constraint:

```python
class Meta:
    constraints = [
        UniqueConstraint(
            fields=["company", "role"],
            condition=Q(is_active=True, branch_id__isnull=True, role__in=["pos_main", "expense_variable", "expense_fixed"]),
            name="uniq_active_singleton_role_per_company",
        ),
        UniqueConstraint(
            fields=["company", "role", "branch_id"],
            condition=Q(is_active=True, role="pos_branch"),
            name="uniq_active_pos_branch_per_branch",
        ),
    ]
```

### 4.4. `resolve_cashbox` при дубле (пока constraint не накатили)

Сообщить, что сейчас происходит при `role=pos_main, is_active=True` с >1 результатом:
исключение 500, произвольный `.first()`, что-то ещё. Если это тихий `.first()` — заменить на
явную ошибку `409 cashbox_role_ambiguous` с перечислением id кандидатов, чтобы не размазывать
деньги по случайной кассе.

## 6. Что уже сделано на фронте (без ожидания бэка)

Раз `is_consumption` не спасает от дублей, а `role`/`branch_id` фронт не выбирает —
добавлена **клиентская защита** в `/crm/kassa` → «Создать кассу»
(`src/features/kassa/ui/Kassa.tsx`, `src/entities/cash/lib/cashboxMutations.ts`
→ `isPosMainCashbox`, `hasActivePosMainCashbox`):

Если у компании уже есть активная касса с `role=pos_main`, а новое название не содержит
`расход`/`переменн`/`постоянн`/`прочих`/`прочие` и чекбокс «Прочие расходы» не отмечен —
перед созданием показывается предупреждение с подтверждением («скорее всего получит роль
`pos_main` — создать всё равно?»). Это снижает вероятность **новых** случайных дублей, но
**не исправляет** уже существующие (для этого нужен бэк, см. §4.1) и не панацея — если
пользователь всё равно подтвердит, или назовёт кассу словом не из списка эвристики, дубль
всё равно возможен без `role` в `POST`.
