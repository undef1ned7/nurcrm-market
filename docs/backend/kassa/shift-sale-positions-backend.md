# Позиции чека в списке продаж смены (`/crm/shifts/{id}`)

**Экран:** `/crm/shifts/{id}` → вкладка «Движение товаров» (`ShiftDetail.tsx`) → строка продажи → стрелка вниз.
**Статус:** фронт реализован **сегодняшними средствами** (детальный запрос по клику); этот документ — что нужно подтвердить/доработать на бэке, чтобы это работало быстро и надёжно.

---

## Что было и что стало

Раньше стрелка `ChevronDown` у каждой продажи в списке была чисто декоративной — клик ничего не делал, позиции чека нигде не показывались (кроме количества: «N позиции»).

Теперь клик по строке продажи разворачивает её и показывает таблицу позиций (товар / кол-во / цена / сумма строки).

## Как это работает на фронте сейчас

1. Список продаж смены — `GET /construction/cash/shifts/{shiftId}/sales/` (уже используется, без изменений).
2. По клику на строку — если в объекте продажи из списка уже есть непустой `items[]`, используем его напрямую, без доп. запроса.
3. Если `items` в списке нет (ожидаемый случай для summary-эндпоинта) — довызываем **уже существующий** контракт:

```http
GET /main/pos/sales/{sale_id}/
```

и берём `data.items[]`. Это тот же эндпоинт, что уже используется в других местах приложения для превью чека (карточка клиента, журнал чеков кассира) — предполагаем, что `sale_id` из списка продаж смены полностью совместим с этим эндпоинтом (та же сущность `PosSale`, просто другой список-фильтр). **Просьба подтвердить** — см. §«Открытые вопросы».

4. Результат кэшируется на фронте по `sale_id` на время открытой страницы — повторный клик на ту же строку не шлёт запрос заново.
5. Поля позиции читаются с фолбэками (как и везде в приложении): `product_name ?? name_snapshot ?? name`, `qty ?? quantity`, `unit_price ?? price`, `line_total ?? total` (если и этого нет — считаем `price × qty` на клиенте).

## Что нужно от бэкенда

### Обязательно — подтвердить

| # | Вопрос | Почему важно |
|---|---|---|
| Q1 | `sale.id` из ответа `GET /construction/cash/shifts/{shiftId}/sales/` — это тот же id, что принимает `GET /main/pos/sales/{id}/`? | Если это разные пространства id (например, обёртка/агрегат по смене) — фронт получит 404 при разворачивании каждой строки. |
| Q2 | Есть ли ограничение доступа: можно ли получить `GET /main/pos/sales/{id}/` для продажи, если пользователь смотрит смену, но сама продажа относится к другому кассиру/филиалу той же компании? | Кассир, открывший чужую закрытую смену (если такое разрешено ролью), не должен получать 403 только из-за смены исполнителя. |

### Опционально — оптимизация (не блокер)

Список продаж смены сейчас, вероятно, не включает `items[]` (summary-эндпоинт для производительности) — поэтому на каждое разворачивание строки уходит отдельный запрос. Это создаёт N дополнительных запросов при просмотре смены с большим числом продаж (открывать по одной — не проблема, но нет способа развернуть «все сразу» без N запросов).

Если для бэка не накладно — можно **сразу включить** `items[]` (или хотя бы `[{name, qty, price}]` в упрощённом виде, без всех полей полного чека) в ответ `GET /construction/cash/shifts/{shiftId}/sales/`. Тогда фронт вообще не будет делать доп. запрос — эта оптимизация уже заложена в код (см. п.2 выше: если `items` уже есть в списке — используется без похода на `/main/pos/sales/{id}/`).

## Тест-кейсы для приёмки

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Клик по продаже с 3 позициями | Разворачивается таблица с 3 строками: название, кол-во, цена, сумма |
| 2 | Повторный клик по той же продаже | Сворачивается (без повторного запроса за данными) |
| 3 | Клик по продаже без позиций (пустой чек, если такое возможно) | Показывается «В этом чеке нет позиций», не пустая таблица и не ошибка |
| 4 | `GET /main/pos/sales/{id}/` вернул 404/403 | Показывается «Не удалось загрузить позиции чека», не белый экран |
| 5 | Смена фильтров списка продаж | Ранее развёрнутая строка сворачивается (не показывает данные не относящейся к текущему фильтру продажи) |

## Не блокер

Фича работает уже сегодня на существующем контракте `GET /main/pos/sales/{id}/` — доработка бэка (Q1/Q2 — подтверждение, опциональная оптимизация — включение `items` в список) не блокирует релиз, только повышает производительность при просмотре смен с большим числом продаж.
