# Предупреждение о чужой кассе (`cashbox_warning`)

**Статус:** ✅ реализовано на бэке и на фронте, 2026-09-23. 15 тестов зелёные (BE), интеграция на фронте — этот документ. **Страховка работает и уже проверена на проде; корневая причина (ниже, §1) для части компаний ещё не устранена — см. §6.**
**Экраны:** открытие смены (`/crm/cashier` → «Открыть смену»), рабочий экран кассира (`ShiftPage.tsx`), детальная страница смены (`/crm/shifts/{id}`).

Читать вместе с: [pos-main-duplicate-role-bug.md](./pos-main-duplicate-role-bug.md) (одна из двух причин — дубли роли `pos_main`), [auto-cashflows-backend.md](./auto-cashflows-backend.md) (резолв кассы).

---

## 1. Контекст (инцидент)

Кассир открыл смену и увидел в ящике на 989 сом больше, чем сам туда положил. Причина в компании из инцидента («Маркет», 4 кассы: «Основная касса компании», «Касса филиала Beauty HUB», «Касса 1 этаж», «Касса 2 этаж») — **ни у одной кассы не проставлена роль** (`role=None` у всех четырёх). Алгоритм `resolve_cashbox()` без явного `cashbox` идёт по цепочке: касса филиала по `branch_id` → касса с ролью `pos_main` → и только если оба шага пустые (как здесь) — эвристика по подстроке `name__icontains="основн"`. Кассир со «2 этажа» не привязан ни к филиалу, ни к роли — поэтому неизбежно попадает на «Основную кассу компании», где уже работает другой кассир.

Это **не тот же баг**, что в [pos-main-duplicate-role-bug.md](./pos-main-duplicate-role-bug.md) (там — несколько *активных* касс с ролью `pos_main` одновременно, и резолв неоднозначен между ними). Здесь ролей нет вообще ни у одной кассы, поэтому шаг 2 пуст, а эвристика по имени срабатывает детерминированно — но не туда, куда нужно конкретному кассиру. По базе (проверено BE) это два разных по составу множества компаний: 44 компании без единой проставленной роли (этот случай) и 38 компаний с дублями `pos_main` (тот баг) — пересечение и суммарный охват см. §6.

Полноценное лечение — бэк проставляет роли/привязки к филиалу для всех касс (см. §6). `cashbox_warning` — это **страховка**, а не лечение: если кассира всё же посадили на кассу с чужим незакрытым остатком, он должен узнать об этом сразу, а не через день сверки.

## 2. Контракт

Ключ присутствует **всегда**, в обоих ответах, у открытых и у закрытых смен (изначально был не у всех — поправлено самим бэком в этом же релизе, см. История):

```
POST /construction/shifts/open/   → cashbox_warning
GET  /construction/shifts/{id}/   → cashbox_warning
```

`null` — предупреждать не о чем. Иначе (пример — реальный ответ прода, поля `code`/`cashbox_id`/`cashbox_name` на верхнем уровне и `shift_id`/`cashier_id`/`opened_at`/`opening_cash` внутри `open_shifts[]` сокращены до того, что реально читает фронт; полный список полей фронт игнорирует безопасно, разбирает по имени, а не по позиции):

```json
{
  "cashbox_warning": {
    "code": "shared_cashbox_open_shift",
    "cashbox_id": "95bd3a14-72c2-45dd-9b58-b95dd0120a95",
    "cashbox_name": "Основная касса компании",
    "message": "На кассе «Основная касса компании» уже открыта смена: Балнура Мыломойка. По её данным в ящике ожидается 6888.00 сом. Проверьте, что вы открыли смену на своей кассе — иначе при закрытии будет расхождение на чужие деньги.",
    "open_shifts": [
      {
        "shift_id": "29e4e801-5317-485f-842a-75b070a2a839",
        "cashier_id": "db063122-f22b-4b5d-8558-8526cda93944",
        "cashier_display": "Балнура Мыломойка",
        "opened_at": "2026-09-23T10:04:59.306874+06:00",
        "opening_cash": "6738.00",
        "drawer_expected_cash": "6888.00"
      }
    ]
  }
}
```

Важно про `drawer_expected_cash`: это **реальное содержимое чужого ящика** (`opening_cash` чужой смены + её наличные продажи на момент ответа), а не её `opening_cash` (в примере выше — `6738.00` против фактических `6888.00`). Показывать нужно именно `drawer_expected_cash`, не `opening_cash`.

Фронт рендерит `warning.message` как есть (готовый русский текст с бэка, без собственного шаблона) — см. §3.1.

## 3. Как это работает на фронте

### 3.1 Общий компонент баннера

`src/entities/shift/ui/CashboxWarningBanner.tsx` — рендерит `warning.message` + список `open_shifts[]` (кассир: сумма). Используется как **постоянный баннер** (не toast — предупреждение не должно исчезать само, иначе смена останется неправильной на весь день незамеченной):

- `src/pages/shifts/ui/ShiftDetail.tsx` — баннер над метриками смены, для любой роли, просматривающей `/crm/shifts/{id}`.
- `src/pages/cashier/ui/ShiftPage.tsx` — баннер в рабочем экране кассира, прямо под заголовком смены (самое важное место — здесь кассир работает весь день).

### 3.2 Модалка при открытии

`src/pages/cashier/ui/OpenShiftPage.tsx` (`handleOpenShift`) — после успешного `POST /shifts/open/` проверяется `response.cashbox_warning`. Если есть — вместо обычного «Смена успешно открыта» показывается **блокирующая модалка** (`AlertModal`, тип `warning`) с текстом предупреждения и разбивкой по чужим сменам; переход назад на кассу происходит только после того, как кассир явно закрыл модалку (`pendingBackAfterWarning` state) — не автоматически через таймаут, как в обычном сценарии успеха.

### 3.3 Явный `cashbox` при открытии — снижение вероятности попадания в этот сценарий (частичное, см. ниже)

`OpenShiftPage.tsx` → `resolveExplicitCashboxId()`: перед отправкой `POST /shifts/open/` фронт запрашивает `GET /construction/cashboxes/`, резолвит роль (`pos_main`/`pos_branch`, та же логика, что и раньше — `resolvePosCashboxRole`) и, **если находится ровно одна активная касса** с этой ролью (и филиалом, если применимо) — передаёт её `id` явным полем `cashbox` в теле открытия.

**Важная оговорка (не была очевидна на момент первой версии этого документа):** этот механизм фильтрует кассы по совпадению `role` с ожидаемым (`pos_main`/`pos_branch`). Если у компании роль вообще не проставлена (`role: null` — ровно случай «Маркета» из §1) — совпадений 0, `cashbox` не передаётся. Если ролей несколько с дублями `pos_main` — совпадений >1, тоже не передаётся. **В обоих случаях фронт намеренно не угадывает** — лучше промолчать и довериться серверной эвристике + `cashbox_warning`, чем подставить неверный id самостоятельно. Это осознанный выбор, не недоработка: клиент не может надёжно отличить «правильную» кассу от остальных без ролей/привязок, которые есть только на бэке.

Охват по базе (аудит BE, 237 компаний с активными кассами):

| Категория | Компаний | `resolveExplicitCashboxId()` сработает? |
|---|---|---|
| Роль проставлена однозначно | 155 | ✅ Да — `cashbox` передаётся явно |
| Роль не проставлена ни у одной кассы (случай «Маркета») | 44 | ❌ Нет — 0 кандидатов |
| Дубли `pos_main` ([pos-main-duplicate-role-bug.md](./pos-main-duplicate-role-bug.md)) | 38 | ❌ Нет — >1 кандидат |

Итого механизм закрывает **155 из 237 компаний (~65%)** — именно те, у кого конфигурация касс и так была в порядке. Для оставшихся **82 (~35%)** — тех, где инцидент вида «989 сом» реально может повториться — единственная защита сегодня это `cashbox_warning` (§2–3.2). Корневое исправление для этих 82 компаний — на бэке, см. §6.

## 5. Финальная проверка на проде (BE, 2026-09-23)

- У исправленной смены (для которой раньше `cashbox_warning` отсутствовал в ответе закрытой смены) — ключ присутствует со значением `null`, `cash_diff = 0.00`.
- У открытой смены «Кай-Нара» на общей кассе — приходит предупреждение с реальным остатком ящика `32 880.68` (значение из `drawer_expected_cash`).

## 6. Что дальше — корневая причина для оставшихся 82 компаний

`cashbox_warning` — страховка, она уже работает и проверена. Но для 82 из 237 компаний (§3.3) кассир всё ещё может **сначала** попасть не на ту кассу — предупреждение сработает постфактум, а не предотвратит путаницу. Два варианта лечения на бэке (предложены BE, порядок важен):

1. **Проставить роли задним числом (рекомендуется в первую очередь).** Разово по 44 компаниям без единой проставленной роли + разобрать 38 с дублями `pos_main`. Ничего не ломает сегодня: после этого `resolveExplicitCashboxId()` на фронте начинает работать для всех 237 компаний без единой строчки нового кода, и резолв на бэке перестаёт доходить до эвристики по имени.
2. **Убрать эвристику по подстроке из `resolve_cashbox()`.** Если касса не определилась однозначно по `branch_id`/`role` — возвращать ошибку («укажите кассу явно»), а не угадывать по названию. Жёстче и убирает класс проблемы целиком, но требует, чтобы фронт **всегда** мог передать `cashbox` — то есть должно идти **после** варианта 1, иначе 82 компании потеряют возможность открыть смену вовсе.

Рекомендация: начинать с варианта 1 — он безопасен, разблокирует уже написанный код на фронте и не требует релиза. Вариант 2 имеет смысл как второй шаг, когда роли у всех компаний в порядке.
