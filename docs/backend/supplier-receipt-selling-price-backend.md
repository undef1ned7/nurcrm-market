# Маркет — Приход: пересчёт цены продажи по наценке

**Экран:** `/crm/market/procurement/receipt`  
**Фронт:** `src/pages/warehouse/ui/supplierReceipt/hooks/useSupplierReceipt.tsx`  
**Эндпоинт:** `POST /main/suppliers/{supplier_id}/receipt/`  
**Статус:** ⚠️ Требуется правка на бэкенде. Фронт **не** патчит товар. Контракт тела запроса не менять.

Связанная формула карточки товара: `docs/flutter/add-product.md` §9.2.

Не использовать `/api/v1`.

---

## 1. Проблема

Администратор оприходует товар с новой ценой закупки. Каталожная цена продажи (`product.price`) остаётся старой, хотя у товара есть `markup_percent`.

Пример (факт на проде):

```http
POST /main/suppliers/4bce59dd-10a0-4708-bcf3-9be66aaace2a/receipt/
```

```json
{
  "items": [
    {
      "product": "992e5a01-c875-48d7-9a19-1fd6c8face24",
      "qty": 100,
      "purchase_price": 120
    }
  ],
  "payment_type": "cash"
}
```

| Поле товара | До | После прихода (сейчас) | Ожидание |
|---|---|---|---|
| `purchase_price` | 100 | 120 | 120 |
| `markup_percent` | `"10.0000"` | `"10.0000"` | `"10.0000"` (не пересчитывать вниз) |
| `price` (продажа) | 110 | **110** ← баг | **132** |

Маржа падает. Фронт не шлёт `price` и не делает `PATCH /main/products/{id}/`. Пересчёт должен быть **внутри этого же POST**, в одной транзакции с остатком и себестоимостью.

---

## 2. Что фронт уже шлёт (не менять)

```http
POST /main/suppliers/{supplier_id}/receipt/
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "items": [
    { "product": "<uuid>", "qty": 100, "purchase_price": 120 }
  ],
  "payment_type": "cash"
}
```

`payment_type`: `cash` | `debt` | `prepayment`.

| Поле | Обяз. | Правило |
|---|---|---|
| `items[].product` | да | uuid товара |
| `items[].qty` | да | > 0 |
| `items[].purchase_price` | нет | ≥ 0; если нет — взять текущий `product.purchase_price` |
| `items[].price` | — | **не слать**. Бэк считает сам |
| `items[].markup_percent` | — | **не слать**. Брать с карточки товара **до** обновления закупки |

Фронт не будет добавлять GET/PATCH товара вокруг прихода.

---

## 3. Требуемое поведение (обязательно)

Для **каждой** строки `items[]` в том же запросе, атомарно с приходом:

1. Прочитать товар **до** записи новой закупки: `markup_percent` (алиас `markup`) и текущий `price`.
2. Записать `product.purchase_price` = `items[].purchase_price` (как сейчас).
3. Если `markup_percent` есть и ≥ 0, и `purchase_price` ≥ 0:

   ```
   selling = purchase_price * (1 + markup_percent / 100)
   product.price = round(selling * 100) / 100
   ```

   Пример: закупка `120`, наценка `"10.0000"` → продажа `132.00`.

4. **`markup_percent` не пересчитывать** из старой продажи и новой закупки. Иначе после шага 2 наценка станет отрицательной и продажа «залипнет».
5. Если наценки нет / `null` / поле пустое — `price` не трогать, только закупка и остаток.
6. Если посчитанная продажа уже равна текущей `price` — `price` можно не писать (идемпотентность).
7. Ошибка пересчёта цены **не должна** оставлять приход без остатка и наоборот: либо весь документ + цены, либо rollback.

Округление как в карточке товара: 2 знака после запятой (`(selling * 100).round() / 100`).  
В API цены и проценты — строки (`"132.00"`, `"10.0000"`), внутри можно decimal.

Оптовая `wholesale_price` этим ТЗ **не** меняется, пока отдельно не попросят.

---

## 4. Почему нельзя считать наценку после смены закупки

Неправильно:

1. `purchase_price` 100 → 120, `price` ещё 110  
2. `markup = (110 / 120 - 1) * 100` ≈ −8.33%  
3. продажа «по наценке» снова 110  

Правильно: взять `markup_percent` **до** шага 1 (`10.0000`), затем `120 * 1.10 = 132`, затем сохранить закупку 120 и продажу 132, наценку оставить 10%.

---

## 5. Приёмочные сценарии

| # | До | Тело прихода | После |
|---|---|---|---|
| 1 | purchase 100, markup 10%, price 110 | `purchase_price: 120` | purchase 120, markup 10%, **price 132** |
| 2 | purchase 100, markup 10%, price 110 | `purchase_price: 100` | purchase 100, markup 10%, price 110 (без изменения продажи) |
| 3 | purchase 100, markup `null`, price 150 | `purchase_price: 120` | purchase 120, markup `null`, price **150** |
| 4 | два товара в `items` | у A markup 10%, у B нет | A пересчитать, B только закупка |
| 5 | нет `purchase_price` в item | — | закупка и продажа как были (qty только) |

После успешного `200` `GET /main/products/{id}/` должен отдать новую `price` без дополнительного PATCH.

## 6. Чеклист приёмки Backend

- [ ] Тот же URL и то же тело, что шлёт фронт сейчас
- [ ] `price = round(purchase_price * (1 + markup_percent / 100), 2)` при наличии наценки
- [ ] `markup_percent` не уменьшается из‑за старой продажи
- [ ] Нет наценки → продажа не меняется
- [ ] Приход + остаток + закупка + продажа в одной транзакции
- [ ] Фронту не нужен `PATCH /main/products/{id}/` после прихода
