# Маркет — Массовое сканирование: один запрос на «Провести приход»

**Экран фронта:** «Массовое сканирование» (`/crm/sklad/mass-scan`, кнопка на `/crm/sklad`)
**Код фронта:** `src/features/mass-incoming/`
- `model/useMassIncoming.ts` — `save()`
- `api/massIncomingApi.ts` — `postMassIncomingBatch` (новое), остальные функции — текущий пошаговый фолбэк

**Статус:** ⚠️ Требуется новый эндпоинт `POST /main/products/mass-incoming/`. Фронт уже готов и пробует его первым при каждом «Провести приход»; пока бэкенд не отвечает 2xx на этом пути, автоматически используется старый пошаговый фолбэк (без изменений, продолжает работать).

Связанные доки: [../flutter/mass-scan.md](../flutter/mass-scan.md) (§9, открытый вопрос #1 — этот документ его закрывает), [alternate-barcodes.md](./alternate-barcodes.md).

## 1. Проблема

Сейчас «Провести приход» на маркет-компаниях без `main.Warehouse` (частый случай) отправляет **по 2-3 запроса на каждую позицию**:

1. Если товар из глобальной базы NurCRM (ещё нет карточки компании) — `POST /main/products/create-by-barcode/`.
2. Если у карточки поменяли цену — `PATCH /main/products/{id}/`.
3. Для самого прихода — `GET /main/products/{id}/` (свежий остаток) + `PATCH /main/products/{id}/` (новое количество).

На скриншоте DevTools по 4 товарам (2 из глобальной базы) это уже 10 запросов: 2×`create-by-barcode` + 4×`GET` + 4×`PATCH`. При обычном приёме поставки на 20-30 позиций это десятки последовательных round-trip'ов, каждый — реальная сетевая задержка (на слабом канале в магазине это секунды на позицию). Один разрыв соединения на 15-й позиции из 30 — и часть товара уже проведена, часть нет (см. `partialPosted` в [mass-scan.md](../flutter/mass-scan.md#53b-приход-без-склада-servermode--false)).

**Нужно:** один запрос, который одной транзакцией создаёт недостающие карточки, обновляет цены и добавляет остаток — либо всё, либо ничего.

## 2. Новый эндпоинт

```
POST /main/products/mass-incoming/
```

Авторизация как у остальных `/main/products/*` — компания берётся из токена, **`warehouse_id` не требуется** (в отличие от существующего `POST /warehouse/{warehouse_id}/mass-incoming/`, который у маркет-компаний обычно недоступен, т.к. `main.Warehouse` не заведён).

### 2.1 Тело запроса

```json
{
  "comment": "Массовое сканирование",
  "items": [
    { "product_id": "3cfab7d5-4881-...", "quantity": "10" },
    { "product_id": "ca400bdb-62f...",   "quantity": "3",  "price": "150" },
    {
      "barcode": "4601234567890",
      "name": "Кофе растворимый 90г",
      "price": "300",
      "quantity": "5",
      "from_global": true
    },
    {
      "barcode": "4601234567891",
      "name": "Скотч канцелярский",
      "price": "120",
      "quantity": "2",
      "from_global": false
    }
  ]
}
```

Каждый элемент `items[]` — **один из двух видов**, отличаются набором полей:

**A. Существующая карточка компании** (есть `product_id`):

| Поле | Тип | Обязательно | Смысл |
|------|-----|-------------|-------|
| `product_id` | string (uuid) | да | Товар компании (`main.Product`) |
| `quantity` | string, число ≥ 0 | да | Сколько **добавить** к текущему остатку (не абсолютное значение!) |
| `price` | string, число ≥ 0 | нет | Если передана и отличается от текущей цены карточки — обновить цену продажи |

**B. Карточки ещё нет — создать и сразу приходовать** (нет `product_id`, есть `barcode`):

| Поле | Тип | Обязательно | Смысл |
|------|-----|-------------|-------|
| `barcode` | string | да | Штрихкод новой карточки |
| `name` | string | да | Название товара |
| `price` | string, число ≥ 0 | да | Цена продажи новой карточки |
| `quantity` | string, число ≥ 0 | да | Начальный остаток |
| `from_global` | boolean | да | `true` — скопировать данные из `GlobalProduct` NurCRM по `barcode` (тот же источник, что сейчас использует `POST /main/products/create-by-barcode/`); `false` — создать вручную (как `POST /main/products/create-manual/`), для штрихкодов, которых нет ни в компании, ни в глобальной базе |

`quantity` и `price` — строки с точкой (как везде на фронте), но сервер должен принимать и без него (число), если это проще для сериализатора.

### 2.2 Поведение

1. **Одна транзакция на весь запрос.** Если хоть один элемент не проходит валидацию или создание/обновление падает — откатить всё, вернуть `400`/`409` (см. §2.4), в базе не должно остаться никаких частичных изменений (ни созданных карточек, ни изменённых остатков/цен).
2. Для элементов вида B:
   - `from_global: true` — найти `GlobalProduct` по `barcode`, создать `main.Product` компании с его данными (как `create-by-barcode` делает сейчас), применить переданные `name`/`price` (пользователь мог их отредактировать на экране перед отправкой — они приоритетнее данных из глобальной базы).
   - `from_global: false` — создать `main.Product` вручную (как `create-manual`) с переданными `barcode`/`name`/`price`.
   - Начальный остаток создаваемой карточки — `quantity` из запроса (не 0 + отдельный приход, как раньше).
3. Для элементов вида A: `quantity` **прибавляется** к остатку, который есть в БД **на момент выполнения запроса на сервере** (не тот, что видел клиент при сканировании) — это важно: между сканом и нажатием «Провести приход» через кассу могла пройти продажа этого же товара, прибавлять нужно к актуальному остатку, а не перезаписывать его.
4. Если передан `price` (и для A, и для B) — сохраняется как цена продажи карточки.
5. **Идемпотентность/гонки при создании (`from_global`/ручное создание):** если запрос обрывается на клиенте после того, как сервер уже закоммитил транзакцию, повторное нажатие «Провести приход» **не отправляется** (фронт снимает такие строки из списка сразу после успеха, до этого клиент не думает, что был успех, если реального 2xx не получил). Но если два независимых запроса от разных сотрудников создают карточку с одним и тем же `barcode` почти одновременно — это должно быть последней линией защиты: используйте `unique(company, barcode)` (если такого ограничения ещё нет) и возвращайте по нему понятную `400`, а не 500/дублирующуюся карточку.
6. Порядок применения элементов внутри запроса не важен для фронта — они независимы друг от друга (разные `product_id`/`barcode`), обрабатывайте как удобно бэку.
7. `comment` — опциональная строка, как в существующем `POST /warehouse/{id}/mass-incoming/`; можно использовать для истории движений/аудита, если такая история уже пишется для обычного прихода через `PATCH /main/products/{id}/`.

### 2.3 Успешный ответ

`200`/`201`, тело — на усмотрение бэка, минимально полезно вернуть созданные id (фронт их сейчас не использует, т.к. закрывает экран после успеха, но пригодится для истории/аудита и будущих доработок):

```json
{
  "created": [
    { "barcode": "4601234567890", "product_id": "e1cdd748-9be..." },
    { "barcode": "4601234567891", "product_id": "532685d6-15a..." }
  ],
  "items": [
    { "product_id": "3cfab7d5-4881-...", "quantity": "42" },
    { "product_id": "ca400bdb-62f...", "quantity": "18" },
    { "product_id": "e1cdd748-9be...", "quantity": "5" },
    { "product_id": "532685d6-15a...", "quantity": "2" }
  ]
}
```

`items[].quantity` в ответе — **новый итоговый остаток** после применения (не то, что было передано в запросе), фронт это поле пока не читает, но полезно для отладки и будущего UI («остаток стал X»).

### 2.4 Ошибки

Транзакция целиком откатывается при любой из них:

| Код | Когда | Тело |
|-----|-------|------|
| `400` | Невалидный элемент: нет `product_id` и нет `barcode`/`name`/`price`/`quantity`/`from_global` вместе; `quantity`/`price` не число или отрицательные; `from_global: true`, но `barcode` не найден в глобальной базе | `{"detail": "..."}` с указанием, какой элемент (по индексу или `barcode`/`product_id`) не прошёл |
| `404` | `product_id` не существует или принадлежит другой компании | `{"detail": "Товар {id} не найден"}` |
| `409` | Конфликт уникальности при создании (см. §2.2.5) — например, карточка с этим `barcode` уже существует, а прислали `from_global`/ручное создание вместо `product_id` | `{"detail": "Товар со штрихкодом {barcode} уже есть в каталоге компании"}` |
| `501`/`404`/`405` (эндпоинта нет) | Пока не задеплоено | Фронт трактует **любой** из этих трёх кодов как «не поддерживается» и переходит на старый пошаговый путь — **это временный, ожидаемый ответ на переходный период**, ничего специально возвращать не нужно, просто пока не регистрируйте роут |

Формат ошибок — как везде в проекте: `{"detail": "..."}`, `{"message": "..."}` или объект по полям. Отдельный парсинг под этот эндпоинт на фронте не нужен, уже используется общий `validateResErrors`.

## 3. Что уже сделано на фронте

- `postMassIncomingBatch()` (`src/features/mass-incoming/api/massIncomingApi.ts`) — шлёт единый запрос.
- `save()` (`src/features/mass-incoming/model/useMassIncoming.ts`) пробует батч первым при каждом нажатии «Провести приход». Как только видит `404`/`405`/`501` — на **всю оставшуюся сессию экрана** переключается на старый пошаговый путь (создание карточек → цены → приход по одной), чтобы не долбить несуществующий эндпоинт на каждое нажатие.
- Любая другая ошибка батч-запроса (400/404 по товару/409/500 и т.д.) показывается пользователю как есть, повторных шагов не будет — по контракту это all-or-nothing, ничего в БД не изменилось.
- Валидация на фронте перед отправкой (без изменений): обязательная цена для товаров из глобальной базы, только числовые цены ≥ 0, хотя бы одна позиция с `quantity > 0`.

## 4. Тест-кейсы

| # | Данные | Запрос | Ожидание |
|---|--------|--------|----------|
| 1 | Товар А (карточка есть), остаток 5 | `items: [{product_id: A, quantity: "10"}]` | 200, остаток А = 15 |
| 2 | Товар А, остаток 5, между сканом и запросом кассир продал 2 | `items: [{product_id: A, quantity: "10"}]` | 200, остаток А = **13** (5 - 2 продажа + 10 приход, а не 15) |
| 3 | Товар Б, цена 100 | `items: [{product_id: Б, quantity: "1", price: "120"}]` | 200, остаток +1, цена продажи Б = 120 |
| 4 | Штрихкод есть в глобальной базе NurCRM, карточки компании нет | `items: [{barcode: "...", name: "Кофе", price: "300", quantity: "5", from_global: true}]` | 201, создана карточка компании с этими name/price, остаток = 5 |
| 5 | Штрихкода нет нигде | `items: [{barcode: "...", name: "Скотч", price: "120", quantity: "2", from_global: false}]` | 201, создана карточка вручную, остаток = 2 |
| 6 | Один запрос: 2 существующих + 1 из глобальной базы + 1 ручной, один из существующих — чужой компании (`product_id` не найден) | весь `items[]` сразу | `404`, **ничего не создано и не изменено** — ни у своих товаров остаток не изменился, ни новых карточек не появилось |
| 7 | `from_global: true`, но по `barcode` в глобальной базе ничего нет | один элемент вида B | `400`, ничего не создано |
| 8 | Карточка с этим `barcode` уже есть в компании, но прислали её как вид B (`from_global`) вместо `product_id` | один элемент вида B | `409`, ничего не создано (не задвоить карточку) |
| 9 | `quantity: "-1"` | любой элемент | `400`, ничего не применено |
| 10 | Эндпоинт ещё не задеплоен | любой запрос | `404` (роут не зарегистрирован) — фронт сам уйдёт на старый путь, специально ничего возвращать не нужно |

## 5. Чек-лист для бэкенда

- [ ] Роут `POST /main/products/mass-incoming/`, авторизация как у остальных `/main/products/*`, компания из токена
- [ ] Элементы вида A (`product_id` + `quantity` [+ `price`]): `quantity` **прибавляется** к остатку на момент выполнения на сервере, не перетирает его
- [ ] Элементы вида B (`barcode`/`name`/`price`/`quantity`/`from_global`): создание карточки (из глобальной базы или вручную) сразу с указанным остатком, без отдельного шага «создать с quantity=0, потом приходовать»
- [ ] Вся операция — одна транзакция, all-or-nothing (см. тест-кейс #6)
- [ ] `409` при попытке создать вид B с `barcode`, который уже есть у компании как карточка (защита от дублей при гонке/повторной отправке)
- [ ] `400` с понятным `detail` на невалидные `quantity`/`price` (нечисловые, отрицательные) и на `from_global: true` без совпадения в глобальной базе
- [ ] `404` при несуществующем/чужом `product_id`
- [ ] Ответ включает `created[]` (barcode → новый product_id) и, желательно, `items[].quantity` — итоговый остаток
- [ ] Пока роут не задеплоен — не регистрировать его вовсе (фронт ждёт `404`/`405`/`501` как сигнал «нет пока», это не баг)
