# Перемещение товаров между складами / филиалами + накладная (ТОРГ-13)

**Статус:** фронт реализован (2026-09-30), бэк — нужно сделать. Фронт ходит на эндпоинты ниже; пока их нет, страница `/crm/branch/transfers` покажет ошибку загрузки.

Фронт: `src/entities/branch/api/transferApi.ts`, `src/pages/branches/ui/transfers/*`.

---

## 1. Что делает фича

Владелец/админ переносит товары **между главным складом и филиалами** (в любом направлении, филиал → филиал тоже).
При проведении:

1. остаток на складе-отправителе уменьшается;
2. остаток на складе-получателе увеличивается;
3. создаётся документ «Накладная на внутреннее перемещение» (форма ТОРГ-13) с номером; фронт рисует из него PDF.

**Это не продажа и не расход:** кассовых движений (`cashflow`), долгов, смен и аналитики выручки/расходов перемещение не создаёт и не меняет. Себестоимость и розница товара при перемещении не меняются.

## 2. Вопрос модели данных (важно, требует решения бэка)

Сейчас на фронте у товара одно поле `branch` (id филиала или `null` = главный склад) — см. фильтры `branch` в `GET /main/products/list/`. Возможны две схемы:

| Схема | Как перемещать | Комментарий |
|---|---|---|
| **A. Остаток по складам** (`ProductStock(product, branch, quantity)`) | Списываем/начисляем строки `ProductStock` | Правильно, но требует, чтобы `quantity` в списке товаров считалось **для запрошенного склада** |
| **B. Товар принадлежит филиалу** (одна запись = один склад) | Уменьшаем `quantity` у товара-источника; в получателе находим двойник (тот же `barcode`, иначе `article`+`name`) и увеличиваем, иначе **создаём копию** товара с `branch = получатель` (те же категория, бренд, цены, единицы) | Проще внедрить сейчас, но нужны правила поиска двойника |

Фронту всё равно: он оперирует только `product` (id на складе-источнике) и `quantity`. **Выбранную схему прошу вписать сюда** и учесть в п. 4.

Партии/сроки годности (`product-batch-expiry-backend.md`): если у товара есть партии, перемещать нужно **по FIFO/FEFO из источника**, сохраняя срок годности в получателе. Если бэк пока этого не умеет — перемещать общим остатком и зафиксировать это ограничение здесь.

## 3. Эндпоинты

Префикс `/api`. Авторизация Bearer. Права: `can_view_branch` (просмотр), создание/отмена — owner/admin (или отдельное право — см. вопросы).
Компания берётся из токена; все запросы фильтруются по компании. Филиалы обязаны принадлежать этой же компании.

### 3.1 `GET /main/branch-transfers/` — список

Query:

| параметр | тип | описание |
|---|---|---|
| `branch` | uuid | перемещения, где филиал — отправитель **или** получатель |
| `from_branch`, `to_branch` | uuid \| `main` | точный фильтр; `main` = главный склад |
| `status` | `completed` \| `cancelled` | |
| `date_from`, `date_to` | `YYYY-MM-DD` | по полю `date` |
| `search` | string | по `number`, названиям складов, `comment` |
| `page` | int | пагинация DRF (`count/next/previous/results`) |

Ответ — страница объектов из 3.2. В списке `items` можно **не отдавать** (фронт сам запросит деталку для карточки и PDF), но тогда обязательны:

- `items_count` — число позиций (колонка «Позиций» в истории);
- `total_quantity`, `total_amount`;
- `created_by.full_name` (колонка «Провёл»);
- `from_branch` / `to_branch` с `name`.

Пагинация обязательна (`count`, `next`, `previous`): история показывает «Найдено: N» и кнопки «Назад / Далее» по `page`.

Сортировка по умолчанию: `-date, -created_at`.

```json
  "seller": {

    "inn": "01234567890123",
    "okpo": "12345678",
    "address": "г. Бишкек, ул. …",

      "id": "…",

  "cancelled_at": null,
  "cancel_reason": null

```

Правила полей:

- `from_branch` / `to_branch`: **`null` = главный склад**, иначе `{id, name}`.
- `items[].name/article/barcode/unit/price` — **снимок на момент проведения** (не пересчитывать при последующем изменении товара, накладная — юридический документ).
- `price` — учётная цена за единицу: предлагаю `purchase_price` (себестоимость); если её нет — розничная `price`. Поставить один вариант и не менять. `amount = quantity × price`.
- `seller` — реквизиты компании (те же, что в `GET /main/sales/json/{id}/invoice/`).
- Числа — строки с точностью Decimal (как в остальном API) или числа; фронт принимает оба.

### 3.3 `POST /main/branch-transfers/` — создать и **сразу провести**

```json
{
  "from_branch": null,
  "to_branch": "7d2e…",
  "date": "2026-09-30",
  "comment": "Пополнение витрины",
  "items": [
    { "product": "a1f0…", "quantity": 12 }
  ]
}
```

`product` — id товара **на складе-отправителе**. `from_branch/to_branch`: `null` = главный склад.

Валидация (ответ `400`, формат DRF `{"field": ["…"]}`, `items` — списком по позициям; тексты на русском, фронт их показывает как есть):

- `from_branch != to_branch` (включая оба `null`);
- оба филиала существуют, из этой компании, **активны** (`is_active`);
- `items` не пустой, без дубликатов `product`;
- `quantity > 0`; для штучных товаров — целое (для весовых — дробное допустимо);
- товар принадлежит складу-отправителю и той же компании;
- `quantity <= остаток источника` → `{"items":[{"quantity":["Недостаточно на складе: доступно 5"]}]}`;
- `date` не позже сегодня + 1 день (бизнес-таймзона Asia/Bishkek, UTC+6); ретро-даты разрешены.

Проведение — **одна транзакция** (`transaction.atomic`) с блокировкой строк остатков (`select_for_update`) в детерминированном порядке (по `product_id`), чтобы два параллельных перемещения не увели остаток в минус. Нумерация `number` — последовательная по компании (`ПЕР-000001`), уникальная, без дыр при откате (генерировать внутри той же транзакции).

Успех: `201` + объект из 3.2 (с `items`, `seller`) — фронт сразу строит PDF из этого ответа.

Идемпотентность: желательно принимать заголовок `Idempotency-Key` (двойной клик по кнопке не должен создавать два документа). Фронт блокирует кнопку на время запроса, но сеть может ретраить.

### 3.4 `POST /main/branch-transfers/{id}/cancel/` — отмена (сторно)

Body: `{"reason": "…"}` (необязательно).

- Только `status == completed`; иначе `400` «Перемещение уже отменено».
- Возвращает остатки: у получателя `-quantity`, у отправителя `+quantity`, в одной транзакции.
- Если у получателя уже нет нужного остатка (успели продать) → `400` «Нельзя отменить: товар «X» уже частично продан/списан на складе-получателе (доступно N)». Частичной отмены нет.
- Документ **не удаляется**: `status = cancelled`, `cancelled_at`, `cancel_reason`, кто отменил. Номер остаётся занятым.
- Ответ: `200` + объект 3.2. Фронт перезагружает список.

Редактирования проведённого перемещения нет (только отмена и новое перемещение).

### 3.5 Изменение существующего эндпоинта: `GET /main/products/list/`

Поля товара, которые читает форма: `id`, `name`, `barcode`, `article`, `unit`, `quantity`, `price`, `purchase_price`, `is_weight`. Для `is_weight=false` фронт не даёт ввести дробное количество; сумма в итоговой строке формы — оценка по `purchase_price` (иначе `price`), настоящую сумму считает бэк.


Форма перемещения ищет товары **на складе-отправителе**:

```
GET /main/products/list/?search=<строка>&page_size=30            # главный склад
GET /main/products/list/?branch=<uuid>&search=<строка>&page_size=30 # филиал
```

Нужно:

- **Без `branch`** — фронт считает ответ остатками главного склада (так же работает `/crm/sklad`). Важно: если у компании есть филиалы, запрос без `branch` должен возвращать **только товары главного склада**, а не все товары компании — иначе в форме перемещения будут чужие остатки. Подтвердите текущее поведение. `branch=<uuid>` — только этого филиала.
- `quantity` в ответе — остаток **именно этого склада**.
- `search` — по названию и штрихкоду (в т.ч. доп. штрихкодам, см. `alternate-barcodes.md`); сейчас, по `warehouse-filters-backend.md`, поиск по `article` не работает — для формы перемещения желательно добавить.
- Поддержать `page_size` (до 100).

## 3.6 Как фронт использует API (для понимания сценариев)

| Экран | Маршрут | Запросы |
|---|---|---|
| История | `/crm/branch/transfers` | `GET …/branch-transfers/?page&status&search&date_from&date_to&from_branch&to_branch` (`main` = главный склад) |
| История филиала | `/crm/branch/transfers?branch=<id>&dir=in\|out` | `branch=<id>` (все), `to_branch=<id>` (входящие), `from_branch=<id>` (исходящие) |
| Карточка перемещения | `…?open=<id>` (боковая панель) | `GET …/{id}/`, `POST …/{id}/cancel/` с `reason` |
| Создание | `/crm/branch/transfers/new?from=&to=` | `GET /main/products/list/?branch=<id>&search=` (без `branch` — главный склад) (в т.ч. по штрихкоду со сканера), `POST …/branch-transfers/` |
| «Повторить» | `/crm/branch/transfers/new?repeat=<id>` | `GET …/{id}/` → позиции копируются, остаток проверяет сервер при `POST` |
| Вкладка «Перемещения» в карточке филиала | `/crm/branch/<id>` | `GET …/branch-transfers/?branch=<id>` (первые 10 + `count`) |

После успешного `POST` фронт сразу скачивает PDF накладной из ответа и открывает её карточку в истории.

## 4. Влияние на остальное

| Область | Требование |
|---|---|
| Остатки / склад | п. 2. История движения товара должна показывать «Перемещение ПЕР-N: из … в …» (если есть журнал движений) |
| Кассы, смены, долги | **Не затрагиваются** |
| Аналитика продаж/финансов | Не учитывать как продажу/закупку/расход |
| Инвентаризация | Перемещение во время открытой инвентаризации склада — на усмотрение бэка (рекомендация: запретить с понятной ошибкой) |
| Пользователь-филиал (`branch_ids` не пуст) | Видит только перемещения, где его филиал — отправитель/получатель. Создавать — только **из** своего филиала (или не может вовсе; см. вопросы) |
| Realtime | Опционально: событие `market.branch_transfer.created` получателю (см. `kassa/realtime-notifications-backend.md`) |
| Удаление филиала | Запретить удалять филиал, у которого есть перемещения или остатки (сейчас `DELETE /users/branches/{id}/` фронт вызывает без предупреждений) |
| Деактивация филиала | Перемещать в неактивный нельзя (валидация п. 3.3); из неактивного — можно (вывоз остатков) |

```python
class BranchTransfer(models.Model):
    id = UUIDField(primary_key=True)
    company = FK(Company)
    number = CharField(max_length=32)            # unique per company
    status = CharField(choices=[("completed",..),("cancelled",..)])
    date = DateField()
    from_branch = FK(Branch, null=True, blank=True, on_delete=PROTECT, related_name="+")
    to_branch   = FK(Branch, null=True, blank=True, on_delete=PROTECT, related_name="+")
    comment = CharField(max_length=500, blank=True)
    created_by = FK(User, on_delete=SET_NULL, null=True)
    created_at = DateTimeField(auto_now_add=True)
    cancelled_at = DateTimeField(null=True)
    cancelled_by = FK(User, null=True, on_delete=SET_NULL, related_name="+")
    cancel_reason = CharField(max_length=500, blank=True)

    class Meta:
        constraints = [UniqueConstraint(fields=["company", "number"], name="uniq_transfer_number")]

class BranchTransferItem(models.Model):
    transfer = FK(BranchTransfer, related_name="items", on_delete=CASCADE)
    product = FK(Product, on_delete=PROTECT)      # товар-источник
    dest_product = FK(Product, null=True, on_delete=PROTECT, related_name="+")  # схема B
    name, article, barcode, unit = …              # снимок
    quantity = DecimalField(max_digits=14, decimal_places=3)
    price = DecimalField(max_digits=14, decimal_places=2)
```

## 6. Тесты, которые нужно написать

1. Главный → филиал: остатки сместились на `quantity`, номер `ПЕР-000001`, `201` с `items` и `seller`.
2. Филиал → филиал и филиал → главный.
3. `from == to` (в т.ч. оба `null`) → `400`.
4. `quantity` > остатка → `400`, остатки не изменились, номер не «сгорел».
5. Дубликат `product` в `items` → `400`.
6. Неактивный филиал-получатель → `400`; чужой филиал/товар другой компании → `400/404`.
7. Гонка: два параллельных перемещения одного остатка — одно проходит, второе `400`, остаток не отрицательный.
8. Отмена: остатки вернулись; повторная отмена → `400`; отмена, когда у получателя уже продали → `400`, ничего не изменилось.
9. Перемещение не создаёт `Cashflow`, не меняет смены/долги/выручку в аналитике.
10. Список: фильтры `branch`, `from_branch=main`, `status`, `date_*`, `search`; пользователь-филиал видит только свои.
11. Схема B: двойник в получателе найден по `barcode`; если нет — создан с теми же ценами, `branch = получатель`; повторное перемещение не плодит копии.

## 7. Открытые вопросы к бэку

1. Схема A или B (п. 2)? Как поступаем с партиями/сроками годности?
2. Какая учётная цена в накладной: `purchase_price` или розничная? (фронту нужно одно из двух, сейчас читает `items[].price`.)
3. Нужен ли отдельный флаг права `can_manage_branch_transfers`, или достаточно owner/admin + `can_view_branch`?
4. Может ли пользователь-филиал (сотрудник) создавать перемещения **из своего** филиала? Фронт сейчас скрывает раздел «Филиалы» для таких пользователей, поэтому UI для них не предусмотрен — это отдельная задача.
5. Нужен ли двухэтапный процесс «отправлено → принято получателем» (статус `in_transit`, приёмка)? Сейчас реализовано **проведение сразу** (`completed`). Если понадобится приёмка, добавляются статусы `sent`/`received` и эндпоинт `/receive/` — фронт расширяется без слома текущего контракта.
6. Серверная генерация PDF (`GET …/{id}/pdf/`) не требуется: фронт строит PDF сам через `@react-pdf/renderer` из JSON п. 3.2 — как для накладных продаж (`/main/sales/json/{id}/invoice/`).
