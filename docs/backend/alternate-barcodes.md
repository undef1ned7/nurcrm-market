# Маркет — Дополнительные штрих-коды товара (`alternate_barcodes`)

**Экраны фронта:**
- Касса: `/crm/market/cashier` (`src/Components/Sectors/Market/CashierPage/CashierPage.jsx`)
- Склад: `/crm/sklad` (`src/Components/Sectors/Market/Warehouse/Warehouse.jsx`)
- Печать штрих-кодов: `/crm/barcodes` (`src/Components/Deposits/Sklad/components/BarcodePrintTab.jsx`)
- Карточка товара: `src/Components/Deposits/Sklad/AddProductPage` (поле «Дополнительные штрихкоды»)

**Эндпоинты, которых касается задача:**
- `POST /main/pos/sales/{sale_id}/scan/` — скан в кассе
- `GET /main/products/warehouse-barcode/{code}/` — поиск по штрихкоду на складе
- `GET /main/products/global-barcode/{code}/` — поиск по штрихкоду в каталоге
- `GET /main/products/list/?search=` — поиск товаров (в т.ч. ручной ввод кода в кассе)
- `GET /main/products/{id}/` — карточка товара

**Статус:** ⚠️ Требуются правки на бэкенде. На фронте сделаны обходные пути (см. §4), но полноценно доп. коды заработают только после правок API. **2026-09-17: добавлено новое требование — поле `quantity` в каждом элементе `alternate_barcodes`, см. §6. Бэкенд подтвердил контракт §6.5, фикс обещан в течение дня (2026-09-17).**

---

## 1. Проблема

У товара, кроме основного `barcode`, может быть список дополнительных кодов — поле `alternate_barcodes` (массив строк). Фронт умеет их заводить и сохраняет через `POST/PATCH /main/products/…` (`parseAlternateBarcodesForApi`), они возвращаются в списке и в карточке и показываются в UI («Доп. штрихкоды: …»).

Но дальше они нигде не работают:

1. **Скан в кассе.** Кассир сканирует дополнительный код → `POST /main/pos/sales/{id}/scan/` отвечает «Товар с таким штрих-кодом не найден». Товар в корзину не попадает, хотя код у него сохранён.
2. **Скан на складе.** `warehouse-barcode/{code}/` и `global-barcode/{code}/` находят товар только по основному `barcode`, по дополнительному — 404.
3. **Поиск.** Ввод дополнительного кода в поиск (`?search=`) ничего не находит — фильтр смотрит на `name`/`barcode`/`article`, но не на `alternate_barcodes`.
4. **Печать.** Печатать можно было только основной код (это была проблема фронта — уже исправлено, см. §4).

Практический эффект: товар с двумя кодами (например, старая и новая упаковка, или собственный внутренний код + заводской EAN) в кассе пробивается только одним из них.

---

## 2. Требуемое поведение

**Главное правило:** везде, где API ищет товар по штрих-коду, поиск должен идти по **множеству** `{barcode} ∪ alternate_barcodes`, а не только по `barcode`.

### 2.1 `POST /main/pos/sales/{sale_id}/scan/`

```json
{ "barcode": "460123456789" }
```

- Искать товар в пределах компании по основному **и** дополнительным кодам.
- Если найден ровно один — добавить в корзину как сейчас (поведение и формат ответа не меняются).
- Если найдено несколько товаров (код встречается у разных товаров) — вернуть уже существующий ответ про неоднозначность: `409` c `{"ambiguous": true, "message": ..., "matches": [{"id": ..., "name": ...}]}`. Фронт покажет модалку выбора (`BarcodeAmbiguityModal`) — этот контракт уже реализован и работает.
- Если не найден — как сейчас, 404 / `{"error": "Товар с таким штрих-кодом не найден"}`.

### 2.2 `GET /main/products/warehouse-barcode/{code}/` и `GET /main/products/global-barcode/{code}/`

То же самое: искать по основному + дополнительным кодам, формат ответа не меняется.

### 2.3 `GET /main/products/list/?search=<код>`

Добавить `alternate_barcodes` в поиск, чтобы:
- ручной ввод кода в поиске кассы находил товар;
- страница печати `/crm/barcodes` находила товар по любому его коду;
- работал фолбэк фронта (см. §4) — он ищет товар через `?search=<код>` и затем сам сверяет коды.

Требование к поиску по коду: **точное совпадение должно попадать в выдачу** (сейчас `search` — icontains по нескольким полям, этого достаточно, важно лишь добавить в список полей `alternate_barcodes`).

### 2.4 Сериализация

`alternate_barcodes` должен присутствовать (даже пустым массивом) в:
- `GET /main/products/list/` (список — используется кассой и печатью);
- `GET /main/products/{id}/` (карточка);
- ответах `warehouse-barcode` / `global-barcode`.

Сейчас список его отдаёт — важно не потерять при изменениях, фронт на это опирается.

### 2.5 Нормализация кодов

Сравнение должно быть устойчивым к типичным расхождениям сканера и карточки:

1. Обрезать пробелы по краям (`" 460123456789 "` = `"460123456789"`).
2. Сравнивать как строки, **не** приводить к числу — ведущие нули значимы (`0460123456789` ≠ `460123456789` как числа, но сканер EAN-13 часто отдаёт код без ведущего нуля).
3. Рекомендуется дополнительно сверять «EAN-нормализованную» форму: если сохранённый код — 13 цифр с ведущим `0`, то скан 12 цифр без него должен находить товар (и наоборот). На фронте эта логика уже есть при печати (`getBarcodePrintEncoding`), в поиске её нет.

### 2.6 Валидация при сохранении товара

- Дубли внутри `alternate_barcodes` одного товара — схлопывать (фронт уже это делает, но подстраховаться стоит).
- Код, совпадающий с `barcode` того же товара — отбрасывать.
- Совпадение кода с другим товаром компании: **не запрещать жёстко** (бывают одинаковые заводские коды), но тогда при скане возвращать `409 ambiguous` (см. §2.1). Если решите запрещать — верните `400` с понятным `detail`, фронт его покажет.

## 4. Что уже сделано на фронте

1. **Печать (`/crm/barcodes`) — исправлено полностью, бэк не нужен.** В карточке товара появился выбор штрих-кода, если у товара их несколько: «(основной)» / «(доп.)». Выбранный код используется в предпросмотре, печати на XP-365B, массовой печати и печати на A4. Товар, у которого заполнены только дополнительные коды, теперь тоже можно напечатать и выбрать в массовую печать.
2. **Скан в кассе — временный фолбэк.** Если `/scan/` отвечает «не найден» (404 или текст с «не найден»), фронт сам ищет товар по всем его кодам: сначала в уже загруженной странице каталога, затем через `GET /main/products/list/?search=<код>`, и добавляет найденный товар в корзину обычным способом. Ошибки другого рода (нет смены, нет остатка, неоднозначность) фолбэк не трогает.
3. **Скан на складе (`/crm/sklad`) — такой же фолбэк** после `warehouse-barcode` и `global-barcode`.

Ограничения фолбэка (поэтому правки на бэке всё равно нужны):
- он работает, **только если** `?search=<код>` возвращает товар — то есть требует §2.3;
- это лишний запрос на каждый «непонятый» скан — заметно на большом каталоге;
- он не даёт серверной проверки неоднозначности (§2.1) и обходит серверную логику скана (весовые коды, упаковки).

После реализации §2 фолбэк перестанет срабатывать сам собой — удалять его не нужно, он останется страховкой.

## 6. Новое поле `quantity` в `alternate_barcodes` (2026-09-17)

### 6.1 Контекст и мотивация

На складе переделан UI ввода доп. штрихкодов: вместо textarea со свободным текстом — структурированные строки с тремя полями: **штрихкод**, **название варианта** (вкус/цвет и т.д., уже было) и **количество в упаковке** (новое). Пример use case: товар «Асу вода» имеет доп. штрихкод для позиции «Клубничный» — упаковка, в которой 6 бутылок; кассир сканирует именно этот код.

Название варианта (`name`) уже поддерживается бэком и используется на фронте (в т.ч. в новой фиче — на кассе к основному названию товара подставляется название варианта: «Асу вода» + «Клубничный» → «Асу вода Клубничный», реализовано полностью на фронте, бэка не касается). Поле `quantity` бэк раньше не принимал.

### 6.2 Требуемая форма API

Элемент `alternate_barcodes` должен принимать и отдавать:

```json
{
  "barcode": "4870204391234",
  "name": "Клубничный",
  "quantity": 6
}
```

- `barcode` (string, обязателен) — как сейчас.
- `name` (string, опционален, может быть `""`) — как сейчас.
- `quantity` (number, опционален) — **новое поле**. Целое или дробное положительное число; означает количество единиц товара в упаковке, под которой зарегистрирован этот доп. штрихкод. Если не задано — поле можно не отправлять или отправлять без него (фронт не шлёт `quantity`, если пользователь его не заполнил).

### 6.3 Что нужно сделать на бэке

1. Добавить `quantity` в сериализатор/модель для элементов `alternate_barcodes` (сейчас там, по всей видимости, только `barcode`/`name`).
2. Принимать его при `POST/PATCH /main/products/…` и сохранять как есть (без округления, если это не целочисленное поле — уточните на своей стороне тип хранения).
3. Отдавать `quantity` обратно во всех местах, где уже отдаётся `alternate_barcodes` (список, карточка, barcode-эндпоинты — см. §2.4).
4. Валидация: если пришло `quantity <= 0` или нечисловое значение — отклонять эту запись (или весь запрос, на ваше усмотрение) с понятной ошибкой; `quantity` отсутствует — это валидный случай (не обязательное поле).
5. **Важно:** если сериализатор сейчас настроен строго (запрещает лишние поля), уточните — сейчас фронт уже отправляет `quantity`, и без правки на бэке это поле либо молча игнорируется (если сериализатор permissive), либо ловит `400` при сохранении товара (если strict). Дайте знать, какой из двух случаев сейчас происходит, и когда ждать фикса.

### 6.5 Ответ бэкенда (2026-09-17) — подтверждённый контракт

**Текущее поведение без фикса:** тихий игнор, без ошибки. `sync_product_alternate_barcodes` сейчас читает из входящего объекта только `barcode` и `name`; `quantity` никуда не попадает — ни в модель `ProductAlternateBarcode`, ни в ответ API. Фронт при этом не получает `400`.

**ETA:** в течение дня (2026-09-17) — миграция БД, сериализаторы, валидация, деплой.

**Финальная форма ответа** (`GET /main/products/list/`, `GET /main/products/{id}/`, `warehouse-barcode`, `global-barcode`):

```json
"alternate_barcodes": [
  { "barcode": "4870204391234", "name": "Клубничный", "quantity": 6 },
  { "barcode": "4870204391235", "name": "Без упаковки", "quantity": null }
]
```

- `quantity`: `integer > 0` или `null`, если не задано.
- На фронте: под это уже подстроено — `buildAlternateBarcodesForApi` округляет (`Math.floor`) и не шлёт `quantity`, если он `<= 0` или не число; инпут в форме — `type="number" min="1" step="1"`.

**Валидация на бэке:** `quantity` опционален; если передан и `<= 0` или не число — `400`:

```json
{ "alternate_barcodes": "Количество в доп. штрихкоде '4870204391234' должно быть положительным числом." }
```

Обратите внимание: ошибка приходит одной строкой на ключе `alternate_barcodes`, а не списком/по индексу элемента — это единственное, за чем стоит проследить на фронте при обработке ошибок сохранения товара (сообщение просто показывается пользователю как есть через общий `validateResErrors`, отдельного парсинга не требуется).
