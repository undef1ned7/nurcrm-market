# Баги в потоке продажи — сводный список (2026-09-29)

Компиляция всех проблем, найденных при разборе кассы `/crm/market/cashier`, истории продаж `/crm/sell`, возвратов и долга. Ничего из списка ещё не исправлено — это фиксация для дальнейшей работы, не отчёт о сделанном.

Контекст решения по продукту (2026-09-29): работаем только с долгом v2, все денежные движения (cashflows) создаёт бэкенд. Пункты ниже это учитывают.

## 1. 🔴 Двойная продажа/двойная оплата — общая корзина веб+мобилка без идемпотентности чекаута

**Где:** `src/entities/sale/model/saleThunk.ts` (`productCheckout`, `startSale`), `src/pages/cashier/ui/hooks/usePaymentPage.ts:432`

**Проблема:** Веб и мобилка используют одну апишку и один аккаунт кассира. Активная корзина резолвится по смене (`shift_id`), а не по устройству — `POST /main/pos/sales/start/` с одинаковым `shift` с двух устройств возвращает **один и тот же `sale.id`**. Если оба устройства (или ретрай после обрыва сети) отправят `checkout` почти одновременно на этот `sale.id`, backend может обработать оба запроса как отдельные продажи/платежи — двойное списание склада, двойная запись оплаты.

**Причина:** `productCheckout` и `startSale` не передают `idempotency_key` вообще. `payingInFlightRef` в `usePaymentPage.ts` защищает только от повторного клика в одной вкладке — не спасает от второго устройства и не перепроверяет статус продажи перед отправкой.

**Важно:** паттерн идемпотентности уже есть в проекте и работает — им просто не покрыли checkout:
- `returnSale` → `idempotency_key`, см. `src/shared/lib/tools/saleReturn.ts`, `buildSaleReturnSignature`
- `payDebtDeal` / `refundDeal` → `crypto.randomUUID()`, см. `src/entities/client/model/clientCreators.ts:134`
- `cashflow-change-requests` → `stableSignature(...)`, см. `src/entities/cash/lib/cashFlowChangeRequest.ts:87`

**Решение (см. обсуждение с Алмазом):**
1. Фронт генерирует ключ идемпотентности на попытку оплаты: `hash(user_id + platform + sale_id + тело_запроса)`, по аналогии с `idempotencyRef` в `RefundPurchase.tsx` — один и тот же ключ переиспользуется, пока не поменялся реальный интент (сумма/способ оплаты/состав корзины), новый генерится только при изменении.
2. Ключ уходит в `productCheckout` (в теле как `idempotency_key`, как в `/return/`, либо в заголовке — на усмотрение бэка).
3. Backend хранит ключ и при повторе с тем же ключом отдаёт уже существующий результат вместо повторной обработки.
4. То же самое стоит добавить в `startSale` — на случай гонки при создании самой продажи с двух устройств одновременно.
5. Опционально: перед `checkout` делать лёгкий `GET /pos/sales/{id}/` и проверять `status === "new"`, чтобы сразу показать «эта корзина уже оплачена» вместо слепой отправки.

**Кто чинит:** нужны изменения и на фронте (генерация+отправка ключа), и на бэке (дедупликация по ключу) — как уже сделано для `/return/` и `/deals/.../pay/`.

## 2. 🔴 Проверка «Товар 18+» никогда не блокирует продажу

**Где:** `src/pages/cashier/ui/hooks/cashier/useCashierProducts.ts:296-306` (`confirmAdultProduct`), `src/shared/ui/AlertModal/AlertModal.tsx:41-50`

**Проблема:** И `onConfirm`, и `onClose` в диалоге «Этот товар предназначен для совершеннолетних» вызывают `finish(true)`. `finish(false)` нигде не вызывается. Клик по фону модалки и Escape в `AlertModal` тоже трактуются как подтверждение (`onConfirm || onClose`). Как ни закрой диалог — товар 18+ добавляется в корзину. Проверка `if (!allowed) return;` в `useCashierCart.ts:134` — фактически мёртвый код, `allowed` не может быть `false`.

**Решение:** Добавить реальный отказ — кнопку «Отмена» с `finish(false)`, и `onClose`/Escape/клик по фону должны тоже резолвить `false` (закрытие без явного подтверждения = отказ), а не `true`. Нужна либо отдельная модалка с двумя кнопками, либо доработка `AlertModal`, чтобы уметь возвращать разный результат для «подтвердил» и «закрыл».

## 3. 🔴 Итог чека может подмениться суммой без скидки при `total = 0`

**Где:** `src/pages/cashier/ui/hooks/cashier/useCashierUi.ts:92`

```js
const total = parseFloat(currentSale?.total || 0) || cart.reduce(...)
```

**Проблема:** `0` — falsy в JS. Если сервер вернул честный `total: "0.00"` (100% скидка, бесплатный акционный товар, корзина после частичного возврата до нуля), `0 || X` откатывается на `X` — сумму корзины **без скидок**. Кассир увидит и потребует оплату за то, что должно быть бесплатным.

**Решение:**
```js
const serverTotal = currentSale?.total;
const total = serverTotal != null && serverTotal !== ""
  ? parseFloat(serverTotal)
  : cart.reduce(...);
```
Явная проверка на `null`/`""` вместо `||`.

## 4. 🟠 Дата долга съезжает на день из-за таймзоны (UTC+6)

**Где:** `src/pages/cashier/ui/paymentPage.utils.ts:35-44` (`getTodayIsoDate`, `addCalendarDaysToIso`)

**Проблема:**
```js
export function addCalendarDaysToIso(days) {
  const d = new Date();
  d.setHours(0, 0, 0, 0);          // локальная полночь
  d.setDate(d.getDate() + days);
  return d.toISOString().split("T")[0];   // конвертирует в UTC!
}
```
Локальная полночь в Бишкеке (UTC+6) — это 18:00 предыдущего дня по UTC. `toISOString()` всегда вернёт дату на день раньше нужной. То же в `getTodayIsoDate()` — используется как `min` для календаря первой даты платежа (`PaymentPageDebtSection.tsx:245`). `addCalendarDaysToIso` — фолбэк даты погашения для долга, когда `deferredDueDate` пуст (`usePaymentPage.ts:769`), уходит в `POST /clients/{id}/deals/` и `POST /main/debts/`.

**Показательно:** рядом, в `src/entities/sale/lib/buildDebtSchedule.ts:47-50`, есть **правильная** реализация `todayIsoDate()` через `getFullYear/getMonth/getDate` без конвертации в UTC — в кодовой базе два конкурирующих способа посчитать «сегодня», один рабочий, другой нет.

**Решение:** переиспользовать `todayIsoDate()`/`addDaysToIso()` из `buildDebtSchedule.ts` вместо локальных реализаций в `paymentPage.utils.ts`, либо переписать их так же (через `getFullYear/getMonth/getDate`, без `toISOString()`). Та же переменная бага есть в `src/features/warehouse-ops/ui/AddProduct/AddProductModal.tsx:29`, `src/shared/lib/tools/deferredPaymentDates.ts:1`, `src/pages/warehouse/ui/supplierReceipt/supplierReceiptUtils.ts:68` — 4 независимые копии `getTodayIsoDate` с одинаковой ошибкой, стоит завести одну общую утилиту.

## 6. 🟡 `postCashflowIfNeeded` фактически мёртв

**Где:** `src/entities/cash/lib/postCashflowIfNeeded.ts:46`, вызовы в `usePaymentPage.ts`

**Проблема:** Функция шлёт cashflow, только если `hasExplicitCashbox(payload.cashbox)` — а касса оплаты никогда не передаёт явный `cashbox` (маршрутизацию выбирает бэк). Поэтому вызов всегда no-op, независимо от `VITE_BE_CASHFLOWS`.

**Статус:** теперь это уже не совсем баг — раз договорились, что **все денежные операции создаёт бэк**, этот фронтовый фолбэк и должен быть мёртвым. Но код вводит в заблуждение: выглядит как рабочий путь, хотя не работает и не должен. Стоит либо явно задокументировать «это legacy no-op, не трогать», либо удалить вызовы, когда дойдут руки до чистки v1/cashflow-legacy кода (см. решение от 2026-09-29 — сейчас трогать не просили).

## 7. 🟡 Сделка-долг создаётся вторым запросом после checkout

**Где:** `src/pages/cashier/ui/hooks/usePaymentPage.ts:651-752`

**Проблема:** `productCheckout` (перевод продажи в статус `debt`, списание склада, чек) и создание сделки — два независимых запроса, второй идёт уже после успешного первого:
1. `POST /main/debts/` — легаси-запись для тарифа «Старт» (свой `try/catch`, `usePaymentPage.ts:668-696`).
2. `dispatch(createDeal(...))` — основная сделка с графиком (свой `try/catch`, `usePaymentPage.ts:698-751`).

Это две **независимые** точки отказа — возможны все 4 комбинации исходов (обе создались / только одна из двух / ни одна).

**Что происходит по шагам, если checkout прошёл, а `createDeal` (и/или `/main/debts/`) — нет:**

- Откатывать уже нечего: к моменту вызова `createDeal` checkout уже подтверждён бэком — продажа в статусе `debt`, товар списан со склада, чек создан. Ни один из двух catch-блоков ничего не откатывает.
- Кассир видит модальное окно-предупреждение (`showAlert`, требует клика «ОК») и дальше как ни в чём не бывало: если была предоплата — постится cashflow, печатается чек, показывается «Успешная оплата», корзина очищается, открывается новая.
- В системе: продажа помечена как `debt`, но **сделки (Deal) с графиком платежей нет** — она не появится ни в «Долгах» клиента, ни в его KPI, ни в списке сделок. Магазин физически отдал товар в долг, а отследить/взыскать этот долг через приложение нельзя — цифрового следа нет.
- Никакого сохранённого состояния о неудаче не остаётся: ни в localStorage, ни в Redux. Если кассир закрыл предупреждение и продолжил работу — информация теряется полностью, восстановить её можно только вручную сверкой продаж в статусе `debt` со списком сделок.

**Решение — сделать процесс самовосстанавливающимся (обсуждали, но не реализовано):**

Раз checkout и создание сделки — два разных запроса и бэк пока не гарантирует атомарность, компенсировать это можно очередью автоповтора на фронте:

1. **Персистентная очередь** (`localStorage`) недооформленных долгов: `{ saleId, createDealPayload, createDealDone, startDebtPayload, startDebtDone, attempts, nextAttemptAt }`. Задача кладётся в очередь сразу, как только `createDeal` и/или `/main/debts/` упали после успешного checkout — вместо (или вместе с) текущего разового `showAlert`.
2. **Фоновый процессор**, который сам, без участия кассира, периодически (с backoff: 10с → 30с → 1мин → 5мин → раз в 30мин, до победного) допробует недостающие запросы, пока оба флага (`createDealDone`, `startDebtDone`) не станут `true` — тогда задача убирается из очереди.
3. Запускать процессор: сразу при постановке в очередь (быстрый повтор транзиентных сетевых сбоев), по таймеру, пока очередь не пуста, и по событию `online` (реконнект сети).
4. Кассиру — ненавязчивый toast вместо блокирующей модалки («Оплата оформлена, долг дооформится автоматически»), и отдельное предупреждение только если попытки не проходят подолгу (например, после 5 неудач подряд) — чтобы не потерять сигнал о реальной проблеме, но не дёргать кассира на каждый ретрай.
5. Идемпотентность самих запросов остаётся на бэке отдельной темой (см. пункт 1) — очередь на фронте не отменяет необходимость `idempotency_key` в `createDeal`/`/main/debts/`, иначе повторные попытки после «потерянного» ответа (запрос на самом деле прошёл, но фронт не получил ответ) могут задвоить сделку.
6. Стратегическое решение — на бэке создавать сделку атомарно вместе с checkout (`debt_schedule` уже шлётся в checkout как extra-поле, см. `debt-installment-schedule-backend.md`), тогда фронтовая очередь становится не более чем подстраховкой на переходный период.

**Статус:** только зафиксировано и спроектировано, реализация не начата — по явной просьбе пока не трогать код, только искать баги.

## 8. 🔴 [Backend] Долг v2 «по месяцам» падает 400: `debt_days`/`debt_months` одновременно

**Где:** бэкенд (`NurCRM API`, отдельный репозиторий), уже задокументировано отдельно: [`docs/backend/kassa/debt-v2-months-xor-bug-backend.md`](./backend/kassa/debt-v2-months-xor-bug-backend.md)

**Проблема:** `POST /main/clients/{id}/deals/` с `debt_months: 3` (без `debt_days` в теле вообще) возвращает `400 {"debt_months": ["Нельзя одновременно указывать debt_days и debt_months."]}`. По дням (`debt_days` + `interval_days`) тот же сценарий проходит.

**Гипотеза причины:** поле `debt_days` модели имеет дефолт (похоже, `30`), который подставляется до XOR-проверки при сборке объекта — валидатор видит «оба поля заполнены», хотя клиент прислал только `debt_months`.

**Статус:** блокирует полный переход на v2-only для месячного графика. Пока просто фиксируем факт (пользователь попросил ничего не менять до подтверждения фикса на бэке).

## 9. 🔴 Оплата долга не переводит продажу обратно в «оплачено» — Sale и Deal никак не связаны

**Где:** `src/pages/cashier/ui/hooks/usePaymentPage.ts:698-746` (`createDeal` без `sale_id`), `src/entities/client/model/clientCreators.ts:130-146` (`payDebtDeal`), `src/entities/client/model/clientSlice.ts:169-175` (`payDebtDeal.fulfilled` — тело закомментировано), `docs/backend/kassa/debt-installment-schedule-backend.md:183`

**Проблема:** Продажа (`Sale`, `/main/pos/sales/{id}/`) и сделка-долг (`Deal`, `/main/clients/{id}/deals/{id}/`) — два разных объекта на бэке, и между ними **нет связи**:

1. При оформлении долга `createDeal` вызывается **без `sale_id`** — thunk его поддерживает (`saleThunk.ts:595-596`), но ни один из вызовов в `usePaymentPage.ts` (ни v1-, ни v2-ветка) его не передаёт. Это не случайность: `sale_id` намеренно не шлют, потому что POS-UUID (`/main/pos/sales/{id}`) не совпадает с ID Sale в модели deals — бэк отвечает `400 {"sale_id": ["Указанная продажа не найдена."]}` (см. таблицу полей в `debt-installment-schedule-backend.md`).
2. Значит созданный `Deal` **физически не знает**, из какой продажи он появился.
3. Когда долг гасится полностью — `payDebtDeal` → `POST /clients/{id}/deals/{id}/pay/` — обновляется только сам `Deal` (его `remaining_debt`/статус). У бэка нет способа понять, какую `Sale` нужно перевести в `paid`, потому что FK никогда не заполнялся.
4. Даже если бы бэк такую связь имел, фронт всё равно не обновит статус сам: `payDebtDeal.fulfilled` в `clientSlice.ts:172-174` ничего не сохраняет (`// state.dealDetail = payload;` — закомментировано), и уж тем более не трогает `sale`-слайс/список истории продаж (`historySellProduct` живёт в другом редьюсере).

**Итог:** продажа так и остаётся в статусе `debt` в `/crm/sell` и `/crm/market/history` навсегда, даже если клиент полностью расплатился. Отчётность/сверка по продажам будет считать её непогашенной бесконечно, хотя в разделе «Долги клиента» она уже закрыта.

**Решение:**
1. **Бэк** должен принимать привязку к POS-продаже при создании `Deal` — либо чинить `400` на реальный `sale_id`, либо (как уже предложено в `debt-v2-backend-implementation.md §5.6`) линковать `Sale` ↔ `Deal` самостоятельно на этапе checkout с `payment_method: debt`, в одной транзакции — это закрывает заодно и пункт 7 (атомарность) и этот пункт (связь).
2. **Бэк**: при полном погашении `Deal` (или при последнем платеже по графику) — переводить связанную `Sale.status` в `paid`.
3. **Фронт**: раскомментировать сохранение `dealDetail` в `clientSlice.ts`, и после успешного `payDebtDeal`/`refundDeal` рефетчить/патчить статус соответствующей продажи в `sale`-слайсе (когда бэк начнёт отдавать связь) — иначе кассир увидит актуальный статус только после ручного обновления страницы истории.

**Статус:** только зафиксировано, не исправлялось.

## 10. 🟡 Типизация продажи ослаблена почти везде — `any`/индекс-сигнатуры вместо конкретных типов

**Где:** `src/entities/sale/model/saleThunk.ts`, `src/entities/sale/model/saleSlice.ts`, `src/shared/lib/tools/posSaleCarts.ts`, `src/pages/cashier/ui/cashierPage.types.ts`, `src/pages/cashier/ui/paymentPage.types.ts`

**Проблема:** в самом важном для денег месте проекта типизация фактически выключена — это напрямую объясняет, почему баги 3, 5, 9 из этого файла вообще смогли появиться и остаться незамеченными компилятором.

1. **Все 28 thunk'ов в `saleThunk.ts`** объявлены как `createAsyncThunk<any, void | any>` — и аргумент, и результат `any`. Значит:
   - Ничто не мешает вызвать `returnSale(...)` без `shiftId` (баг 5) — TypeScript не подскажет, что поле забыто, потому что тип аргумента `any`.
   - Ничто не мешает `createDeal(...)` без `sale_id` (баг 9) — то же самое.
   - Результат любого thunk (`result.payload`) тоже `any` — обращение к `result.payload.sale_id` или `result.payload.debt_amount` не проверяется вообще, опечатка в имени поля даст `undefined` в рантайме, а не ошибку сборки.

2. **`saleSlice.ts`**: `initialState` — `start: null as any`, `posCarts: [] as any[]`, `history: [] as any[]` и так далее (~30 мест с `as any`). Экспортируемый хук `useSale()`:
   ```ts
   export const useSale = () => useSelector((state: any) => state.sale);
   ```
   `state.sale` — `any`. Это состояние читают буквально во всех хуках кассы (`currentSale`, `posCarts`, `activeSaleId`...) — то есть `currentSale.total`, `currentSale.items`, `currentSale.status` нигде не проверяются компилятором ни в одном из ~15 файлов кассы, которые к ним обращаются.

3. **Канонического типа `Sale`/`SaleItem`/`PosCart` нет вообще нигде в репозитории.** Проверил — ни `interface Sale`, ни `type SaleItem` не объявлены ни разу. `posSaleCarts.ts` — файл, который единолично отвечает за нормализацию ответа `/pos/sales/start/` и всех связанных операций — принимает и возвращает `any` в 21 месте (`normalizePosStartResponse(data: any)`, `mergeSaleIntoStateStart(state: any, sale: any, ...)` и т.д.). Как следствие — по всему проекту одно и то же поле продажи читается по-разному в разных местах с ручными фолбэками:
   - `item.unit_price || item.price`
   - `item.line_discount || item.discount_total`
   - `item.product || item.product_id`
   - `sale.total ?? sale.total_amount`
   - `raw.items_count ?? raw.itemsCount ?? raw.item_count`

   Это не всегда баг сам по себе (бэк действительно шлёт по-разному в разных версиях API), но без единого типа с задокументированными алиасами каждый файл придумывает свой список фолбэков заново — разойдись они хоть немного, получаем тихую потерю данных (ровно как в багах 3 и 9).

4. **ID-поля типизированы как `string | number` почти везде** (`CartLine.saleId/itemId/productId` в `cashierPage.types.ts`) — из-за этого по кассе разбросаны десятки сравнений вида `String(item.id) === String(pending.itemId)` вместо простого `===`. Это работает, но каждое такое место — потенциальная точка, где забыли завернуть в `String(...)` и сравнение молча всегда `false` (типичный источник «товар не находится в корзине» багов).

5. **Деньги типизированы непоследовательно**: где-то `number` (`total: number` в `PaymentPageProps`), где-то `number | string` (`PaymentSale.order_discount_total?: number | string`), где-то голая строка из API, которую в разных местах по-разному приводят (`parseFloat`, `Number(...)`, `.toFixed(2)` при отправке обратно). Общего `Money`-типа/хелпера нет — именно из-за этой пестроты возник баг 3 (`parseFloat(currentSale?.total || 0) || cart.reduce(...)`, где `0` по недосмотру трактуется как «нет данных»).

6. **Дублирующиеся и расходящиеся типы одного и того же понятия:** `AlertModalState` объявлен дважды — в `cashierPage.types.ts` (с `onConfirm?/onClose?`) и в `paymentPage.types.ts` (без них). Меняя логику алертов в одном месте, легко забыть про второй тип и получить рассинхрон (собственно то, что уже произошло с багом 2 — «подтверждение» и «закрытие» перепутаны местами именно в файле, где тип это позволяет).

7. **Escape-хэтчи `[key: string]: unknown`** в `CashierProduct`, `PaymentSale`, `PieceSaleModalState` и др. — сами по себе нормальная практика для «немного лишних полей от бэка», но здесь через них проходят и точно известные, всегда нужные поля (`status`, `client_id`, `is_wholesale`) — то есть индекс-сигнатура фактически глушит контроль типов там, где он был бы полезен и дёшев.

**Решение:**
1. Завести в `entities/sale` канонические интерфейсы `PosSale`, `PosSaleItem`, `PosCartTab` с явно перечисленными алиасами полей (по одному месту вместо десятка фолбэк-цепочек в разных файлах).
2. Типизировать `saleThunk.ts` по одному thunk'у за раз: `createAsyncThunk<PosSale, StartSaleArgs>` и т.п. вместо блانкет `<any, void | any>` — начать с самых денежных: `productCheckout`, `returnSale`, `createDeal` (ровно там, где уже нашли реальные баги от их безтиповости).
3. `useSale()` типизировать через `RootState` (`useSelector((state: RootState) => state.sale)`), убрать `as any` из `initialState`.
4. Один `Money`-хелпер (`toMoney(value): number`, `formatMoney(value): string`) вместо разбросанных `parseFloat`/`Number`/`.toFixed(2)`.
5. Объединить два `AlertModalState` в один общий тип в `shared/ui/AlertModal`, чтобы оба потребителя гарантированно были синхронны.

**Статус:** только зафиксировано, не исправлялось — большой объём, имеет смысл делать постепенно, начиная с thunk'ов, где уже нашли реальные баги.

## 11. 🔴 Возвраты не отражаются в итогах смены — ни в разбивке по долгу, ни в отдельном блоке «Возвраты»

**Где:** `src/pages/cashier/ui/ShiftPage.tsx:97-113` (`loadSales`) и `:291-320` (`salesSummary`), `src/pages/shifts/ui/ShiftDetail.tsx:592-627` (блок «Возвраты»), бэк — сериализатор смены (`GET /construction/shifts/{id}/`)

**Репро (реальный кейс):** продажа `2b303958-...` — `payment_method: "debt"`, `total: "135.00"`, `shift: "274a245d-..."`, по ней оформлен полный возврат → `status: "canceled"`. Ожидание: эта сумма должна уйти из «долга» смены и появиться как возврат — в т.ч. если бы продажу изначально оплатили наличными, возврат всё равно должен попасть в блок «Возвраты», а не потеряться. По факту — обе части неправильные, каждая по-своему.

**Проблема, часть 1 — экран кассы во время смены (`ShiftPage.tsx`) всё ещё считает возвращённую продажу «Долгом».**

Итоги на этом экране (карточки «Продажи / Наличные / Безналичные / Долг», `:538-577`) считаются не из `shift.payment_breakdown` с бэка, а руками, из отдельного запроса:

```js
// loadSales, строка ~87
const requestUrl = url || "/main/pos/sales/";
const params = { shift: openShiftId, page: currentPage };
const response = await api.get(requestUrl, { params });
// ...
const sales = (data?.results || []).map((sale) => ({
  ...
  status: sale.status === "paid" ? "Оплачен" : "Долг",
  statusType: sale.status === "paid" ? "paid" : "debt",
  ...
}));
```

Запрос `GET /main/pos/sales/?shift=X` не фильтрует по статусу — возвращает все продажи смены, включая `canceled`/`partially_returned`/`new`. Маппинг статуса бинарный: «всё, что не ровно `"paid"`, считается `"Долг"»`. Возвращённая продажа (`status: "canceled"`) тоже сюда попадает и трактуется как живой непогашенный долг — дальше `salesSummary` (`:291-320`) суммирует её 135.00 в карточку «Долг» и в общий «Продажи».

Показательно: в этом же репозитории уже есть правильная реализация той же задачи — `src/entities/shift/lib/paymentBreakdown.ts`:
```js
const SKIP_STATUSES = new Set(["canceled", "cancelled", "refunded", "returned"]);
const isSkippedSale = (sale) => SKIP_STATUSES.has(String(sale?.status ?? "").toLowerCase());
// ...
for (const sale of sales) {
  if (isSkippedSale(sale)) continue; // ← вот этого не хватает в ShiftPage.tsx
  ...
}
```
Её уже использует `CloseShiftPage.tsx` и `ShiftDetail.tsx` (панель «Способы оплаты» там верно показывает `debt: count 4`, без возвращённой). А главный экран кассы во время смены (`ShiftPage.tsx`) — свой, отдельный, не поправленный код без этой проверки.

**Проблема, часть 2 — блок «Возвраты» на `ShiftDetail.tsx` в принципе никуда не смотрит.**

Карточка «Возвраты» на `/crm/shifts/:id` (`:592-627`) — буквально захардкоженная вёрстка:

```jsx

<div className="shift-detail-page__detail-label">{t("crm.shifts.detail.cashPlain")}</div>
```

Ни `shift.returns_count`, ни `shift.returns_total`, ни вообще какая-либо переменная не используются — просто четыре литеральных `0` / `0.00 сом`. Соседние карточки на той же странице честно читают `shift.sales_total`, `shift.sales_count`, `shift.cashbox_name` (`:513-524`) — «Возвраты» единственный блок, который никогда не покажет ничего, кроме нуля, сколько бы возвратов ни было.

**И бэк тоже ничего не отдаёт под это.** В объекте смены (`GET /construction/shifts/{id}/`) нет полей `returns_count`/`returns_total`/разбивки по наличным-безналичным — только `sales_count`, `sales_total`, `cash_sales_total`, `noncash_sales_total`, `payment_breakdown`. **Итог:** возвращённая продажа сейчас не оказывается по-настоящему нигде — на кассе во время смены она всё ещё числится как «Долг» (часть 1), а на детальной странице смены, где для неё есть специально выделенный блок «Возвраты», он не работает вообще, независимо от того, был возврат или нет (часть 2).

   - `returns_count` — количество возвратов за смену;
   - `returns_total` — общая сумма;
   - `returns_cash` / `returns_noncash` — разбивка по факту возврата денег (наличные/безналичные), а не по исходному способу оплаты продажи — деньги могли вернуть не так, как приняли (см. пункт 1 в `sale-return-cashflow-backend.md` про переопределение способа возврата).
2. **Фронт, `ShiftDetail.tsx`**: как только поля появятся — забиндить карточку «Возвраты» на `shift.returns_count`/`shift.returns_total`/`shift.returns_cash`/`shift.returns_noncash` вместо литералов `0`.
3. **Фронт, `ShiftPage.tsx`**: переиспользовать `resolveShiftPaymentBreakdown`/`aggregateSalesPaymentBreakdown` из `entities/shift` вместо самодельного `salesSummary`, либо как минимум добавить проверку `isSkippedSale` перед классификацией статуса — чтобы возвращённая продажа не считалась «Долгом» ни на одном экране.

## 12. 🟡 После каждой продажи улетает лишний `GET` на только что оплаченную продажу и получает 404

**Где:** `src/pages/cashier/ui/components/CashierSubPages.tsx:107-138` (`onComplete`), `src/pages/cashier/ui/hooks/cashier/useCashierShifts.ts:364-386` (два эффекта синхронизации `sale_id` в URL), `src/features/create-sale/model/useMarketCashierMultiCart.ts:75-89` (`switchToCart`)

**Репро (из devtools):** сразу после `POST /pos/sales/{id}/checkout/` (201) и `POST /pos/sales/start/` (201, новая корзина) улетает `GET /pos/sales/{тот же id, что только что оплатили}/` → **404**.

**Причина — гонка между Redux-стейтом и URL:**

1. После успешной оплаты `onComplete` вызывает `multiCart.refreshCartsFromStart()` → `startSale()` создаёт новую корзину, `currentSale.id` в Redux меняется на новый. Только **после** этого `onComplete` явно чинит URL:
   ```js
   setSearchParams(prev => { p.set(MARKET_CASHIER_SALE_ID_PARAM, String(activeId)); return p; }, { replace: true });
   ```
2. Между обновлением Redux и применением `setSearchParams` есть окно, в котором `currentSale.id` уже новый, а `?sale_id=` в URL — ещё старый (только что оплаченный).
3. В этом окне срабатывает отдельный эффект в `useCashierShifts.ts`:
   ```js
   useEffect(() => {
     if (!urlSaleId || !openShiftId) return;
     if (String(currentSale?.id) === String(urlSaleId)) return; // не совпало — URL отстал
     multiCart.switchToCart(urlSaleId).catch(() => {});          // пытается вернуться на старую продажу
   }, [urlSaleId, openShiftId, currentSale?.id, multiCart]);
   ```
   Он видит рассинхрон «URL≠Redux» и решает, что нужно переключиться на продажу из URL — то есть на ту, что только что оплатили.
4. `switchToCart` слепо, без проверки статуса, шлёт `GET /pos/sales/{id}/` на эту продажу — а она уже финализирована и по этому эндпоинту больше не отдаётся → 404.

Соседний эффект («дописать `sale_id` в URL, если его нет», `:374-386`) тут не помогает — он реагирует только на **отсутствие** параметра в URL, а не на устаревшее значение, поэтому не может подстраховать это конкретное окно рассинхрона.

**Почему воспроизводится каждый раз, а не иногда:** `onComplete` всегда сначала обновляет Redux (`refreshCartsFromStart`), потом URL (`setSearchParams`) — порядок гарантированно создаёт это окно при каждом завершении оплаты, не только изредка.

**Видимые последствия:**
- Лишний 404-запрос и шум в логах/мониторинге бэка при каждой продаже.
- `multiCart.switching` на короткое время становится `true` (проброшено как проп `switching` в `CashierProductsPanel`/`CashierCartPanel`) — возможен короткий визуальный сбой/блокировка корзины сразу после оплаты.
- Кассиру ничего не видно — ошибка молча проглатывается (`.catch(() => {})`), глобальный axios-интерцептор реагирует только на 401.

**Решение:**
1. В `onComplete` обновлять URL (`setSearchParams`) **до** или **синхронно вместе с** обновлением активной продажи, а не отдельным шагом после `await` — либо вообще убрать эту ручную правку URL и доверить её единому источнику истины.
2. В эффекте `switchToCart(urlSaleId)` добавить защиту: не дёргать `getSale`, если `urlSaleId` совпадает с продажей, которая по локальному состоянию уже финализирована (например, хранить id последней оплаченной продажи в рефе и игнорировать его в этом эффекте один рендер).
3. Более надёжный вариант — синхронизировать `sale_id` в URL через `replace` в том же `dispatch`/reducer, что обновляет `activeSaleId`, чтобы Redux и URL менялись за один тик, а не двумя независимыми эффектами, которые могут гоняться друг за другом.

**Статус:** только зафиксировано, не исправлялось.
