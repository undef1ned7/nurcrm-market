# Исправление: долг v2 «по месяцам» падает 400 (`debt_days`/`debt_months`)

**Баг:** [sale-flow-bugs.md, пункт 8](../sale-flow-bugs.md#8--backend-долг-v2-по-месяцам-падает-400-debt_daysdebt_months-одновременно)
**Полный отчёт для бэка:** [docs/backend/kassa/debt-v2-months-xor-bug-backend.md](../backend/kassa/debt-v2-months-xor-bug-backend.md) — этот файл уже содержит репро, гипотезу причины и критерии приёмки, здесь — краткая выжимка + статус.
**Нужен бэк:** да, целиком
**Приоритет:** 🔴 критично — блокирует любую продажу в долг «по месяцам» на v2, а с 2026-09-29 договорились работать только с v2

---

## 1. Суть (коротко)

```
POST /main/clients/{id}/deals/
{ "debt_months": 3, "first_due_date": "...", "interval_months": 1, "installments": [...], "schedule_version": "v2", ... }
```
→ `400 {"debt_months": ["Нельзя одновременно указывать debt_days и debt_months."]}`, хотя `debt_days` в теле запроса нет вообще. По дням (`debt_days` + `interval_days`, без `debt_months`) тот же запрос проходит без ошибки.

## 2. Гипотеза причины

Поле `debt_days` модели, судя по всему, имеет дефолт (похоже, `30` — это видно из другого зафиксированного поведения: без `debt_days` в запросе бэк в ответе как-то возвращал `"debt_days": 30`). Этот дефолт, вероятно, подставляется на уровне модели ещё до XOR-проверки (`if debt_days and debt_months: raise ValidationError`), и валидатор видит «оба поля заполнены», хотя клиент прислал только `debt_months`.

Разбор дефолта и что именно нужно поправить в валидаторе — см. разделы 2–4 полного отчёта: [debt-v2-months-xor-bug-backend.md](../backend/kassa/debt-v2-months-xor-bug-backend.md).

## 3. Что нужно от бэка (кратко, полный текст — в основном файле)

1. Починить XOR-проверку так, чтобы она смотрела на **наличие поля в теле запроса**, а не на итоговое значение объекта после применения дефолтов модели.
2. Прогнать регрессионно оба сценария:
   - `debt_months: 4` → 4 ежемесячных платежа, без 400;
   - `debt_days: 10` + `interval_days: 2` → по-прежнему без 400 (не сломать то, что уже работает).

## 4. Что делает фронт

Ничего — payload уже полностью соответствует контракту (см. `debt-installment-schedule-backend.md`), фронт не занижает и не завышает поля. Единственное временное смягчение — если нужно продавать в долг прямо сейчас, до фикса бэка: в UI кассы можно временно скрыть/задизейблить выбор «по месяцам» в v2-графике с подсказкой «временно недоступно», оставив рабочий вариант «по дням». Это UX-решение, не обязательное, делать только если требуется снять острую боль для кассиров до релиза бэка.

## 5. Статус

Только задокументировано, ждём фикса на бэке. Ничего на фронте менять не нужно.
