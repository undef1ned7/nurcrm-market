# Исправление: автодооформление долга — очередь автоповтора + атомарность на бэке

**Баг:** [sale-flow-bugs.md, пункт 7](../sale-flow-bugs.md#7--сделка-долг-создаётся-вторым-запросом-после-checkout)
**Нужен бэк:** да — стратегическое решение (атомарность); фронтовая очередь — тактическая подстраховка на переходный период
**Приоритет:** 🟠 высокий — при сбое продажа остаётся в статусе «долг» без сделки, без единого способа это обнаружить

---

## 1. Проблема

`productCheckout` (перевод продажи в статус `debt`, списание склада, чек) и создание сделки — два независимых запроса, второй идёт после успешного первого:
1. `POST /main/debts/` — легаси для тарифа «Старт» (`usePaymentPage.ts:668-696`).
2. `dispatch(createDeal(...))` — основная сделка с графиком (`usePaymentPage.ts:698-751`).

Если второй (или оба) упадут — checkout уже подтверждён, откатывать нечего, кассир видит одно предупреждение и работает дальше. Данные расходятся молча, без сохранённого состояния для повтора.

## 2. Решение — часть A: атомарность на бэке (стратегически, приоритет)

### 2.1. Что нужно бэку

При `POST /main/pos/sales/{id}/checkout/` с `payment_method: "debt"` — создавать `Deal` **в той же транзакции**, что и сам checkout, а не полагаться на отдельный вызов `POST /clients/{id}/deals/` с фронта.

Фронт уже отправляет всё необходимое для этого прямо в теле `checkout` — поле `debt_schedule` (см. `usePaymentPage.ts:628-646` и контракт в `docs/backend/kassa/debt-installment-schedule-backend.md`, раздел «Checkout v2»):

```json
POST /main/pos/sales/{id}/checkout/
{
  "payment_method": "debt",
  "client_id": "...",
  "cash_received": "2000.00",
  "schedule_version": "v2",
  "debt_schedule": {
    "unit": "month",
    "count": 4,
    "interval_months": 1,
    "first_due_date": "2026-09-12",
    "installments": [...]
  }
}
```

Сейчас это поле, по документации, «желательно, не блокер» — бэк его может игнорировать. **Задача — перестать его игнорировать**: если `debt_schedule` присутствует и `payment_method === "debt"`, создавать `Deal` прямо внутри обработчика checkout, атомарно со списанием склада/сменой статуса продажи. Это одновременно:
- закрывает этот баг (нет второго запроса — нет второй точки отказа);
- закрывает пункт 9 из `sale-flow-bugs.md` (Sale и Deal физически создаются в одном месте, можно сразу проставить связь между ними — см. [09-sale-deal-linkage.md](./09-sale-deal-linkage.md)).

### 2.2. Алгоритм (псевдокод)

```python
@transaction.atomic
def checkout(request, sale_id):
    sale = get_sale_for_update(sale_id)  # select_for_update — блокировка от гонки с идемпотентностью (см. 01-idempotent-checkout.md)
    ...обычная логика checkout (списание склада, чек, статус)...

    if request.data.get("payment_method") == "debt":
        schedule = request.data.get("debt_schedule")
        deal = create_deal_for_sale(
            sale=sale,
            client_id=request.data.get("client_id"),
            amount=sale.total,
            prepayment=request.data.get("cash_received"),
            schedule=schedule,  # если передан — используется как есть, вместе с installments
        )
        sale.linked_deal = deal
        sale.save(update_fields=["linked_deal"])

    return sale_to_response(sale)
```

Если что-то в блоке создания `Deal` упадёт — вся транзакция откатывается **вместе с checkout**: продажа не переходит в статус `debt`, склад не списывается, кассир получает честную ошибку и может повторить попытку целиком, а не остаётся с наполовину сделанной операцией. Это принципиально лучше текущего поведения, где checkout уже необратимо прошёл к моменту сбоя `createDeal`.

### 2.3. Критерии приёмки (бэк)

- [ ] `checkout` с `payment_method: "debt"` + `debt_schedule` создаёт `Sale` и `Deal` одной транзакцией.
- [ ] Если создание `Deal` падает по любой причине (невалидный график, клиент не найден) — весь `checkout` откатывается, продажа остаётся в исходном статусе (не `debt`), склад не списан.
- [ ] Ответ `checkout` содержит ссылку на созданную сделку (`deal_id` или вложенный объект) — нужно для связи (см. пункт 9).
- [ ] Фронтовый отдельный `POST /deals/` для этого сценария становится необязательным — но не ломается, если фронт временно продолжает его слать (на время миграции), т.е. **дублирующий вызов не должен создавать вторую сделку** — тут пригодится идемпотентность из [01-idempotent-checkout.md](./01-idempotent-checkout.md), либо отдельная проверка «у этой продажи уже есть привязанная сделка — вернуть её, не создавать новую».

## 3. Решение — часть B: очередь автоповтора на фронте (тактически, пока бэк не готов)

Даже после фикса на бэке имеет смысл оставить эту подстраховку — легаси-запрос `/main/debts/` для тарифа «Старт» всё равно остаётся отдельным вызовом (см. `usePaymentPage.ts:668-696`), и его атомарность не покрывает пункт 2.

### 3.1. Персистентная очередь — `src/entities/sale/lib/debtDealQueue.ts`

```ts
export type PendingDebtDealTask = {
  id: string;                 // uuid, стабильный ключ идемпотентности задачи
  saleId: string;
  clientName: string;
  createDealPayload: Record<string, unknown>;  // аргументы для dispatch(createDeal(...))
  createDealDone: boolean;
  startDebtPayload: Record<string, unknown> | null;  // тело POST /main/debts/, null — если не требуется (не тариф «Старт»)
  startDebtDone: boolean;
  attempts: number;
  nextAttemptAt: number;      // epoch ms
  createdAt: number;
  lastError?: string;
};
```

Хранилище — `localStorage`, ключ `market_pending_debt_deals_v1`, значение — JSON-массив задач. Функции: `enqueuePendingDebtDeal`, `listPendingDebtDeals`, `processPendingDebtDeals(dispatch)`.

**Backoff:** `[10_000, 30_000, 60_000, 5*60_000, 30*60_000]` мс — растёт с каждой неудачной попыткой, дальше стабилизируется на 30 минутах, повтор до победного (финансовые данные не должны «сдаваться»).

**`processPendingDebtDeals`** — для каждой задачи, чьё время пришло:
1. Если `!startDebtDone && startDebtPayload` — пробует `POST /main/debts/`, при успехе помечает `startDebtDone: true` (best-effort — неудача здесь не блокирует попытку `createDeal`).
2. Если `!createDealDone` — пробует `dispatch(createDeal(...)).unwrap()`, при успехе — `createDealDone: true`, при неудаче — увеличивает `attempts`, считает следующий `nextAttemptAt`.
3. Если оба флага `true` — задача удаляется из очереди, кассиру/админу показывается ненавязчивый toast об успехе.
4. Если после `WARN_AFTER_ATTEMPTS` (например, 5) попыток задача всё ещё не закрыта — один раз показать `notify.warning` («не удаётся дооформить долг, система продолжит пробовать»), дальше молчать до следующего такого порога или до успеха.

### 3.2. Постановка в очередь

В `usePaymentPage.ts`, в catch-блоках `createDeal`/`/main/debts/` (`:668-751`) — вместо (или вместе с) текущего разового `showAlert`, вызывать `enqueuePendingDebtDeal({...})` с точными payload'ами, которые уже собраны в этом коде (просто сохранить их в переменные до вызова, а не только внутри try).

Заменить блокирующий `showAlert("warning", ...)` на `notify.info(...)` — раз система теперь сама разруливает ситуацию, не нужно требовать от кассира клика «ОК» на модалке.

### 3.3. Запуск процессора

Хук `useDebtDealQueueProcessor()` (например, в `src/features/create-sale/model/`):
- при монтировании — сразу `processPendingDebtDeals(dispatch)`, если очередь не пуста;
- интервал (например, 30с), пока очередь не пуста;
- слушатель `window.addEventListener("online", ...)` — повтор сразу после восстановления сети.

Монтировать в `useCashierPage.ts` (работает всё время, пока открыта касса) — этого достаточно для реалистичного сценария (касса — обычно постоянно открытая вкладка на выделенном устройстве на всю смену).

### 3.4. Идемпотентность самих запросов

Очередь на фронте не защищает от ситуации «запрос на самом деле прошёл на бэке, но фронт не получил ответ (таймаут) → повторная попытка создаёт вторую сделку». Нужно, чтобы `createDeal`/`POST /main/debts/` тоже поддерживали идемпотентность (см. [01-idempotent-checkout.md](./01-idempotent-checkout.md) — тот же паттерн, тот же `Idempotency-Key`, привязанный к `task.id`).

## 4. Тестирование

- Unit-тест на `debtDealQueue.ts`: постановка задачи → `processPendingDebtDeals` с замоканным `dispatch` (createDeal fails → succeeds на 2-й попытке) → задача удаляется из очереди только после обоих успехов.
- Unit-тест на backoff: 5 неудач подряд → `nextAttemptAt` растёт по расписанию, `notify.warning` вызывается ровно один раз на 5-й попытке.
- Ручной сценарий: отключить сеть перед вызовом `createDeal` (DevTools → offline), включить обратно через 15 секунд — задача должна сама дооформиться без перезагрузки страницы.

## 5. Статус

Часть A (бэк) — не начата, требует согласования с бэкенд-командой. Часть B (очередь на фронте) — спроектирована здесь и в переписке, код не писался (по явной просьбе — сначала только документация/поиск багов).
