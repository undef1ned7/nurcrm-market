# Исправление: связать Sale и Deal, переводить продажу в «оплачено» при погашении долга

**Баг:** [sale-flow-bugs.md, пункт 9](../sale-flow-bugs.md#9--оплата-долга-не-переводит-продажу-обратно-в-оплачено--sale-и-deal-никак-не-связаны)
**Нужен бэк:** да, основное решение — на бэке
**Приоритет:** 🔴 критично — отчётность по продажам показывает вечный «долг» даже после полного погашения

---

## 1. Проблема

`Sale` (`/main/pos/sales/{id}/`) и `Deal` (`/main/clients/{id}/deals/{id}/`) — два разных объекта, между которыми нет связи:

1. `createDeal` вызывается **без `sale_id`** (`usePaymentPage.ts:698-746`, ни v1-, ни v2-ветка его не передаёт) — намеренно, потому что POS-UUID (`/main/pos/sales/{id}`) не совпадает с ID Sale в модели deals, бэк раньше отвечал `400 {"sale_id": ["Указанная продажа не найдена."]}` (см. таблицу полей в `docs/backend/kassa/debt-installment-schedule-backend.md`).
2. Созданный `Deal` физически не знает, из какой продажи он появился.
3. При полном погашении (`payDebtDeal` → `POST /clients/{id}/deals/{id}/pay/`) обновляется только сам `Deal`. Бэк не может перевести `Sale.status` в `paid`, потому что связи никогда не было.
4. Даже если бы связь была — фронт тоже ничего не обновит сам: `payDebtDeal.fulfilled` в `src/entities/client/model/clientSlice.ts:172-174` не сохраняет ответ (`// state.dealDetail = payload;` — закомментировано), и не трогает `sale`-слайс.

## 2. Решение — бэк

### 2.1. Вариант 1 (предпочтительный) — линковать `Sale` ↔ `Deal` автоматически на checkout

Если бэк реализует атомарное создание `Deal` прямо внутри `checkout` (см. [07-debt-deal-retry-queue.md, раздел 2](./07-debt-deal-retry-queue.md#2-решение--часть-a-атомарность-на-бэке-стратегически-приоритет)) — связь появляется бесплатно: `Deal` создаётся с уже известным `sale.id` на бэке, фронту вообще не нужно передавать `sale_id` явно, конфликта UUID не возникает, потому что это внутренняя серверная операция, а не отдельный HTTP-запрос с фронта.

Это закрывает сразу два бага (7 и 9) одним изменением на бэке — рекомендуется делать вместе.

### 2.2. Вариант 2 (если атомарность пока не делается) — принимать `sale_id` в `POST /deals/`

Если создание `Deal` остаётся отдельным запросом с фронта:
- Убрать `400` на `sale_id`, соответствующий реальному `/main/pos/sales/{id}` — сейчас модель `Deal.sale` ссылается на какую-то другую сущность «Sale» (не POS), нужно либо завести отдельное поле (`pos_sale_id`), либо расширить существующий FK, чтобы принимать оба типа идентификаторов.
- Фронт в этом случае начинает передавать `saleId` в `createDeal` — thunk уже это умеет (`saleThunk.ts:595-596`, `if (saleId != null && saleId !== "") payload.sale_id = saleId;`), нужно только добавить `saleId: result.payload?.sale_id || result.payload?.id` (id только что созданной продажи из ответа checkout) в оба вызова `createDeal` в `usePaymentPage.ts:698-746`.

### 2.3. Обновление статуса продажи при погашении

Независимо от выбранного варианта связи — бэку нужно:
- при **полном** погашении `Deal` (`remaining_debt` достигает 0, включая оплату последнего платежа по графику) — переводить связанную `Sale.status` в `paid`;
- при **частичном** погашении — статус продажи можно оставить `debt` (или ввести отдельный статус вроде `partially_paid`, если это уже поддерживается где-то ещё в системе — свериться с `normalizeSaleStatus` на фронте, `src/shared/lib/tools/saleReturn.ts`, там сейчас только `paid | debt | partially_returned | canceled | new`, для частичного погашения долга отдельного статуса нет — нужно решить, заводить ли новый, или не менять статус до полного погашения);
- аналогично обработать `refundDeal` (возврат платежа по долгу) — если после возврата платежа продажа ранее считалась `paid`, а теперь снова есть остаток — статус должен вернуться в `debt`.

### 2.4. Критерии приёмки (бэк)

- [ ] `Deal`, созданный из POS-продажи (любым из двух вариантов выше), содержит ссылку на исходную `Sale`.
- [ ] Полное погашение `Deal` → `Sale.status` становится `paid`.
- [ ] Частичное погашение → статус `Sale` определён явно (решить и задокументировать, что именно показывается) — не должен молча оставаться в состоянии, не отражающем реальность.
- [ ] `refundDeal` (отмена платежа по долгу) корректно возвращает `Sale.status` обратно в `debt`, если это уместно.
- [ ] Ответ `GET /main/pos/sales/{id}/` включает ссылку на связанный `Deal` (`deal_id` или вложенный объект) — нужно фронту для прямых переходов «продажа → её долг» (полезно для UI истории продаж, не блокер, но крайне желательно).

## 3. Решение — фронт

### 3.1. Раскомментировать сохранение ответа в `clientSlice.ts`

```js
// src/entities/client/model/clientSlice.ts
.addCase(payDebtDeal.fulfilled, (state, { payload }) => {
  state.loading = false;
  state.dealDetail = payload;   // было закомментировано
})
```
То же для `refundDeal.fulfilled`, `updateDealDetail.fulfilled`, `onPayDebtDeal.fulfilled` — проверить каждый, сейчас везде одинаковый паттерн с закомментированной строкой.

### 3.2. Обновление статуса продажи после погашения (когда бэк начнёт отдавать связь)

После успешного `payDebtDeal`/`refundDeal`, если ответ содержит ссылку на связанную продажу (`payload.sale_id`/`payload.sale`):

```js
// там, где вызывается payDebtDeal (страница долгов клиента / DebtPaymentModal.tsx)
const result = await dispatch(payDebtDeal({ id, data, clientId })).unwrap();
if (result?.sale_id) {
  // Точечно обновить статус в списке истории продаж, если он там сейчас показан,
  // либо просто инвалидировать кэш истории, чтобы при следующем открытии
  // /crm/sell или /crm/market/history подтянулось актуальное состояние.
  dispatch(getSale({ id: result.sale_id })); // если пользователь тут же переходит к продаже
}
```

Конкретная реализация (точечный патч в списке истории vs. просто рефетч) зависит от того, что бэк реально вернёт — уточнить контракт ответа `payDebtDeal`/`refundDeal` с бэком до написания этого кода.

### 3.3. `createDeal` с `saleId` (если выбран вариант 2 на бэке)

```js
// usePaymentPage.ts, оба вызова createDeal (v1 и v2 ветки)
dispatch(createDeal({
  ...,
  saleId: result.payload?.sale_id || result.payload?.id,  // ← добавить, id только что оплаченной продажи
}))
```

## 4. Тестирование

- Как только бэк выкатит связь — end-to-end сценарий: продажа в долг → оплата всей суммы долга через `payDebtDeal` → открыть `/crm/sell`/`/crm/market/history` → статус продажи должен быть `paid`, без ручного обновления страницы (или с одним рефетчем, если решили не делать точечный патч).
- Частичное погашение → статус продажи ведёт себя так, как решено в п. 2.3, задокументированное поведение подтверждено тестом.

## 5. Статус

Только задокументировано. Основное решение зависит от бэка (раздел 2), фронтовая часть (раздел 3) — небольшая, но бессмысленна до того, как бэк определится с вариантом связи.
