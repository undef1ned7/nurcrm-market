# Исправление: возвраты должны корректно отражаться в итогах смены

**Баг:** [sale-flow-bugs.md, пункт 11](../sale-flow-bugs.md#11--возвраты-не-отражаются-в-итогах-смены--ни-в-разбивке-по-долгу-ни-в-отдельном-блоке-возвраты)
**Нужен бэк:** да — новые агрегаты на объекте смены
**Приоритет:** 🔴 критично — искажает финансовую отчётность по смене на двух разных экранах

---

## 1. Проблема (две независимые части)

**Часть 1 — `ShiftPage.tsx` (главный экран кассы во время смены) считает возвращённую продажу «Долгом».**
`src/pages/cashier/ui/ShiftPage.tsx:97-113` (`loadSales`) запрашивает `GET /main/pos/sales/?shift=X` без фильтра по статусу и маппит:
```js
status: sale.status === "paid" ? "Оплачен" : "Долг",
statusType: sale.status === "paid" ? "paid" : "debt",
```
Любой статус, кроме `"paid"` (включая `"canceled"` после возврата), попадает в «Долг» — `salesSummary` (`:291-320`) суммирует его сумму в карточку «Долг» и в общий «Продажи» наверху экрана.

**Часть 2 — блок «Возвраты» на `ShiftDetail.tsx` ни к чему не привязан.**
`src/pages/shifts/ui/ShiftDetail.tsx:592-627` — четыре литеральных `0` / `0.00 сом`, без единой переменной. Бэк тоже не отдаёт под это данные: в объекте `GET /construction/shifts/{id}/` нет `returns_count`/`returns_total`/разбивки по наличным-безналичным — только `sales_count`, `sales_total`, `cash_sales_total`, `noncash_sales_total`, `payment_breakdown`.

## 2. Решение — бэк

### 2.1. Новые поля в сериализаторе смены

Добавить в ответ `GET /construction/shifts/{id}/` (и в список `GET /construction/shifts/` — свериться, показывается ли карточка возвратов где-то ещё):

```json
{
  ...существующие поля...,
  "returns_count": 1,
  "returns_total": "135.00",
  "returns_cash": "0.00",
  "returns_noncash": "135.00"
}
```

**Ключевое требование (согласовано с пользователем):** `returns_cash`/`returns_noncash` считаются **по факту того, как деньги были фактически возвращены**, а не по исходному способу оплаты продажи. Пример: продажа оплачена наличными, но кассир по какой-то причине оформил возврат средств на карту (или наоборот) — сумма должна попасть в ту колонку, которая отражает реальное движение денег при возврате, а не то, чем изначально расплатились. Это та же логика, что уже описана для компенсирующего движения по кассе в [`sale-return-cashflow-backend.md`, §9.1](../backend/kassa/sale-return-cashflow-backend.md#91-переопределение-способа-возврата-денег-реальный-инцидент) («переопределение способа возврата денег») — переиспользовать тот же источник истины (`refund_method`, если он уже есть на компенсирующем движении по кассе, а не заново придумывать).

### 2.2. Что считать «возвратом» для этих агрегатов

Продажи со статусом, попадающим в уже существующий на фронте список исключений (`SKIP_STATUSES` в `src/entities/shift/lib/paymentBreakdown.ts`: `canceled`, `cancelled`, `refunded`, `returned`) — то есть полностью или частично возвращённые продажи, привязанные к этой смене (`sale.shift == shift.id`).

**Частичные возвраты** (`status: "partially_returned"`) — считать сумму именно **возвращённой части**, а не всей продажи целиком (иначе можно задвоить: часть продажи всё ещё в «Продажи», часть — в «Возвраты», но нельзя, чтобы вся сумма продажи попадала в оба агрегата одновременно). Источник суммы возврата — уже существующая операция `POST /pos/sales/{id}/return/`, у неё должна быть своя денежная сумма по факту возврата (не пересчитывать из `sale.total`, а брать фактическую сумму компенсирующего движения — это надёжнее, особенно при частичных возвратах и переопределении способа выдачи денег).

### 2.3. Критерии приёмки (бэк)

- [ ] `GET /construction/shifts/{id}/` содержит `returns_count`, `returns_total`, `returns_cash`, `returns_noncash`.
- [ ] Полностью возвращённая продажа (`canceled`) — учитывается в `returns_*`, полностью исключается из `payment_breakdown`/`sales_total` (уже так работает, судя по примеру в баге 11 — не сломать при добавлении новых полей).
- [ ] Частично возвращённая продажа — в `returns_*` попадает только возвращённая часть; оставшаяся часть продолжает корректно считаться в `sales_total`/`payment_breakdown`.
- [ ] `returns_cash`/`returns_noncash` — по факту способа возврата денег, а не по исходному способу оплаты продажи (сценарий «оплатили наличными → вернули иначе» должен корректно отразиться).
- [ ] Возврат, оформленный **в другую смену**, чем исходная продажа (если такое в принципе возможно в системе) — учитывается в смене, где был **оформлен возврат**, не в смене исходной продажи (уточнить у бэка, возможен ли вообще такой сценарий и как сейчас определяется `shift` у операции возврата).

## 3. Решение — фронт

### 3.1. `ShiftDetail.tsx` — забиндить карточку «Возвраты»

```jsx
// было: захардкоженные 0
<div className="shift-detail-page__detail-value">{shift.returns_count ?? 0}</div>
...
<div className="shift-detail-page__detail-value">
  {parseFloat(shift.returns_cash || 0).toFixed(2)} сом
</div>
...
<div className="shift-detail-page__detail-value">
  {parseFloat(shift.returns_total || 0).toFixed(2)} сом
</div>
...
<div className="shift-detail-page__detail-value">
  {parseFloat(shift.returns_noncash || 0).toFixed(2)} сом
</div>
```

(Обратить внимание на порядок полей в текущей вёрстке — «Количество возвратов» и «Наличные» в одном ряду, «Сумма возвратов» и «Безналичные» в другом, см. скриншот и структуру `:592-627` — просто сопоставить правильные поля с правильными ячейками.)

### 3.2. `ShiftPage.tsx` — не считать возврат «Долгом»

Заменить самодельный `salesSummary` на переиспользование уже существующей корректной логики:

```js
import { resolveShiftPaymentBreakdown } from "@entities/shift";

// вместо ручного построения salesData/salesSummary из GET /main/pos/sales/?shift=X:
const breakdown = resolveShiftPaymentBreakdown(currentShift, salesDataRaw);
// breakdown уже пропускает canceled/partially_returned через isSkippedSale
```

Если полностью переезжать на `resolveShiftPaymentBreakdown` сразу тяжело (разный формат данных для карточек «Наличные/Безналичные/Долг» на этом экране по сравнению с `ShiftPaymentBreakdown`-компонентом на `ShiftDetail.tsx`) — минимальный фикс: добавить ту же проверку `isSkippedSale` (или использовать уже существующий `normalizeSaleStatus` из `src/shared/lib/tools/saleReturn.ts`) прямо в `loadSales`:

```js
import { isSkippedSale } from "@entities/shift"; // экспортировать наружу, если сейчас internal
...
const sales = (data?.results || [])
  .filter((sale) => !isSkippedSale(sale))
  .map((sale) => ({ ... }));
```

Как только бэк отдаст `returns_*` (раздел 2) — этот же экран можно дополнительно обогатить карточкой возвратов, аналогичной `ShiftDetail.tsx`, если по UX это нужно и на экране активной смены, а не только в детальном просмотре.

## 4. Тестирование

- `ShiftDetail.tsx`: подставить мок `shift` с `returns_count: 1, returns_total: "135.00", returns_noncash: "135.00"` — карточка должна показать именно эти числа, не нули.
- `ShiftPage.tsx`: юнит-тест на `salesSummary`/новую логику — продажа со статусом `canceled` не должна попадать ни в `deferred`, ни в `total`.
- End-to-end (после того как бэк выкатит поля): оформить продажу в долг → оформить полный возврат → открыть `/crm/shifts/:id` для этой смены → «Возвраты» показывает 1 возврат на нужную сумму, «Способы оплаты» не показывает эту продажу как долг.
