# Исправление: итог чека не должен подменяться при `total = 0`

**Баг:** [sale-flow-bugs.md, пункт 3](../sale-flow-bugs.md#3--итог-чека-может-подмениться-суммой-без-скидки-при-total--0)
**Нужен бэк:** нет
**Приоритет:** 🔴 критично — прямой риск потребовать оплату за товар, который должен быть бесплатным

---

## 1. Проблема

`src/pages/cashier/ui/hooks/cashier/useCashierUi.ts:92`:

```js
const total =
  parseFloat(currentSale?.total || 0) ||
  cart.reduce((sum, item) => sum + (item.price || 0) * item.quantity, 0);
```

`0 || X` в JS — `0` ложно, поэтому при честном `total: "0.00"` с сервера (100% скидка, промо-товар, корзина после частичного возврата до нуля) выражение откатывается на `X` — сумму корзины **без скидок**.

## 2. Исправление

```js
const serverTotalRaw = currentSale?.total;
const hasServerTotal = serverTotalRaw != null && serverTotalRaw !== "";
const parsedServerTotal = hasServerTotal ? parseFloat(serverTotalRaw) : NaN;

const total = Number.isFinite(parsedServerTotal)
  ? parsedServerTotal
  : cart.reduce((sum, item) => sum + (item.price || 0) * item.quantity, 0);
```

Ключевое отличие: используем `Number.isFinite` на распарсенное значение и явную проверку на `null`/`""` на входе, а не `||` — так `0` из бэка остаётся `0`, а на локальный расчёт откатываемся только если сервер реально ничего не прислал (`undefined`/`null`/пустая строка) или прислал мусор, который не парсится в число.

## 3. Смежные места — проверить на ту же ошибку

Похожий паттерн `X || fallback` на денежных полях стоит проверить и в других местах, где `currentSale`/`sale` читается напрямую (проверено при разборе — сюда же может уйти любое новое место с `sale.total || ...`, `sale.subtotal || ...` и т.п.):

- `src/pages/cashier/ui/hooks/cashier/useCashierProducts.ts:531` — `const subtotal = parseFloat(currentSale?.subtotal || 0) || 0;` — тут итоговый фолбэк на `0` (а не на пересчёт корзины), поэтому падение до `0` при `subtotal: "0.00"` неотличимо от честного нуля — **не баг**, можно не трогать.
- `src/pages/cashier/ui/paymentPage.utils.ts` (`getPaymentAmounts`) — использует уже посчитанный `total` как аргумент, само по себе не пересчитывает — проверить, что вызывающий код (после фикса выше) передаёт туда уже исправленное значение.

## 4. Тест

Добавить unit-тест (или дополнить существующий, если для `useCashierUi` есть тестовый файл) на сценарий:
- `currentSale = { total: "0.00" }`, `cart = [{ price: 100, quantity: 2 }]` → ожидаемый `total === 0`, не `200`.
- `currentSale = { total: undefined }`, тот же `cart` → ожидаемый `total === 200` (фолбэк на корзину работает, когда сервер действительно не прислал число).
- `currentSale = null` (корзина ещё не создана) → фолбэк на корзину, без ошибок.

## 5. Бэк

Не требуется. Единственное, что стоит **устно уточнить у бэка** (не блокер): что именно означает `total: "0.00"` в ответе — всегда ли это «сумма после скидки равна нулю» (то, на что рассчитан фикс), или бывают случаи, когда `"0.00"` означает «сумма ещё не посчитана» (тогда фронту нужен отдельный признак «расчёт не готов», а не подмена нулём). Судя по остальным местам, где `total` читается напрямую без доп. проверок (`PaymentPage`, чеки, печать), в проекте уже подразумевается первый вариант — фикс с этим согласован.
