# Исправление: лишний 404 после каждой продажи (гонка URL/Redux)

**Баг:** [sale-flow-bugs.md, пункт 12](../sale-flow-bugs.md#12--после-каждой-продажи-улетает-лишний-get-на-только-что-оплаченную-продажу-и-получает-404)
**Нужен бэк:** нет
**Приоритет:** 🟡 низкий — не искажает данные, но лишняя нагрузка и шум в логах при каждой продаже

---

## 1. Проблема

После `checkout` → `startSale` (новая корзина) есть короткое окно, в котором `currentSale.id` в Redux уже новый, а `?sale_id=` в URL — ещё старый (только что оплаченный). Эффект в `useCashierShifts.ts:364-368` реагирует на это расхождение как на «нужно переключиться на продажу из URL» и вызывает `switchToCart(oldSaleId)`, который слепо шлёт `GET /pos/sales/{id}/` на уже финализированную продажу → 404.

Полный разбор цепочки — в самом баге, здесь сразу план исправления.

## 2. Варианты исправления (от простого к надёжному)

### Вариант A — синхронизировать URL и Redux в одном шаге (минимальное изменение)

В `CashierSubPages.tsx:107-138`, в `onComplete`, переставить порядок так, чтобы `setSearchParams` для нового `activeId` вызывался в том же тике, что и получение нового `activeId`, без промежуточного рендера с рассинхроном. Практически это уже почти так и есть (`setSearchParams` идёт сразу после `await multiCart.refreshCartsFromStart()`), проблема не в порядке кода, а в том, что **между строками кода Redux уже перерендерил `useCashierShifts`, а `setSearchParams` ещё не долетел до `useSearchParams()`** — это асинхронность React Router, а не порядок операторов в файле.

Более надёжно в рамках этого варианта — сразу **удалять** старый `sale_id` из URL перед созданием новой корзины, а не ждать, пока появится новый:

```js
// onComplete, до multiCart.refreshCartsFromStart()
setSearchParams(
  (prev) => {
    const p = new URLSearchParams(prev);
    p.delete(MARKET_CASHIER_SALE_ID_PARAM);  // убрать старый ID сразу
    return p;
  },
  { replace: true },
);
await multiCart.refreshCartsFromStart();
// ...дальше как сейчас — проставить новый activeId в URL
```

Тогда в промежуточном рендере `urlSaleId` будет `null`, а не старый id — эффект `useEffect(() => { if (!urlSaleId || ...) return; ... })` просто не сработает (условие `!urlSaleId` отсекает), вместо того чтобы пытаться загрузить старую продажу.

### Вариант B — защита прямо в `switchToCart` (более надёжно, не зависит от порядка эффектов)

В `src/features/create-sale/model/useMarketCashierMultiCart.ts`, `switchToCart` — не дёргать `getSale`, если целевой id — это продажа, которая по локально известному состоянию уже была только что финализирована. Например, хранить в рефе id последней успешно оплаченной продажи и на один цикл игнорировать попытку «переключиться» на неё:

```js
const lastCheckedOutSaleIdRef = useRef<string | null>(null);

// вызывать это из onComplete сразу после успешного checkout:
export function markSaleJustCheckedOut(saleId: string) {
  lastCheckedOutSaleIdRef.current = String(saleId);
}

const switchToCart = useCallback(
  async (saleId) => {
    if (!saleId || !shiftId) return;
    const id = String(saleId);
    if (id === lastCheckedOutSaleIdRef.current) {
      // Это продажа, которую только что оплатили в этой же сессии — не
      // пытаемся её загрузить, это гонка URL/Redux, а не реальный переход.
      lastCheckedOutSaleIdRef.current = null; // разово, не блокировать навсегда
      return;
    }
    ...остальное как сейчас...
  },
  [...],
);
```

Это более надёжный вариант, потому что не зависит от точного тайминга React/React Router — защита срабатывает на уровне бизнес-логики («не пытайся загрузить то, что мы сами только что закрыли»), а не на уровне «успели/не успели обновить URL вовремя».

### Вариант C — оба вместе (рекомендация)

Сделать оба: вариант A убирает race в подавляющем большинстве случаев, вариант B — страховка на случай, если где-то ещё в коде похожая гонка проявится (например, при быстром переключении между несколькими корзинами подряд). Вариант B дешёвый и низкорискованный, есть смысл добавить в любом случае.

## 3. Что НЕ нужно делать

- Не нужно менять сам `getSale`/бэкенд — 404 тут технически корректный ответ (продажи с таким статусом на этом эндпоинте больше нет), проблема не в ответе бэка, а в том, что фронт не должен был вообще спрашивать.
- Не нужно глушить 404 глобально в axios-интерцепторе — это скроет реальные 404 в других местах, где они действительно являются ошибкой.

## 4. Тестирование

- Ручная проверка: DevTools → Network, отфильтровать по `pos/sales`, провести полную оплату — после фикса не должно быть `GET /pos/sales/{id}/` на id только что оплаченной продажи.
- Юнит-тест на `switchToCart` (вариант B): вызвать `markSaleJustCheckedOut("X")`, затем `switchToCart("X")` — `dispatch(getSale(...))` не должен быть вызван.

## 5. Бэк

Не требуется.
